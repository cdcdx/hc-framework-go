# 23. 事件与消息总线

> **文档角色**：事件驱动的统一消息模型与 MQ 适配器设计说明
> **对应源码**：`internal/event/`、`internal/mq/`
> **权威源约定**：事件类型以 `internal/event/events.go` 为准；事件→主题映射以 `internal/mq/topics.go` 为准；MQ 配置以 [202_配置参考.md](202_配置参考.md) 为准

---

## 一、设计目标

事件系统是本框架异步解耦的基石，实现三个核心目标：

1. **业务解耦**：核心业务（挂机结算、商城兑换）通过发布事件触发副作用（任务进度更新、积分投递），不直接调用下游服务。
2. **可靠投递**：关键路径（积分调整）通过 Outbox 模式保证跨库最终一致；生产端失败降级本地 DLQ 并在恢复后自动补发。
3. **可插拔后端**：通过统一 Producer/Consumer 接口，同一套业务代码可对接 Kafka / RabbitMQ / RocketMQ / 内存总线，仅需切换 `mq.type` 配置。

## 二、事件模型

### 2.1 事件类型

定义在 `internal/event/events.go`，共 7 种事件：

| 事件类型 | 触发点 | 消费者 | 说明 |
|----------|--------|--------|------|
| `user.registered` | 注册成功 | 日志服务 | 异步记录注册审计日志 |
| `user.logged_in` | 登录成功 | 日志服务 | 异步记录登录审计日志 |
| `idle.settled` | 挂机结算 | 任务服务 | 驱动挂机相关任务进度 |
| `task.completed` | 任务完成 | — | 预留，暂无非幂等消费者 |
| `shop.redeemed` | 兑换成功 | 任务服务 | 驱动兑换相关任务进度 |
| `user.points.adjust` | 积分变动 | Outbox 补偿器 | Outbox 模式跨进程最终一致 |
| `cache.invalidate` | 写降级 | 缓存刷新 | 异步刷新各 Pod L2 缓存 |

### 2.2 消息结构

```go
type Message struct {
    TraceID   string            // 链路追踪 ID（W3C traceparent）
    Timestamp time.Time         // 事件发生时间
    Type      string            // 事件类型（如 "idle.settled"）
    Payload   interface{}       // 具体事件数据（JSON 序列化）
    EventID   string            // 全局唯一事件 ID（用于消费端幂等去重）
    Metadata  map[string]string // 扩展元数据
}
```

- **EventID**：生产端由 UUID v4 生成，消费端经 `event_dedup` 表实现 effectively-once 语义。
- **TraceID**：从业务上下文透传，实现端到端链路追踪。

### 2.3 事件→主题映射

由 `internal/mq/topics.go` 的 `topicMapOf()` 单一来源维护，按 MQ 类型和配置分派：

```
user.registered   ──────→ user-events
user.logged_in    ──────→ user-events
idle.settled      ──────→ idle-events
task.completed    ──────→ task-events
shop.redeemed     ──────→ shop-events
user.points.adjust──────→ user-points
cache.invalidate  ──────→ cache-events
```

每个 MQ 后端（Kafka/RabbitMQ/RocketMQ）可有独立主题名配置，未配置时统一回落 `mq.kafka.topics.*`。

## 三、消息队列适配器

### 3.1 架构概览

```
                    ┌──────────────────────────┐
                    │    Producer 接口          │
                    │  Send / SendSync / Close  │
                    └──────┬────────┬──────────┘
                           │        │
              ┌────────────┼────────┼──────────────┐
              │            │        │              │
         ┌────▼────┐ ┌────▼────┐ ┌─▼─────┐  ┌─────▼──────┐
         │  Kafka  │ │RabbitMQ │ │Rocket │  │ Memory/Noop│
         │Producer │ │Producer │ │MQ Pro │  │  (本机/空)  │
         └─────────┘ └─────────┘ └───────┘  └────────────┘
              │            │         │
              └────────────┼─────────┘
                      ┌────▼────┐
                      │producer │
                      │ Base    │ ← 共享：异步队列、溢出池、熔断、DLQ、replay
                      └─────────┘
```

**生产者统一异步模型**：「入队即返回」——`Send` 仅写入有界 channel，后台 worker 协程真正发送；队列满转入溢出池；溢出池也满则降级本地 DLQ 文件（`replayLoop` 每 30s 自动补发）。

三套 Broker 生产者的核心差异仅在于 `sendOne`（真正发送一条消息）和 `relay`（DLQ 补发一条）的具体实现，其余生命周期（队列管理、熔断、DLQ、关闭）由 `producerBase` 统一提供。

### 3.2 各适配器特性

| 特性 | Kafka | RabbitMQ | RocketMQ | Memory | Noop |
|------|-------|----------|----------|--------|------|
| 发送模式 | 异步 + 熔断 | 异步 + channel 池 | 异步 + 重试 | 同步丢弃 | 空操作 |
| 发送确认 | DeliveryTimeout | Publisher Confirm | SendSync 回执 | 无(进程内) | 无 |
| 重试 | 指数退避 3 次 | 指数退避 3 次 | `send_retries` (默认 2) | 无 | 无 |
| DLQ | 本地 JSONL 落盘 | 本地 JSONL 落盘 | 本地 JSONL 落盘 | 缓冲满丢弃 | 计数丢弃 |
| 消费模式 | 无消费组+分区直读 | Topic 交换机+手动 Ack | PushConsumer+%RETRY% | 有界 channel | 空操作 |
| 消费并发 | worker 池(默认 32) | channel 池(默认 32) | SDK 管理 | `concurrency` 可配 | 无 |
| 分区顺序 | `ordered_commit` 可选 | 不保证 | 不保证 | 不保证 | 不保证 |

### 3.3 生产者异步发送路径

```
Send(msg) → queue(有界channel, 默认8192)
              ↓
          loop 协程取消息
              ↓
   ┌── sendOne(msg) ──────────────────┐
   │  成功 → 返回                      │
   │  熔断打开 → requeue(200ms退避)    │
   │  真实错误 → fallbackToDLQ         │
   └───────────────────────────────────┘
              ↓
          队列满时 → 溢出池(sendSem, 默认256)
              ↓
          溢出池也满 → DLQ 落盘 (replayLoop 30s补发)
```

### 3.4 消费端重试与去重

```
Subscribe(topic, handler)
    ↓
handle(msg)
    ↓
callHandlerSafe(ctx, msg, handler)  ← panic 兜底 recover
    ↓
┌─── 成功 → Ack / 推进 offset ───────────┐
│   重试错误 → retryProcess               │
│     ├── 指数退避: base * 2^attempt      │
│     ├── 耗尽 → DLQ(消费者)/死信交换机    │
│     └── handler panic → 不重试直接 DLQ   │
│  不可恢复错误 → DLQ                      │
└─────────────────────────────────────────┘
```

- **幂等去重**：`EventID` 经 `event_dedup` 表在事务内先标记后执行，确保重投不重复累加进度。
- **消费进度**：Kafka 支持 `ConsumerProgressStore`（文件/SQL），`ordered_commit` 模式同步落盘缩小崩溃窗口。
- **全局死信**：生产端 DLQ 可自动 replay 补发；消费端 DLQ 为存档语义，需人工处理。

## 四、积分可靠投递（Outbox 模式）

积分调整是关键写路径，采用**跨库最终一致**的 Outbox 模式：

```
1. 业务事务内: 更新积分 + INSERT points_outbox(状态=pending)
2. 后台 RelayLoop: 扫描 pending 记录 → 发布 user.points.adjust 事件
3. 消费端: PointsOutboxApplier.ApplyPointsAdjust → 更新状态=applied
4. 补偿: RelayLoop 对长期 pending 的记录重试补偿
```

**关键保证**：
- 业务事务与 outbox 写入在同一 DB 事务内，两者原子成功或回滚。
- 事件发布失败不阻塞业务（RelayLoop 异步补偿）。
- 消费端幂等：`ApplyPointsAdjust` 检查 `points_outbox` 状态，已 applied 的跳过。

## 五、监控与可观测性

MQ 层通过统一 `Metrics` 接口上报 Prometheus 指标：

| 指标 | 类型 | 标签 | 说明 |
|------|------|------|------|
| `mq_producer_send_total` | Counter | type, topic, result | 生产者发送结果(success/failure) |
| `mq_producer_dlq_total` | Counter | type, topic | 降级到本地 DLQ 的累计消息数 |
| `mq_producer_dropped_total` | Counter | type, topic | 真正丢弃的消息数(memory 满/nop) |
| `mq_dlq_backlog` | Gauge | type, topic | 待补发的 DLQ 积压数 |
| `mq_consumer_dlq_backlog` | Gauge | type, topic | 消费侧待人工处理的毒消息数 |
| `mq_consumer_fetch_errors_total` | Counter | type, topic | 消费端拉取错误计数 |

告警规则见 [403_可观测性与告警.md](./403_可观测性与告警.md) §2.3、§四。

## 六、配置速查

```yaml
mq:
  type: kafka                    # kafka / rabbitmq / rocketmq / memory / none
  kafka:
    brokers: ["127.0.0.1:9092"]
    topics:
      user_events: "user-events"
      idle_events: "idle-events"
      task_events: "task-events"
      shop_events: "shop-events"
      user_points: "user-points"
      cache_events: "cache-events"
    producer:
      delivery_timeout: 5s       # 发送超时
      queue_size: 8192           # 异步队列大小
    consumer:
      worker_pool_size: 32       # 消费并发
      ordered_commit: false      # 分区内顺序提交
  rabbitmq:
    pool_size: 32                # channel 池大小
    send_timeout: 10s
  rocketmq:
    send_timeout: 3s
    send_retries: 2
```

完整字段见 [202_配置参考.md](./202_配置参考.md) §mq。
