# 定时抢购（高并发 / 高可用 / 易扩展）设计方案

> 本文档是「商品定时抢购」功能的**设计单一来源（SSOT）**：需求映射、并发模型、防超卖两道防线、
> 高并发削峰、高可用自愈、易扩展运维接口与容量规划。
> 接口契约（字段 / 错误码）见 `04_API参考.md`；迁移 SQL 见 `migrations/business/`；指标清单见 `09_可观测性与告警.md`。

---

## 1. 需求映射

| 需求 | 实现 |
|---|---|
| xx:xx 特定时间开放 | `ShopFlashActivity.StartTime` / `EndTime` 时间窗校验 |
| xx 商品限量 x 个 | `LimitQty`，独立管理，与 `ShopItem.Stock` 解耦（一个商品可挂多场不同限量的抢购） |
| 先到先得 | 全局 FIFO 扣减（Redis 原子预扣 + DB 条件更新行锁串行） |
| 限定个数内入库兑换 | 两道防线都通过 → 同一事务内建订单 + 扣积分（入库） |
| 限定个数外直接返回不入库 | 任一道防线判定售罄 → 事务内返回错误回滚，**绝不创建订单 / 扣积分**（不入库） |
| 每人限购 | `PerUserLimit`：Redis 每人计数 + 用户分布式锁 + DB 订单数 三重把关 |

核心不变量：**全局不超卖（成功订单数 ≤ LimitQty）、每人不超额（单用户成功数 ≤ PerUserLimit）、超量请求零入库。**

---

## 2. 防超卖两道防线（核心）

抢购最终以 **DB 条件更新为权威**，Redis 预扣是前置的**削峰快速拦截层**。

### 2.1 第一道：Redis 原子预扣（削峰，可选）

`cache.Manager.TryAcquireFlashSale` 一段 Lua 脚本在 Redis 单线程内原子完成：
- 若 `stock` 计数器不存在，用 `LimitQty` 初始化（仅首请求承担，或由预热任务提前填好）；
- 校验每人已抢 `HGET(users, userID) ≥ PerUserLimit` → 返回 `-2`（超每人限购）；
- 校验 `stock ≤ 0` → 返回 `-1`（已抢光）；
- 否则 `DECR stock` + `HINCRBY users` → 返回剩余库存。

超出限量 / 每人限购的请求在此**直接拒绝，不触达 DB**，海量无效请求在 Redis 层被消化。
L2（Redis）不可用时本道自动跳过，全交由 DB 兜底，**不阻断抢购**。

预扣成功但最终未入库（DB 判定售罄 / 积分不足 / 事务失败）时，由 `ReleaseFlashSale` 回滚名额，
避免「Redis 扣了、DB 没成」的库存幽灵占用。

### 2.2 第二道：DB 条件更新（权威，必走）

`repository.AcquireFlashQuota`：

```sql
UPDATE shop_flash_activities
   SET sold_qty = sold_qty + 1
 WHERE id = ? AND sold_qty < limit_qty;
```

行锁天然串行，`RowsAffected == 0` 即已抢光。只有它成功，才在同一事务内
`创建订单 → 写积分流水 → 写积分 Outbox`（同提交）；否则事务内返回 `ErrFlashSaleSoldOut`
回滚，**不入库**。即便 Redis 层被绕过或计数漂移，DB 仍是不可逾越的最终防线——**零超卖**。

### 2.3 每人限购三重把关

1. **Redis 每人计数**（削峰）：`flashsale:users:{id}` Hash，超 `PerUserLimit` 直接拒；
2. **用户分布式锁**：`redeem:flash:lock:{userID}:{activityID}`，串行化同一用户对同一活动的并发抢购，防止并发绕过；
3. **DB 订单数**（权威）：`CountUserFlashOrders` 以 `(activity_id, user_id)` 联合索引计数，无 Redis / 计数漂移时仍严格限制。

## 3. 高并发：削峰与缓存

开抢瞬间流量可达平时的千倍，关键在「把无效请求挡在 DB 之前」+「热点读走缓存」。

### 3.1 库存预扣削峰（见 §2.1）
海量「已抢光 / 超限购」请求在 Redis 层即被拦截，DB 承接的请求量 ≤ 实际可售量 + 少量边界竞争。

### 3.2 活动元信息三级缓存
`FlashRedeem` / `FlashActivities` 读取活动配置（时间窗 / 限量 / 价格）走三级缓存
（`flashsale:activity:{id}`、`flashsale:activities:active`，TTL 默认 5s）。
开抢瞬间用户轮询列表 / 详情的 DB 读取被缓存削减约两个数量级。
TTL 取短（5s）以平衡「削峰」与「活动状态 / 下架最终一致」——状态变更最多 5s 后对所有客户端可见。

### 3.3 提前预热（自动 + 手动）
- **自动**：调度器每 15s 由 **Leader** 执行 `WarmupDueFlashSales`，扫描「即将开抢（提前 2min）/ 已开始」
  的活动，以 DB 权威剩余值（`limit_qty - sold_qty`）强制对齐 Redis 库存，使开抢瞬间削峰层已就绪。
- **手动**：运营接口 `POST /admin/flash/activities/{id}/warmup` 立即预热。
预热幂等（`Reconcile` 强制覆盖），多副本重复执行无副作用。

## 4. 高可用：容错、自愈与可观测

### 4.1 透明降级
- L2 不可用 → 跳过 Redis 预扣，纯 DB 兜底（不阻断）；
- 缓存未启用 → 活动读直连 DB；创建 / 预热降级为 no-op；
- 积分 Outbox 投递失败 → 由后台 RelayLoop 补偿，不影响本次兑换结果。

### 4.2 库存对账自愈
进程崩溃可能导致「Redis 预扣未回滚」的库存漂移。调度器预热任务与手动 `sync` 接口均以 DB 权威值
重置 Redis 计数器（`cache.ReconcileFlashSale`），异常后自动恢复健康状态，无需人工介入。

### 4.3 选主保护定时任务
预热 / 对账任务在多副本部署下通过 `cluster.LeaderElector` 门控，**仅 Leader 执行**，
避免重复写；无选主时各副本均执行（重复对齐幂等安全）。Leader 租约到期自动释放，实现故障转移。

### 4.4 可观测指标（Prometheus，见 `09`）
| 指标 | 含义 |
|---|---|
| `shop_flash_redeem_total{result}` | 抢购结果计数：success / sold_out / user_limit / not_started / ended / other。`sold_out`+`user_limit` 占比反映削峰拦截效果 |
| `shop_flash_warmup_total{result}` | 库存预热 / 对账计数：warmed / skipped / error |
| `shop_flash_active_activities` | 当前进行中活动数（gauge） |

`other` 持续抬升提示 DB / 缓存 / 积分等下游异常，应配置告警。

## 5. 易扩展：运营配置接口（易扩展）

抢购活动通过运营接口配置，无需改代码发版。所有 `/api/v1/admin/flash/*` 接口需请求头
`X-Admin-Token: <admin.token>`，与用户 JWT 体系分离；`admin.token` 为空时一律 403。

> **配置方式**：`admin.token` 在 `config.yaml`（及 `config.stress.yaml` / `config.example.yaml`）的 `admin.token` 字段配置；
> 生产环境推荐用环境变量 `APP_ADMIN_TOKEN` 注入（viper 自动覆盖，避免明文落地）。K8s 部署见 `deployments/secret.yaml`。
> k6 压测需通过 `ADMIN_TOKEN` 传入同一串（见 `scripts/k6/shop_flash.sh`）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/flash/activities` | 活动列表（含已结束，全状态） |
| GET | `/api/v1/admin/flash/activities/:id` | 活动详情 |
| POST | `/api/v1/admin/flash/activities` | 创建活动（自动预热 + 写缓存） |
| PUT | `/api/v1/admin/flash/activities/:id` | 更新活动（限量 / 时间窗 / 每人限购 / 状态；不改动 `sold_qty`） |
| POST | `/api/v1/admin/flash/activities/:id/end` | 下架 / 结束 |
| POST | `/api/v1/admin/flash/activities/:id/warmup` | 手动预热 Redis 库存 |
| POST | `/api/v1/admin/flash/activities/:id/sync` | 库存对账（事故后修复） |

用户侧接口：`GET /api/v1/shop/flash/activities`（进行中列表）、`POST /api/v1/shop/flash/redeem`（抢购）。
完整字段与错误码见 `04_API参考.md`。

新增活动只需调运营接口，**水平扩展的 Pod 通过缓存 / DB / 调度器自动感知**，无需重启或改配置。

## 6. 容量规划与边界

- **DB 写入上限**：每场抢购的 DB 写入 ≈ 成功订单数（≤ `LimitQty`），与瞬时 QPS 解耦——削峰层把无效请求挡在 DB 外。
- **Redis 单 Key 压力**：`stock` 计数器为单 Key 热点，但仅 `DECR`/`INCR` 原子操作，Redis 单实例即可支撑数十万 TPS；
  集群部署时 `flashsale:stock:{id}` 与 `flashsale:users:{id}` 带相同 hash tag 保证同 slot，Lua 可原子执行。
- **已知边界**：
  - 活动元信息缓存 5s 最终一致，下架后最多 5s 内仍可抢（极小窗口，可接受）；
  - Redis 库存漂移在「进程崩溃」极端场景下最多造成 1 个名额偏保守（少卖不超卖），由对账自愈；
  - 每人限购以 DB 订单数为最终权威，Redis 计数为削峰；Redis 不可用时不削弱限购正确性。

## 7. 数据流（抢购成功）

```
用户 ──POST /shop/flash/redeem──▶ handler
   │
   ├─① 鉴权 + 用户分布式锁(串行化同用户并发)
   │
   ├─② Redis 原子预扣(TryAcquireFlashSale) ──超量/超限购──▶ 直接返回(不入库)
   │        │ 成功
   │        ▼
   ├─③ DB 每人限购计数校验(CountUserFlashOrders)
   │
   ├─④ 校验商品/积分
   │
   └─⑤ 事务: AcquireFlashQuota(条件更新) ──售罄──▶ 回滚 + 释放Redis(不入库)
            ├─ 建订单
            ├─ 写积分流水
            └─ 写积分 Outbox
          ▼ 提交成功 → 释放Redis预扣保持 → 返回订单(入库)
```
