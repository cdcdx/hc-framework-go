# 消息队列技术选型参考

> 通用参考：覆盖市面主流消息队列 / 流平台，按类别分组，分析同类产品的差异、适用场景、核心特点、性能参数、可靠性与扩展能力。供技术选型时横向比对，不与本框架具体配置耦合（具体配置见 [202_配置参考.md](./202_配置参考.md)）。
>
> 与 [501_数据库技术选型参考.md](./501_数据库技术选型参考.md) 第九节"消息/流平台"的关系：本文是其深化与扩展——15 仅作 5 个队列的速览，本文覆盖 19 个产品并细化可靠/事务/延迟/顺序/堆积等队列专属维度，末尾给出本框架 Kafka / RabbitMQ / RocketMQ 三队列的压力测试方案。

## 一、高吞吐流式消息队列

> 以「顺序追加日志 + 分区并行」为核心，吞吐优先于单条延迟，适合事件流、日志管道、数据集成。

| 平台 | 水平扩展 | 持久化 | 单节点吞吐 | 端到端延迟 | 协议 | 核心定位 |
|------|:--:|:--:|:--:|:--:|--------|------|
| Kafka | ✅ 分区 | ✅ 顺序日志 | 100万~200万 msgs/s | 1~10ms | 自有(TCP) | 高吞吐流式标准 |
| Redpanda | ✅ 分区 | ✅ 顺序日志 | 100万~300万 msgs/s | 1~5ms | Kafka 兼容 | Kafka 的 C++ 重写 |
| Pulsar | ✅ 分区 | ✅ 分层(BookKeeper) | 100万~200万 msgs/s | 1~5ms | 自有 | 计算存储分离+多租户 |
| Amazon Kinesis | ✅ 分片 | ✅ 托管 | 自动扩缩 | <1s | HTTP | AWS 托管流 |

### 1. Apache Kafka
- **数据模型**：分区有序日志（Topic → Partition → Offset），消息不可变、可回溯
- **典型场景**：事件总线、日志采集、数据管道、事件溯源、埋点追踪、流计算（Kafka Streams/Flink source）
- **核心特点**：极高吞吐（顺序落盘 + 零拷贝）、持久化 + 任意 offset 回溯、发布订阅、生态最成熟（Connect/Streams/Schema Registry）、KRaft 去 ZK（3.3+）
- **缺点**：运维复杂（分区再均衡、存储扩容）；批处理优化致单条延迟较高；无内置灵活路由（只有 partition key）；4.0 KRaft 下部分老客户端 group 协议不兼容
- **性能参数**：
  - 延迟：P50 1~3ms, P99 5~10ms（Producer → Broker → Consumer，batching 开）
  - 吞吐：100万~200万 msgs/s（单 Broker，小消息）；集群可达千万级
  - 备注：关闭 batching（linger.ms=0）延迟可降到亚毫秒但吞吐骤降；acks=all 牺牲部分吞吐换持久性
- **可靠性**：acks=all + min.insync.replicas≥2 → 持久化不丢；ISR 机制；事务（精确一次）支持

### 2. Redpanda
- **数据模型**：Kafka 协议兼容的分区日志（无 ZK，单二进制）
- **典型场景**：Kafka 协议替代、不愿引入 ZK/JVM 的场景、边缘/资源受限环境的高吞吐流
- **核心特点**：C++ 实现、线程 per 核心（Seastar）、无 ZK、Kafka API 完全兼容、内置 Schema Registry + HTTP proxy、资源占用低
- **缺点**：生态年轻（社区小于 Kafka）；企业功能（分层存储/多租户）需 Redpanda Cloud/Enterprise；部分 Kafka 高级特性支持滞后
- **性能参数**：
  - 延迟：P50 1~2ms, P99 3~5ms（C++ 无 GC 抖动）
  - 吞吐：100万~300万 msgs/s（单节点，官方 benchmark 常优于 Kafka 2~6 倍）
  - 备注：相同硬件下吞吐/延迟优于 Kafka；JVM 调优负担消失
- **可靠性**：Raft 复制（替代 ISR）；acks=all 持久化；与 Kafka 一致的 exactly-once 语义

### 3. Apache Pulsar
- **数据模型**：Topic 分区 + 分层存储（Broker 无状态 + BookKeeper 日志层）
- **典型场景**：多租户事件中心、跨地域复制（geo-replication）、IoT 海量消息、需计算存储独立扩展的场景
- **核心特点**：计算存储分离（Broker 无状态、扩容不搬数据）、原生多租户（tenant/namespace）、分层存储（热 BookKeeper + 冷 S3）、 Functions（轻量流计算）
- **缺点**：运维复杂（BookKeeper + ZooKeeper，3.x 可去 ZK）；社区与生态小于 Kafka；客户端库不如 Kafka 丰富
- **性能参数**：
  - 延迟：P50 1~3ms, P99 < 5ms（BookKeeper 持久化写入）
  - 吞吐：100万~200万 msgs/s（单 Broker）；存储层可独立扩展突破 broker 瓶颈
  - 备注：分层存储使冷数据成本接近对象存储；多租户隔离能力强
- **可靠性**：BookKeeper 副本（quorum 写）；跨地域复制原生支持；exactly-once（事务）

### 4. Amazon Kinesis (Data Streams)
- **数据模型**：分片（Shard）顺序流，托管流式数据
- **典型场景**：AWS 生态内的事件流、日志/埋点采集、实时分析（Firehose/Lambda/Kinesis Analytics）
- **核心特点**：全托管、按分片计费、与 AWS 服务深度集成、自动分片扩缩（enhanced fan-out）
- **缺点**：AWS 锁定；费用随分片数 + PUT/GET 记录数递增（成本敏感）；单分片 1MB/s 写入上限；延迟相对 Kafka 略高
- **性能参数**：
  - 延迟：P50 100~300ms（典型），enhanced fan-out 可 < 200ms
  - 吞吐：单分片 1MB/s 或 1000 records/s 写；读 2MB/s（enhanced fan-out 每消费者 2MB/s）
  - 备注：扩容靠增加分片数（无法自动平滑，需 reshard）；按用量计费，高吞吐场景成本可能高于自建 Kafka
- **可靠性**：数据保留 24h~365 天可配；分片内有序；持久化跨多 AZ

> **同类对比**：Kafka 通用流式标准、生态最全；Redpanda Kafka 协议的高性能无 ZK 替代；Pulsar 多租户 + 计算存储分离；Kinesis AWS 托管按量计费。

## 二、业务可靠消息队列

> 以「灵活路由 + 消息确认 + 死信」为核心，单条投递可靠性优先于吞吐，适合业务解耦、任务分发。

| 平台 | 水平扩展 | 持久化 | 单节点吞吐 | 端到端延迟 | 协议 | 核心定位 |
|------|:--:|:--:|:--:|:--:|--------|------|
| RabbitMQ | ✅ 集群 | ✅ | 1万~5万 msgs/s | <1ms | AMQP | 灵活路由+可靠投递 |
| ActiveMQ Artemis | ✅ 集群 | ✅ | 5万~15万 msgs/s | <1ms | AMQP/Core | ActiveMQ 下一代 |
| ActiveMQ Classic | ⚠️ 有限 | ✅ | 1万~3万 msgs/s | 1~5ms | OpenWire/AMQP | 传统 JMS |

### 5. RabbitMQ
- **数据模型**：交换机（Exchange）+ 队列（Queue）+ 绑定（Binding），AMQP 模型；消息消费后即删除
- **典型场景**：任务队列、应用解耦、流量削峰、RPC、订单异步处理、需要灵活路由的业务消息
- **核心特点**：AMQP 标准、灵活路由（Direct/Topic/Fanout/Headers）、publisher confirm + 消费手动 Ack、死信队列（DLX）、延迟插件、多协议（STOMP/MQTT）
- **缺点**：吞吐低于 Kafka（单条消息模型）；大量堆积性能下降（队列过长）；持久化 + 镜像队列吞吐大幅下降；Erlang 运维门槛
- **性能参数**：
  - 延迟：P50 < 0.5ms, P99 < 5ms（非持久化或 confirm 命中）
  - 吞吐：1万~5万 msgs/s（单节点，持久化 + ACK）；非持久化可达 5万~10万
  - 备注：单消息延迟极低但吞吐有限；Quorum Queue 提升可靠但吞吐略降；流（Stream）模式可逼近 Kafka 吞吐
- **可靠性**：publisher confirm + 消费 Ack + DLX；Quorum Queue（Raft）高可用；镜像队列（已逐步被 Quorum 替代）

### 6. ActiveMQ Artemis
- **数据模型**：基于日志的 JMS 队列/主题（非 KV），支持 AMQP/MQTT/STOMP/OpenWire
- **典型场景**：Java/Jakarta EE 生态的 JMS 队列、企业内部消息总线、RabbitMQ 的开源替代（AMQP）
- **核心特点**：ActiveMQ 下一代（非 Java 也可用）、日志型存储（高性能）、AMQP 1.0 原生、支持 JMS 2.0、无文件锁瓶颈
- **缺点**：生态/社区小于 RabbitMQ；国内案例少；与 ActiveMQ Classic 配置不兼容（迁移成本）
- **性能参数**：
  - 延迟：P50 < 0.5ms, P99 < 5ms（日志存储，持久化）
  - 吞吐：5万~15万 msgs/s（单节点，日志型持久化，显著高于 Classic）
  - 备注：持久化吞吐优于 RabbitMQ（日志顺序写）；非持久化更高
- **可靠性**：日志复制（HA pairs）；AMQP 事务；死信地址

### 7. ActiveMQ Classic
- **数据模型**：JMS 队列/主题，基于 KahaDB/LevelDB 持久化
- **典型场景**：遗留 Java 系统的 JMS 队列、传统企业消息总线
- **核心特点**：JMS 1.1 标准、OpenWire/AMQP 多协议、成熟稳定、Spring 集成良好
- **缺点**：架构老旧、性能远不如 Artemis；大流量下 KahaDB 锁瓶颈；社区已逐步转向 Artemis
- **性能参数**：
  - 延迟：P50 1~5ms, P99 5~20ms
  - 吞吐：1万~3万 msgs/s（单节点，KahaDB 持久化）
  - 备注：新项目不应再选 Classic，应选 Artemis 或 RabbitMQ
- **可靠性**：KahaDB 持久化 + 主从复制；JMS 事务

> **同类对比**：RabbitMQ 路由灵活、生态最广；Artemis 性能更强（日志型）适合 JMS/AMQP；ActiveMQ Classic 仅遗留系统维护。

## 三、分布式事务消息队列

> 以「事务消息 + 延迟/定时 + 顺序」为核心，适合电商交易、金融最终一致性场景。

| 平台 | 水平扩展 | 持久化 | 单节点吞吐 | 端到端延迟 | 协议 | 核心定位 |
|------|:--:|:--:|:--:|:--:|--------|------|
| RocketMQ | ✅ 分区 | ✅ CommitLog | 10万~100万 msgs/s | <1ms | 自有 | 事务+延迟+顺序消息 |
| TubeMQ | ✅ 分区 | ✅ | 50万~100万 msgs/s | 1~5ms | 自有 | 腾讯海量消息 |

### 8. Apache RocketMQ
- **数据模型**：Topic + 队列（读/写队列分离），CommitLog 顺序写 + ConsumeQueue 索引
- **典型场景**：分布式事务最终一致性（交易/库存/积分）、电商异步解耦、延迟/定时消息、顺序消息、金融通知
- **核心特点**：事务消息（半消息 + 本地事务回查）、18 个内置延迟级别（5.x 支持任意延迟）、严格顺序消息、百万级吞吐、阿里背书 + 国内生态好
- **缺点**：依赖 NameServer（5.x Controller 模式可去）；海外社区弱于 Kafka；部分高级功能商业化（商业版）；延迟消息 4.x 仅固定级别
- **性能参数**：
  - 延迟：P50 < 0.5ms, P99 < 5ms（同步发送，CommitLog 顺序写）
  - 吞吐：10万~100万 msgs/s（单 Broker，取决于消息大小与磁盘）
  - 备注：事务消息有额外回查开销；顺序消息吞吐受单分区串行限制
- **可靠性**：同步刷盘 + 主从同步复制 → 不丢；事务消息保证本地事务与发送原子；消费失败 %RETRY% → %DLQ%（broker 侧死信）

### 9. Apache TubeMQ (原腾讯 TUBEMQ)
- **数据模型**：分区队列，偏海量日志/消息堆积场景
- **典型场景**：海量数据采集、大数据管道、腾讯内部海量消息（替代部分 Kafka 场景）
- **核心特点**：C++/Java 混合、超高堆积能力（TB 级）、低资源占用、腾讯出品并捐赠 Apache
- **缺点**：社区小、文档少；事务/延迟等业务能力弱于 RocketMQ；非腾讯系团队采用风险高
- **性能参数**：
  - 延迟：P50 1~3ms, P99 < 5ms
  - 吞吐：50万~100万 msgs/s（单节点，主打堆积不降速）
  - 备注：堆积场景表现优于 Kafka（不因堆积而吞吐下降）；业务消息能力有限
- **可靠性**：Master/Partition 多副本；ACK 确认

> **同类对比**：RocketMQ 事务+延迟+顺序业务消息首选；TubeMQ 海量堆积管道（弱业务能力）。

## 四、轻量云原生消息队列

> 以「轻量、低延迟、易部署」为核心，适合微服务通信、边缘/IoT。

| 平台 | 水平扩展 | 持久化 | 单节点吞吐 | 端到端延迟 | 协议 | 核心定位 |
|------|:--:|:--:|:--:|:--:|--------|------|
| NATS (JetStream) | ✅ | ✅ JetStream | 1000万+ msgs/s | <0.1ms | 自有 | 轻量云原生 |
| NSQ | ✅ | ✅ 磁盘 | 5万~10万 msgs/s | <1ms | 自有 | Go 实时分布式 |
| ZeroMQ | ❌(库) | ❌ | 数百万~千万 msgs/s | <0.1ms | 自有 | 嵌入式消息库 |

### 10. NATS / JetStream
- **数据模型**：Subject 发布订阅；Core NATS 为 at-most-once（无持久化），JetStream 提供 streams（持久化 + 回溯）
- **典型场景**：微服务间异步通信、边缘/IoT 设备消息、云原生 Service Mesh 控制面、轻量事件总线
- **核心特点**：极轻量（单一 Go 二进制）、千万级吞吐、亚毫秒延迟、JetStream 持久化（acks/exactly-once）、Leaf Nodes 跨地域、原生多租户
- **缺点**：持久化能力（JetStream）弱于 Kafka/Pulsar；生态工具不如大型 MQ 丰富；国内案例少
- **性能参数**：
  - 延迟：P50 < 0.1ms, P99 < 0.5ms（Core NATS at-most-once）；JetStream P99 < 1ms
  - 吞吐：1000万+ msgs/s（单节点，Core pub/sub）；JetStream 百万级
  - 备注：延迟与吞吐均为消息队列天花板；JetStream 持久化会降低到百万级
- **可靠性**：JetStream 提供 at-least-once/exactly-once + 持久化；Core NATS 无持久化（网络断即丢）

### 11. NSQ
- **数据模型**：Topic + Channel（每个 channel 收到全部消息副本），无 broker、去中心化 nsqlookupd 发现
- **典型场景**：Go 生态实时消息分发、轻量任务队列、本地/小规模分布式消息
- **核心特点**：纯 Go、单二进制部署、无中心 broker、水平扩展简单、HTTP 管理接口
- **缺点**：吞吐与生态不如 Kafka/RocketMQ；持久化能力弱（磁盘队列）；无事务/延迟消息；社区活跃度下降
- **性能参数**：
  - 延迟：P50 < 0.5ms, P99 < 1ms
  - 吞吐：5万~10万 msgs/s（单节点）
  - 备注：轻量易用，但大规模/高可靠场景不如主流 MQ
- **可靠性**：磁盘队列持久化 + ACK；无强一致副本（靠多 channel 消费者）

### 12. ZeroMQ
- **数据模型**：非 broker 的嵌入式消息库（socket 抽象），无持久化、无 broker
- **典型场景**：进程间/节点间超低延迟通信、HPC、金融交易内部总线、自建消息拓扑
- **核心特点**：极低延迟（无 broker）、多种模式（pub/sub/req/rep/push/pull）、几十种语言绑定
- **缺点**：非完整 MQ（无持久化/无 broker/无路由中心）；无消息可靠性保证（应用自行实现）；无集群管理
- **性能参数**：
  - 延迟：P50 < 0.1ms, P99 < 0.5ms（无 broker，进程间/本地）
  - 吞吐：数百万~千万 msgs/s（取决于拓扑与网络）
  - 备注：本质是「智能 socket 库」，适合自建通信层，不替代消息中间件
- **可靠性**：无（应用层自行实现重试/持久化）

> **同类对比**：NATS 轻量云原生全功能；NSQ Go 轻量分发；ZeroMQ 嵌入式通信库（非 broker）。

## 五、云托管消息服务

> 全托管免运维，按量计费，适合云上业务、不想自建 MQ 的团队。

| 服务 | 云厂商 | 持久化 | 吞吐 | 延迟 | 模型 | 核心定位 |
|------|------|:--:|:--:|:--:|--------|------|
| AWS SQS/SNS | AWS | ✅ | 自动扩缩 | <10ms | 队列+Pub/Sub | AWS 托管消息 |
| Azure Service Bus | Azure | ✅ | 自动扩缩 | <10ms | 队列+主题 | 企业消息托管 |
| Google Cloud Pub/Sub | GCP | ✅ | 自动扩缩 | <100ms | Pub/Sub | GCP 托管流 |
| 阿里云 RocketMQ/MNS | 阿里云 | ✅ | 自动扩缩 | <5ms | 多模型 | 国内托管 MQ |
| 腾讯云 TDMQ | 腾讯云 | ✅ | 自动扩缩 | <5ms | 多模型(Pulsar/RocketMQ/Kafka) | 多协议托管 |

### 13. AWS SQS / SNS
- **数据模型**：SQS 为队列（Standard/FIFO），SNS 为发布订阅；常组合 SNS→SQS 扇出
- **典型场景**：AWS 生态内任务队列、事件通知、Serverless（Lambda 触发）、微服务解耦
- **核心特点**：全托管、无限伸缩、Standard 至少一次（可能重复）、FIFO 精确一次 + 顺序、SNS 扇出
- **缺点**：AWS 锁定；Standard 模式不保证顺序且可能重复；FIFO 吞吐受限（3000 msgs/s/分区）；费用按请求计
- **性能参数**：
  - 延迟：P50 10~30ms, P99 < 100ms（API 轮询模型）
  - 吞吐：Standard 无硬上限（按需）；FIFO 3000 msgs/s（分区）
  - 备注：延迟高于自建 MQ（HTTP API + 轮询）；长轮询可降低空轮询成本
- **可靠性**：消息持久化（多 AZ）；至少一次（Standard）/ 精确一次（FIFO）；DLQ 支持

### 14. Azure Service Bus
- **数据模型**：队列 + 主题/订阅（含规则过滤），企业级消息
- **典型场景**：Azure 生态企业应用集成、B2B 消息、需会话/事务的企业消息
- **核心特点**：事务、会话（顺序）、死信、重复检测、计划消息、AMQP 1.0
- **缺点**：Azure 锁定；费用随吞吐/连接数递增；非 Azure 生态采用少
- **性能参数**：
  - 延迟：P50 < 10ms, P99 < 50ms
  - 吞吐：标准层按吞吐单元计费；高级层独享
  - 备注：企业消息能力（事务/会话）强于 SQS；适合 .NET/Azure 生态
- **可靠性**：事务、死信、重复检测；持久化多副本

### 15. Google Cloud Pub/Sub
- **数据模型**：主题 + 订阅（至少一次，支持顺序与精确一次）
- **典型场景**：GCP 生态事件流、Dataflow/Firebase 触发、BigQuery 流式入库
- **核心特点**：全托管、无限伸缩、at-least-once（新版可选 exactly-once）、push/pull 模式、Schema 注册
- **缺点**：GCP 锁定；延迟相对自建高；费用按数据量计
- **性能参数**：
  - 延迟：P50 50~100ms, P99 < 1s（push 模式）
  - 吞吐：自动扩缩（按区域，可达百万级 msgs/s）
  - 备注：与 BigQuery/Dataflow 深度集成；全球路由
- **可靠性**：至少一次（默认）/ 精确一次（beta）；持久化；DLQ 支持

### 16. 阿里云消息队列 (RocketMQ / Kafka / MNS)
- **数据模型**：托管 RocketMQ/Kafka/MNS 多产品线
- **典型场景**：阿里云生态电商/金融、不想自建 RocketMQ 的团队、Serverless 事件
- **核心特点**：托管版 RocketMQ（事务/延迟/顺序）、与阿里云 EventBridge/FC 集成、MNS 轻量队列
- **缺点**：阿里云锁定；高级功能按规格计费；跨可用区延迟
- **性能参数**：
  - 延迟：P50 < 5ms, P99 < 50ms（RocketMQ 规格）
  - 吞吐：按实例规格（标准/铂金），铂金可达百万级
  - 备注：国内合规/可用区优势；事务消息托管首选
- **可靠性**：多副本 + 跨可用区；事务消息；DLQ

### 17. 腾讯云 TDMQ
- **数据模型**：托管 Pulsar / RocketMQ / Kafka / CMQ 多协议
- **典型场景**：腾讯云生态、多租户消息中心、需多协议统一的团队
- **核心特点**：Pulsar 为核心（多租户/分层存储）、兼容 RocketMQ/Kafka 协议、CMQ 队列模型
- **缺点**：腾讯云锁定；多协议映射有功能损耗；文档/社区不如原生
- **性能参数**：
  - 延迟：P50 < 5ms, P99 < 50ms
  - 吞吐：按集群规格弹性
  - 备注：多协议托管减少 MQ 种类；Pulsar 多租户隔离强
- **可靠性**：多副本；跨可用区；DLQ

> **同类对比**：AWS SQS/SNS 简单队列+扇出；Azure Service Bus 企业事务消息；GCP Pub/Sub 流式托管；阿里云/腾讯云国内合规+多协议托管。

## 六、轻量级 / 嵌入式队列

> 不独立部署 broker，依托已有组件或进程内实现，适合轻量/中小规模。

| 方案 | 类型 | 持久化 | 吞吐 | 延迟 | 核心用途 |
|------|------|:--:|:--:|:--:|------|
| Redis Streams | 内存+持久化 | ✅ AOF/RDB | 10万~50万 msgs/s | <1ms | 轻量队列/流 |
| Beanstalkd | 内存+磁盘 | ✅(可选) | 1万~5万 jobs/s | <1ms | 轻量任务队列 |

### 18. Redis Streams
- **数据模型**：内存日志流（XADD/XREAD/XRANGE），消费组（XGROUP）+ pending entries list
- **典型场景**：轻量消息队列、已有 Redis 的中小规模事件流、任务分发、Stream 聚合
- **核心特点**：复用 Redis 基础设施、消费组 + 确认（XACK）、回溯（XRANGE）、低延迟
- **缺点**：内存容量受限（成本高）；大堆积触发淘汰/逐出风险；集群模式跨 slot 限制；不如专业 MQ 的路由/事务/延迟
- **性能参数**：
  - 延迟：P50 < 0.5ms, P99 < 1ms（纯内存）
  - 吞吐：10万~50万 msgs/s（单节点，取决于消息大小与持久化）
  - 备注：AOF 持久化吞吐略降；适合「已有 Redis、不想引入新 MQ」的场景
- **可靠性**：AOF appendfsync=always → 强持久化但吞吐降；消费组 XACK 确认；无原生 DLQ（需应用实现）

### 19. Beanstalkd
- **数据模型**：tube → job（带优先级/延迟/TTR 的任务）
- **典型场景**：轻量任务队列、延迟任务、后台 job 分发
- **核心特点**：极简、优先级、延迟/定时任务、TTR（超时重投）、C 实现
- **缺点**：无集群/高可用（单点）、持久化弱（binlog）、无消费组、社区不活跃
- **性能参数**：
  - 延迟：P50 < 0.5ms, P99 < 1ms
  - 吞吐：1万~5万 jobs/s（单节点）
  - 备注：仅适合单机/小规模任务队列；生产高可用需自建代理
- **可靠性**：binlog 持久化（可选）；TTR 保证 job 最终执行；无副本

> **同类对比**：Redis Streams 复用 Redis 生态、功能较全；Beanstalkd 极简延迟任务、无高可用。

## 十二、Kafka / RabbitMQ / RocketMQ 三队列压力测试方案

> 目标：在同一套业务语义（本框架 `mq.Producer`/`mq.Consumer` 接口）下，横向压测三队列的**生产吞吐、消费吞吐、端到端延迟、堆积恢复、故障降级**能力，为选型与容量规划提供量化依据。
>
> 设计原则：① 复用本框架真实代码路径（不写单独压测 stub，保证数据贴近生产）；② 三队列统一压测负载与指标口径；③ 同时用各 MQ 官方 benchmark 工具做「裸金属基线」剥离框架开销。

### 12.1 压测环境搭建

#### 12.1.1 Broker 部署（单机对齐，docker-compose）

### 12.2 压测场景与指标

#### 场景一：纯生产吞吐（Producer Throughput）

- **方法**：N 个生产者 goroutine 持续 `Send` 固定时长（如 5min），记录发送总量与 `recordSend` 成功/失败计数。
- **变量**：消息大小（256B/1KB/4KB）、生产者并发数（1/8/32/128）、acks 强度。
- **指标**：
  - 生产吞吐（msgs/s 与 MB/s）
  - 发送成功率（`mq_producer_send_total{result="success"}` / 总）
  - DLQ 降级量（`mq_producer_dlq_total`）
  - 生产者 P99 入队延迟（`Send` 返回耗时）
- **预期**：Kafka/RocketMQ 吞吐显著高于 RabbitMQ；acks=all 下 Kafka 吞吐下降明显。

#### 场景二：纯消费吞吐（Consumer Throughput）

- **方法**：预灌入 M 条消息后启动消费者，handler 为空操作（sleep 0），记录消费完毕耗时。
- **变量**：消费并发（worker_pool_size / prefetch / PushConsumer 并发）、ordered_commit 开关。
- **指标**：
  - 消费吞吐（msgs/s）
  - 消费延迟（handler 调用到完成）
  - 端到端延迟（生产时间戳 → 消费完成时间戳，需在消息体带 `Timestamp`）
- **预期**：Kafka 无消费组直读吞吐高；ordered_commit=true 会显著降低单分区吞吐；RabbitMQ prefetch 调大提升吞吐。

#### 场景三：端到端延迟（Latency）

- **方法**：低速率（如 1000 msgs/s）持续发送，每条消息带生产时间戳，消费时计算延迟分布。
- **变量**：acks、batching（Kafka linger.ms）、confirm 模式。
- **指标**：P50 / P95 / P99 / P999 端到端延迟。
- **预期**：RabbitMQ 单条延迟最低；Kafka batching 开启会抬高 P99；RocketMQ 同步发送延迟稳定。

#### 场景四：堆积恢复（Backlog Recovery）

- **方法**：生产者高速灌入 1000 万条消息后停止，启动消费者排空，记录排空耗时与吞吐曲线。
- **指标**：
  - 排空吞吐（msgs/s）
  - 堆积期间 broker 内存/磁盘占用
  - 堆积期间消费延迟是否恶化
- **预期**：Kafka/TubeMQ 堆积不降速；RabbitMQ 堆积过长性能下降；RocketMQ CommitLog 顺序读恢复稳定。

#### 场景五：故障注入与降级（Resilience）

- **方法**：稳定发送中，`docker stop` broker 30s 后 `docker start`，观察框架降级与恢复行为。
- **指标**：
  - 熔断器状态变更（`OnStateChange` 日志）
  - DLQ 落盘量（`mq_producer_dlq_total`）与 replay 补发量
  - 消息丢失量（发送总量 - 消费总量 - DLQ 剩余）
  - 恢复时间（broker 起来到熔断半开→关闭）
- **预期**：三队列均应「不丢消息」（DLQ + replay 兜底）；熔断打开期间 requeue 不落 DLQ；恢复后 replay 自动补发。这是验证 §3.29~3.31 一致性改动的关键场景。

#### 场景六：裸金属基线（官方工具）

剥离框架开销，用各 MQ 官方 benchmark 工具测同一负载，作为框架压测的参照上限：

| 队列 | 官方压测工具 | 命令示例 |
|------|-------------|---------|
| Kafka | `kafka-producer-perf-test` / `kafka-consumer-perf-test` | `kafka-producer-perf-test --topic bench --num-records 10000000 --record-size 1024 --throughput -1` |
| RabbitMQ | `rabbitmq-perf-test` (Java) | `rabbitmq-perf-test -h 127.0.0.1 -u guest -p guest -t fanout -s 1024 -x 32 -y 32` |
| RocketMQ | `rocketmq-client-go/v2` benchmark / `org.apache.rocketmq.benchmark.Producer` | `sh bin/mqadmin -n 127.0.0.1:9876 ... ; sh benchmark/producer.sh` |

> 对比公式：框架吞吐 / 官方基线 = 框架开销比。若开销比 < 80%，说明框架异步队列/熔断/DLQ 路径无明显瓶颈；若过低，定位是溢出池、record 指标还是序列化。

### 12.3 指标采集与可视化

本框架已内置 Prometheus 指标（`internal/mq/metrics.go`）：

| 指标 | 含义 | 用途 |
|------|------|------|
| `mq_producer_send_total{mq_type,topic,result}` | 发送成功/失败计数 | 吞吐与成功率 |
| `mq_producer_dlq_total{mq_type,topic}` | 降级本地 DLQ 计数 | 故障降级量 |
| `mq_producer_dropped_total{mq_type,topic}` | 真正丢弃计数 | 内存总线/禁用场景丢失量 |

Grafana 看板建议面板：
1. **吞吐面板**：`rate(mq_producer_send_total{result="success"}[1m])` 按 mq_type 分组
2. **成功率面板**：`success / (success+failure)`
3. **降级面板**：`rate(mq_producer_dlq_total[1m])`
4. **延迟面板**：消费侧自埋点 P50/P99（在 handler 计算端到端延迟并上报）
5. **broker 资源面板**：CPU/内存/磁盘/网络（node_exporter + broker 自带 metrics）

### 12.4 压测执行步骤（推荐顺序）

1. `docker compose -f docker-compose.bench.yml up -d` 起三队列 + 监控
2. 跑**场景六（官方基线）**记录裸金属上限
3. 切 `mq.type=kafka` 跑场景一~五，记录指标
4. 切 `mq.type=rabbitmq` 重复
5. 切 `mq.type=rocketmq` 重复
6. 汇总三队列 × 六场景的对比表（吞吐/延迟/成功率/恢复时间）
7. 计算框架开销比，定位瓶颈
