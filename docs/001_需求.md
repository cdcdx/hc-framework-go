## 一、总体架构目标
- 搭建高并发后台框架：高可用、可扩展、可观测。
- 支撑亿级总用户、千万级在线用户，系统全年可用性 ≥ 99.99%。
- 核心性能指标：
    - 读接口 P99 < 50ms（L1 命中）/ P99 < 100ms（L2 命中）/ P99 < 500ms（回源 DB）。
    - 写接口 P99 < 200ms（不含异步任务）。
    - 缓存命中率 ≥ 95%。
    - 核心写接口峰值 ≥ 5000 TPS。
- 故障隔离：任何单一组件故障不影响整体服务可用性（降级运行）。

## 二、请求链路
- 业务数据请求链路：
    - 客户端 => 负载均衡层(Nginx/LVS/K8s Ingress) => 服务层(Go/Gin) => 中间件链 => 三级缓存层 => 数据库层。
    - 中间件分三层：全局链（Recovery → Trace → RequestInfo → RequestLogger → CORS → Metrics）→ v1 组链（RateLimit）→ 路由级（SecurityIPLimit + Captcha 作用于认证接口，Auth + CircuitBreaker 作用于业务路由）。
- 三级缓存矩阵全覆盖：
    - L1(Ristretto 本地内存，<1ms) => L2(Redis/Valkey 分布式，1-5ms) => L3(MySQL/PSQL/MongoDB，10-200ms)。
    - 全路径穿透/击穿/雪崩防护：
        - 穿透防护：布隆过滤器（Redis Bitmap，容量 1 亿，误判率 1%）+ 空值缓存（TTL 60s）。
        - 击穿防护：热点 Key 回源时加 Redis SETNX 分布式锁（EX 10s），未获取锁的协程自旋等待（50ms 间隔，最多 10 次）。
        - 雪崩防护：TTL = 基础 TTL × (0.8 ~ 1.2) 随机偏移。
        - 一致性保障：写入后延迟双删（立即删 L1+L2 + 500ms 异步二次删 L1），失败进入死信日志。

## 三、可观测性与链路追踪
- 溯源追踪：
    - 基于 OpenTelemetry SDK，服务层全链路集成 TraceID，从 HTTP 请求到 Kafka 消息生产消费全程透传。
    - HTTP 请求从 Header `X-Trace-Id` 提取或自动生成 UUID v4，设置 Response Header `X-Trace-Id`。
    - Kafka 消息生产时将 TraceID 注入消息 Header，消费时提取并创建子 Span。
    - 导出器：OTLP → Jaeger/Tempo，采样策略：生产 10% / 错误 100% / 开发 100%。
- 日志结构化输出（Zap），统一 JSON 格式，关键字段：trace_id、span_id、user_id、level、caller、message、timestamp、duration_ms。
    - 日志级别策略：Info（正常业务流程）/ Warn（可恢复异常）/ Error（需关注错误，如 DB 超时）/ Fatal（不可恢复）。
    - 敏感字段脱敏：password、token、secret 自动替换为 `***`。
    - 日志级别动态调整：支持通过 HTTP 端点 `/debug/loglevel` 或 SIGNAL 信号实时切换。
    - 请求体 > 4KB 自动截断，敏感路径（/login、/register）不记录 request body。
- 系统监控：
    - 内置 /metrics 指标（缓存命中率/熔断器状态/限流令牌数/QPS/延迟分位数/内存分配/Goroutine 数量）。
    - K8s 三探针（liveness/readiness/startup），详细映射：
        - startup：GET /ready，initialDelaySeconds=10，periodSeconds=5，failureThreshold=30。
        - liveness：GET /health，periodSeconds=10。
        - readiness：GET /ready，periodSeconds=5。
    - 健康检查集成 Redis/Kafka/DB 连通性 /health 端点，返回各组件状态与延迟。
    - 告警规则（Prometheus AlertManager）：
        - P99 延迟 > 1s（持续 5 分钟）。
        - 错误率 > 1%（持续 5 分钟）。
        - 缓存命中率 < 80%（持续 10 分钟）。
        - 熔断器状态 = OPEN（即时告警）。
        - Pod 数量 < 2（即时告警）。
        - Kafka 消费 lag > 10,000（持续 10 分钟）。

## 四、流量治理与韧性体系
- 限流：令牌桶限流（5000 TPS 默认，Burst = 1000），支持按接口/按用户维度配置。
    - 限流响应：返回 429 + Header `Retry-After: <秒>`。
    - 限流指标同步写入 Prometheus Counter。
    - 响应 Header 透出：`X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`。
- 熔断：三态熔断器（CLOSED → OPEN → HALF_OPEN），失败率 ≥ 50% 自动 OPEN，OPEN 持续 30s → HALF_OPEN 放量 10 个探测请求，全部成功 → CLOSED。
    - 按路由分组独立熔断，互不影响。
    - OPEN 时返回 503 + 错误码，状态变更写入日志 + Prometheus Gauge。
- 降级：熔断器触发时强制全量降级为异步，各组件独立降级互不影响。
    - 读降级：跳过 L2 直读 DB。
    - 写降级：同步转异步 Kafka。

> 限流 / 熔断 / 账号锁定的具体机制、参数与运行时热更新，以 [405_安全与防护.md §四](./405_安全与防护.md#四限流与熔断)（安全专题单一来源）为准。
- 削峰填谷：Kafka 批量消费，消费者 8 协程并发 + 指数退避重试 + 死信队列（DLQ），失败消息补偿本地日志。
    - 批量拉取：MaxPollRecords=100，批量攒批 100 条或 1s 触发。
    - 提交策略：处理后手动提交 offset（at-least-once 语义）。
- 消费者支持批量处理消息，批量操作数据库和缓存（Pipeline），减少 IO 次数。
- Redis 分布式锁防并发冲突，热点回源自动加分布式锁（Redis SETNX EX 10s），锁释放使用 Lua 脚本保证原子性。
- 消息幂等性：消费者根据 `{event_type}:{biz_id}:{version}` 去重（Redis SETNX），防止重复消费。

## 五、缓存策略
- 缓存库支持：Redis / Valkey（兼容协议，Valkey 为 Redis 开源继任者）。
- L1 本地缓存（Ristretto）：最大内存 256MB（可配置），LFU + Window-TinyLFU 回收策略，默认 TTL 5 分钟。
    - 指标暴露：l1_hit_total、l1_miss_total、l1_size_bytes、l1_evictions_total。
    - 容量告警：HitRatio < 80% 时 warn 日志。
- L2 分布式缓存（Redis/Valkey）：连接池 min=10、max=100，支持 Sentinel/Cluster 模式。
    - Pipeline 批量读写：一次 Pipeline ≤ 100 条命令。
    - 指标暴露：l2_hit_total、l2_miss_total、l2_latency_histogram。
- 热点 Key 自动检测（滑动窗口算法，窗口 10s），自动提升到高频队列。
    - 热点 Key 提升 TTL（×3）、启用本地预取，阈值 Top N 可配置（默认 100）。
- L2 变更广播（Redis Pub/Sub Channel: `cache:invalidate:{namespace}`）使各 Pod 同步清理本地 L1 缓存。
- 数据一致性保障：
    - 写入后延迟双删策略：立即删 L1+L2 + 500ms 二次删 L1。
    - 缓存 TTL 带 ±20% 随机偏移，避免缓存雪崩。
- 缓存键命名规范：`{domain}:{entity}:{id}`，如 `user:profile:{user_id}`。
- 序列化：通过 Serializer 接口支持 JSON（通用）/ Protobuf（高频）可切换。
- TTL 策略：
    - 用户资料：30 分钟 / 商品列表：5 分钟 / 任务配置：1 小时 / 积分余额：1 分钟（写频繁）。
    - 热点数据：自动提升 ×3。
    - 空值标记（`__NULL__`）：TTL 60s。

## 六、数据库设计
- 数据库支持：MySQL / PostgreSQL / SQLite / MongoDB / Elasticsearch / ClickHouse。
- 读写分离：主库写入、从库读取，基于 GORM dbresolver 自动路由，事务内所有操作绑定主库。
    - 从库健康检查：3s 间隔 Ping，不健康自动摘除。
- 分库分表策略：不同类型数据保存到不同数据库。
- 多数据库智能路由：
    - 用户数据（用户ID/用户名/邮箱/密码/第三方授权信息/登录记录）=> MongoDB / SQLite。
    - 业务数据（积分余额/兑换订单/挂机记录/任务记录）=> MySQL / PostgreSQL / SQLite。
    - 日志数据（注册/登录/挂机/订单/操作审计）=> Elasticsearch / SQLite。
    - 监控分析数据（QPS/延迟/缓存命中率时序）=> ClickHouse / SQLite。
- ORM 层统一抽象（GORM v2），通过配置切换底层数据库驱动，业务代码无感知。
- 连接池配置：MaxIdleConns=25、MaxOpenConns=200（生产建议 200~400，代码默认 120，详见 [202_配置参考.md](./202_配置参考.md)）、ConnMaxLifetime=1h；MongoDB MinPoolSize=10、MaxPoolSize=100。
- 故障切换：主库不可用时自动 fallback 到备选库（如 SQLite），切换事件告警。
- 关键数据双写（如用户表）：可配置主备同时写入（异步 Kafka 投递）。
- 数据迁移：golang-migrate，按 `migrations/{driver}/` 分目录管理，命名 `{timestamp}_{description}.up.sql` / `.down.sql`，CI 部署前自动执行。
- 事务管理：Service 层通过 `Transaction` 函数统一管理，自动传递上下文 Tx，支持嵌套事务（SavePoint）。

## 七、消息中间件
- 支持：Kafka / RabbitMQ / RocketMQ，通过适配器模式统一接口（Producer/Consumer）。
    - 通过配置切换：`mq.type: kafka`。
- Kafka 可靠消息：
    - 生产者：acks=all + 幂等（enable.idempotence=true） + LZ4 压缩 + 分区键路由。
        - 发送超时 5s、最大重试 3 次、buffer.memory=64MB、batch.size=16KB。
    - 消费者：8 协程并发（Worker Pool）+ 指数退避重试（1s→2s→4s→8s→16s，最多 5 次）+ 死信队列（DLQ Topic: `{原topic}.dlq`）。
        - DLQ 消息同时持久化到本地 JSON 文件备用补偿。
        - 批量拉取 MaxPollRecords=100，批量攒批 100 条或 1s 触发。
        - 提交策略：处理成功后手动提交 offset（at-least-once 语义）。
    - 消息顺序性：同一用户/同一业务 Key 路由到同一分区。
    - 消息幂等性：消费者根据 `{event_type}:{biz_id}:{version}` 做 Redis SETNX 去重。
- 消息体统一包含 trace_id、timestamp、event_type、key、payload、headers。
- 消息体序列化：Protobuf（生产推荐）/ JSON（开发调试），通过 Serializer 切换。
- 事件定义清单：
    | 事件类型 | Topic | 生产者 | 主要消费者 |
    |---------|-------|--------|-----------|
    | user.registered | user-events | Auth Service | 任务系统（每日登录）、审计日志 |
    | user.logged_in | user-events | Auth Service | 审计日志 |
    | idle.settled | idle-events | Idle Service | 任务进度更新、积分流水 |
    | task.completed | task-events | Task Service | 审计日志、积分流水 |
    | shop.redeemed | shop-events | Shop Service | 任务进度更新、积分流水 |

## 八、用户认证与安全
- 用户认证：JWT Bearer Token（RS256 生产 / HS256 开发），bcrypt 密码哈希（cost factor = 12）。
    - Access Token 有效期 2h，Refresh Token 有效期 7d。
    - Refresh Token 轮转：每次 Refresh 返回新 Access Token + 新 Refresh Token，旧 Refresh Token 立即失效。
    - Token 黑名单：登出/修改密码后 jti 存入 Redis SET `jwt:blacklist:{jti}`，TTL = Token 剩余有效期。
- 公开接口：注册、登录、Google OAuth 回调、Token 刷新。
- 其余业务接口统一 JWT 中间件鉴权，解析 user_id 到 context。
- 登录注册方式：
    - Google OAuth2.0 授权登录（scopes: openid email profile，state 防 CSRF 存入 Redis TTL 5min）。
        - 账号匹配：按 google_id → email → 创建新账号。
    - 邮箱 + 密码注册/登录，邮箱不存在则自动创建账号。
    - 密码强度校验（至少 8 位，大小写字母+数字+特殊字符至少 3 类）。
    - 密码修改后强制所有 Token 失效（Redis 记录 password_changed_at 时间戳）。
- 防水墙（CAPTCHA）技术：
    - 支持 tencent / Turnstile / reCAPTCHA / hCAPTCHA 可插拔切换。
    - 接口抽象：`type CaptchaProvider interface { Verify(token, remoteIP string) (bool, error); GetScriptSrc() string }`。
    - 触发策略（滑动窗口计数，Redis 存储）：
        - 单邮箱 1 分钟内请求 ≥ 5 次。
        - 单 IP 1 分钟内请求 ≥ 10 次。
        - 失败次数递增等待（第 3 次失败等待 5s，第 5 次等待 30s，第 10 次锁定 30min）。
    - 验证码通过后设置 5 分钟白名单免验证。
- 安全限制：
    - IP 级别：单 IP 每分钟注册上限 3 次、登录上限 10 次（Redis 滑动窗口）。
    - 账号级别：单账号连续失败 5 次锁定 15 分钟（Redis Key `login:fail:{user_id}`）。
    - 请求频率：全局限流 + 用户级别限流双重保障。
- CSRF 防护：SameSite=Strict Cookie + 自定义 Header 检查。
- CSP 头：`Content-Security-Policy: default-src 'self'`。

> 认证链路（JWT 令牌时效 / 黑名单 / Refresh 轮转）、防水墙、账号锁定、IP 限流等机制的完整规范与运维细节，见 [405_安全与防护.md](./405_安全与防护.md)（安全专题单一来源）。

## 九、接口设计

> 接口**权威契约与完整端点清单见 [201_API参考.md](./201_API参考.md)（权威，路由以 `internal/handler/`、`internal/router/` 为准）**；**全部端点以 [201_API参考.md](201_API参考.md) 为准**，本章仅列需求要点，端点与需求要点另见 [002_需求规格说明书.md](./002_需求规格说明书.md)。

### 9.1 通用约定
- Base URL：`/api/v1`
- 鉴权方式：`Authorization: Bearer <access_token>`（公开接口除外）
- Content-Type：`application/json`
- 统一响应格式：
```json
{
    "code": 0,
    "message": "success",
    "data": {},
    "trace_id": "abc123-def456"
}
```
- 分页格式：cursor 分页，请求参数 `cursor` + `limit`，响应返回 `next_cursor`。

### 9.2 挂机系统
- 挂机接口：
    - POST /api/v1/idle/start —— 开始挂机，记录设备标识与上线时间。
        - 流程：校验用户无活跃会话 → 创建挂机会话（Redis SET idle:active:{user_id}）→ 创建 DB 记录。
        - 旧设备互踢：检测已有活跃会话 → 终止并结算旧会话 → 创建新会话 → 旧设备心跳返回 10403。
    - POST /api/v1/idle/heartbeat —— 心跳上报（间隔 30s），维持在线状态，若超时 90s 无心跳则自动离线。
        - 实现：延长 Redis Key TTL（EXPIRE 90s），避免高频写 DB。
    - POST /api/v1/idle/stop —— 停止挂机，根据在线时长结算积分。
        - 结算公式：`积分 = 有效在线分钟数 × 每分钟积分`（每分钟积分可配置）。
        - 结算幂等性：同一段挂机时长不可重复结算。
    - POST /api/v1/idle/stop-device —— 仅停止指定 `device_id` 的挂机，其余设备继续挂机（多设备场景）。
    - GET /api/v1/idle/status —— 查询当前挂机状态与累计时长。
    - GET /api/v1/idle/records —— 查询挂机历史记录（支持时间范围过滤 + cursor 分页）。
- 在线挂机系统规则：
    - 根据设备在线时长奖励积分（每分钟 +N 积分，N 可配置）。
    - 同一用户仅允许一个设备在线挂机，新设备上线自动踢下线旧设备。
    - 挂机积分每日上限可配置（默认每日上限 1440 分钟），超出部分不计入但不中断挂机。
- 离线检测（定时任务）：扫描 Redis Keys `idle:active:*` → TTL 过期的 Key 触发自动结算。

### 9.3 任务系统
- 任务奖励系统：
    - GET /api/v1/tasks —— 获取任务列表（每日任务/周任务/成就任务，合并用户进度）。
    - POST /api/v1/tasks/:id/claim —— 领取任务奖励。
        - 校验：任务已完成 AND 未领取 → 幂等保障（已领取不可再领）。
    - GET /api/v1/tasks/progress —— 查询任务进度。
- 任务类型：
    - 每日任务：每日登录、挂机满 X 分钟、完成 N 次兑换等，每日 0 点重置。
    - 周任务：累计挂机、累计兑换等，每周一 0 点重置。
    - 成就任务：一次性任务，达成条件永久完成（如累计积分达 N），永不重置。
- 进度追踪：
    - 事件驱动：通过 Kafka 消息异步更新进度（解耦核心接口性能）。
    - 查询进度优先查缓存（L1 → L2 → DB）。
- 周期重置（定时任务）：每日 00:00 UTC 清空 daily 进度、每周一 00:00 UTC 清空 weekly 进度。

### 9.4 积分兑换系统
- GET /api/v1/shop/items —— 商品列表（支持分页 `cursor` + `limit`、分类筛选 `category`）。
- POST /api/v1/shop/redeem —— 积分兑换商品。
- GET /api/v1/shop/orders —— 兑换订单记录（支持时间范围过滤 + cursor 分页）。
- GET /api/v1/shop/orders/:id —— 订单详情（含商品快照信息）。
- 兑换规则：
    - 扣减积分前校验余额充足（优先查 Redis，fallback DB）。
    - 兑换流程：校验登录态 → 校验商品存在且上架 → 加 Redis 分布式锁 `redeem:lock:{user_id}`（EX 5s）→ 开启 DB 事务 → 扣减积分 → 乐观锁扣减库存（WHERE version=?）→ 创建订单 → 提交事务 → 释放锁 → 删缓存 → 发送 Kafka `shop.redeemed` 事件。
    - 乐观锁更新失败 → 回滚事务 → 返回 10302 库存不足。
    - 库存不足时拒绝兑换，杜绝超卖。

### 9.5 用户接口
- POST /api/v1/auth/register —— 注册（邮箱 + 密码 + 验证码），注册成功自动签发 JWT。
- POST /api/v1/auth/login —— 登录（邮箱 + 密码），记录 IP/设备/时间用于审计。
- POST /api/v1/auth/google —— Google OAuth 授权回调，完成登录/注册。
- POST /api/v1/auth/refresh —— 刷新 Token，返回新 Access + Refresh Token，旧 Token 立即失效。
- GET /api/v1/user/profile —— 获取用户信息。
- PUT /api/v1/user/profile —— 更新用户信息。
- PUT /api/v1/user/password —— 修改密码（需鉴权，客户端提交 SHA256 哈希后的密码，见 [201_API参考.md](./201_API参考.md) §2.5）。
- GET /api/v1/user/points —— 查询积分余额与流水（支持 cursor 分页）。

### 9.6 系统接口（公开/内网）
- GET /health —— 各依赖组件连通性检查（Redis PING、DB PING、Kafka ListOffsets），返回各组件状态与延迟（K8s liveness 探针）。
- GET /ready —— 服务就绪探针（所有依赖 + 自身 warm-up 完成，K8s readiness/startup 探针）。
- GET /metrics —— Prometheus 指标端点。
- GET /metrics/cache —— 缓存统计 JSON 视图（兼容）。
- PUT /debug/loglevel —— 动态日志级别调整（内网）。
- POST /debug/reload —— 配置热更新重载（内网）。
> 调试/内网接口（`/debug/*`）不应暴露到公网；完整系统接口见 [201_API参考.md §七](./201_API参考.md#七系统接口)。

    - auth：JWT 算法（RS256/HS256）、签名密钥/公钥路径、Access Token TTL、Refresh Token TTL、密码哈希 cost
    - ratelimit：全局令牌桶速率 + Burst、IP/用户维度速率、限流白名单
    - circuit_breaker：失败率阈值、OPEN 持续时间（秒）、HALF_OPEN 探测请求数
    - captcha：验证码类型（tencent/turnstile/recaptcha/hcaptcha）、SiteKey、SecretKey、阈值策略
    - oauth：Google ClientID、ClientSecret、RedirectURL、Scopes
    - logging：日志级别、输出格式（json/console）、输出目标
    - task：每日重置时间（UTC 时）、每周重置星期
    - idle：心跳间隔、超时阈值、每分钟积分、每日积分上限

## 十四、部署与运维

> 完整部署与运维（构建/K8s/压测/备份/容灾）见 [002_需求规格说明书.md](./002_需求规格说明书.md)；百万设备级部署另见 [401_集群设备部署手册.md](./401_集群设备部署手册.md)。本章为需求基线要点。

- 构建：
    - 多阶段 Docker 构建（golang:1.25-alpine → alpine:3.20，非 root 用户运行）。
    - 编译参数：`CGO_ENABLED=0 go build -ldflags="-s -w"`，精简二进制体积。
- 容器化部署：Docker + K8s。
    - Deployment replicas ≥ 3，resources.requests/limits 配置。
    - HPA 水平自动扩缩容：minReplicas=3、maxReplicas=30，基于 CPU > 70% + 内存 > 80% + 自定义 QPS 指标。
    - PDB：maxUnavailable=1 或 minAvailable=2，保障可用性。
    - ConfigMap 管理非敏感配置，Secret 管理 JWT 密钥/DB 密码/API Key。
- 优雅关闭：SIGTERM/SIGINT 信号触发。
    - 关闭顺序（反向依赖）：停止接收新请求（HTTP Server.Shutdown 30s timeout）→ 关闭 Kafka Consumer（停止拉取，等待处理中的完成）→ 关闭 DB 连接池 → 关闭 Redis 连接池 → 关闭 Kafka Producer（flush 缓冲区）→ 退出进程。
    - 每步骤最多等待 5s，总关闭时间 < 30s。
- 滚动更新：K8s RollingUpdate 策略，maxSurge=1，maxUnavailable=0，确保零停机更新。
- 日志收集：Stdout 输出 JSON 日志 → Filebeat/Fluentd 采集 → Kafka → Logstash → Elasticsearch（或 Grafana Loki）。
- 监控面板：Grafana Dashboard 展示 Go Runtime、HTTP QPS/Latency、Cache Stats、DB Stats、MQ Stats。
- 压力测试：
    - 工具：k6 脚本化测试。
    - 场景 1 — 注册/登录：500 VU，持续 5 分钟，rate=100/s。
    - 场景 2 — 挂机心跳：10,000 VU，每 30s 发心跳，持续 10 分钟。
    - 场景 3 — 商品兑换抢购：1,000 VU 同时兑换，库存 500，验证无超卖。
    - 场景 4 — 混合负载：70% 读 + 30% 写，2,000 VU，持续 30 分钟。
    - 验收指标：P99 < 200ms（读）/ P99 < 500ms（写），error rate < 0.1%，缓存命中率 ≥ 95%，兑换无超卖。
- 数据备份：
    - DB 每日全量备份 + binlog 增量备份，保留 30 天。
    - Redis RDB 快照每小时一次 + AOF 持久化。
- 容灾：
    - Redis Sentinel/Cluster 主从自动切换。
    - DB 主从切换，从库故障自动剔除。
    - Kafka 集群 ≥ 3 Broker，replication factor = 3，min.insync.replicas = 2。
