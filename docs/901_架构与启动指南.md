# 901 · 架构与启动指南（go-zero 版）

> 适用分支：`feature/go-zero-migration`
> 本文档描述**真实实现**，与代码严格一致。gin 版（多微服务 + Redis）的演进背景见 [900_go-zero迁移说明.md](900_go-zero迁移说明.md)。

---

## 1. 总体架构

go-zero 版将 gin 单体重构成 **「rest 网关 + 单一领域后端」**。原 gin 版的 5 个微服务（user / idle / task / shop / 结算）被合并为 **一个 hc 后端**（合并 user/idle/task/shop 四域），域间调用为**进程内函数调用**。

**合并部署（当前推荐）**：gateway 与后端编译为**单一进程 `hc-server`**，网关通过进程内 `LocalHcClient` 直接调用后端 logic，不再经由 gRPC 网络，无需 etcd 服务发现。只对外暴露 REST（:8080），Prometheus 指标也统一由该端口的 `/metrics` 暴露。

```
HTTP 请求
   │
   ▼
hc-server (单进程)
   ├─ Gateway(REST, :8080)   ← 鉴权 / 图形验证码 / IP 限频 / 统一响应(code+message+data+trace_id)
   │     └─ 进程内直接调用 ──► 后端 logic（同一进程，无网络）
   ├─ 后端（合并 user/idle/task/shop 四域，原 hc-rpc 的 logic/svc）
   │     ├─ user 域  认证(注册/登录/Google/刷新Token/改密) + 资料 + 积分账户
   │     ├─ idle 域  多设备挂机会话 + 时长结算（进程内入账积分）
   │     ├─ task 域  任务定义/进度/领取（进程内发奖）
   │     └─ shop 域  商品/兑换/订单/定时抢购（进程内扣款）
   └─ Metrics(:8080/metrics)  Prometheus 拉取端点（网关与后端共用）
```

> **历史兼容**：分支早期为「hc-gateway(:8080) + hc-rpc(gRPC :8001)」双进程架构（跨进程 gRPC + etcd）。现已合并为单进程，对外 gRPC 接口已移除，仅保留 REST。独立双进程入口（`app/gateway/api/gateway.go` 与已移除的 `app/rpc/cmd`）不再使用。

### 1.1 关键设计决策

| 维度 | go-zero 版（本分支） | gin 版（历史） |
|------|---------------------|---------------|
| 服务划分 | 单 rpc（四域合并） | 5 个微服务 |
| 服务发现 | etcd（可直连 `direct://`） | etcd / consul |
| 域间协作 | 进程内函数调用 | 跨进程 gRPC |
| 数据层 | gorm（sqlite 起步，可切 mysql/postgres） | gorm + Redis 双写 |
| 会话/在线态 | DB 表 `idle_records`（无 Redis） | Redis 活跃会话集 + 心跳 |
| 结算 | 请求驱动、进程内同步入账 | 事件驱动 + 定时结算 |
| 限流 | 网关 IP 滑动窗口（内存） | 网关 + RPC 多 middleware（leakyBucket 等） |
| 熔断/降级 | go-zero 内置 Breaker（gRPC 客户端） | Resilience4j 显式熔断器 |
| 验证码 | 进程内内存 Provider（可插拔 Redis） | Redis 存储 |
| 邮件/异步 | **未实现**（无 Mail/事件总线） | 异步邮件、事件总线 |
| 可观测 | go-zero 内置 Prometheus + 链路追踪 | 自建 |

> **说明**：本实现刻意保持"零外部中间件依赖"（sqlite + 内存验证码即可跑通），生产可将 `DataSource` 切到 MySQL/PostgreSQL、验证码 Provider 切到 Redis，无需改业务逻辑。

### 1.2 依赖与版本

- Go ≥ 1.22
- `github.com/zeromicro/go-zero` v1.7.x（rest/zrpc/conf/logx）
- `gorm.io/gorm` + `github.com/mattn/go-sqlite3`（默认）；生产可换 `gorm.io/driver/mysql`
- `github.com/google/uuid`、`golang.org/x/oauth2/google`、`github.com/go-resty/resty/v2`（Google OAuth）
- 可选 etcd（`go.etcd.io/etcd/client/v3`）用于服务发现

### 2.1 分层依赖约束（强制）

依赖方向单向向下，**`common/` 不得 import `app/` 下任何包**：

```
app/server  →  app/gateway  →  app/rpc  →  common/
                                             ↑
                                    （禁止反向箭头）
```

违反该约束会导致 `common` 层无法被独立复用，并在补测试时触发 import cycle。

**适配点模式**：当 `common` 层组件需要上层配置时，由 `common` 定义**自有的最小契约**，上层负责转换。以多库客户端为例：

- `common/dbclient` 定义 `DBSpec`/`Specs`（仅含 Driver、DSN、连接池参数）
- `app/rpc/config` 提供 `Databases.ToSpecs()`，在此完成 **DSN 解析**与**连接池优先级**（vendor 段 > 顶层通用字段）
- `dbclient.NewFactory(cfg.Databases.ToSpecs())` 只消费解析后的结果

校验方式：

```bash
for p in $(go list ./common/...); do
  go list -deps "$p" | grep "hc-framework-go/app" && echo "违规: $p"
done
```

## 3. 请求生命周期

以"开始挂机"为例（合并部署，进程内调用）：

1. 客户端 `POST /api/idle/start`（带 `Authorization: Bearer <jwt>`）
2. 网关 `jwt_auth` middleware 校验 JWT，将 `user_id` 写入 `r.Context()`（key `user_id`）
3. `IdleStartHandler` 解析参数 → 调 `logic.IdleStartLogic.IdleStart`
4. 网关 logic 构造 `hc.IdleStartRequest{UserId, DeviceId}` → 通过 `svcCtx.HcRpc.IdleStart(req)` **进程内**调用 `LocalHcClient`（直接转发到后端 `HcServer.IdleStart`，无网络）
5. 后端 `IdleStartLogic` 执行：幂等查重 → 活跃设备数上限检查（`Config.Idle.MaxActiveDevices`）→ 落库 `idle_records`
6. 返回 `hc.IdleRecord` → 网关 logic 转 `types` → `response.Success` 输出 `{code, message, data, trace_id}`

> 网关 logic 与后端 logic 的关系：网关侧负责**协议转换 + 鉴权上下文注入**；后端负责**全部业务规则与数据访问**。后端业务错误通过 `errorx` 编码，网关 `handleError` 还原为统一 JSON。`LocalHcClient`（`app/rpc/server/local.go`）实现 `hc.Hc` 接口，使网关调用代码无需关心"本地 / 远程"。

## 4. 本地启动（合并部署，推荐）

### 4.1 前置依赖

- Go ≥ 1.22
- protoc + protoc-gen-go + protoc-gen-go-grpc（仅首次生成 pb 代码需要）
- 无需 etcd（合并部署已移除跨进程 gRPC 与服务发现）

### 4.2 步骤

```bash
# 1. 生成 rpc 的 pb 代码（protoc + protoc-gen-go + protoc-gen-go-grpc）
make gen

# 2. 收敛依赖（首次克隆必做，生成 go.sum）
go mod tidy

# 3. 编译并启动合并单进程服务 hc-server（REST :8080 + /metrics）
make run-server
# 或一体化脚本（默认即合并模式）
./build.sh build
./build.sh kill      # 关闭运行中的服务
```

### 4.3 配置

合并部署使用单一配置 `config/server.yaml`，包含两个顶层块：

- `Gateway:` —— 网关配置（rest.RestConf + Auth/Captcha/Security）
- `Rpc:` —— 后端配置（DB/Jwt/BcryptCost/GoogleOAuth/Idle/Log/Telemetry）

详见 [902_配置参考.md](902_配置参考.md)。

### 4.4 验证

启动后：

- 网关健康检查：`curl http://localhost:8080/health`
- Prometheus 指标：`http://localhost:8080/metrics`（网关与后端共用同一端点）
- sqlite 数据文件默认落到 `data/hc.db`（首次启动 `svc.Seed` 自动建表 + 种子数据）

### 4.5 优雅关闭

合并进程启动时由 `main.go` 持有 `ServiceContext`，并通过 `defer rpcCtx.Close()` 在进程退出（`SIGTERM`/`SIGINT`）时统一释放资源：

- 停止后台 `idle scan` goroutine（通过 `stop` 通道通知，`WaitGroup` 等待其退出，避免 goroutine 泄漏）
- 关闭 L2 缓存连接（`cache.Manager.Close()` 内部仅关闭非 nil 的 Redis 连接）
- 关闭 MQ Producer / Consumer
- 关闭 `dbclient.Factory` 持有的全部 SQL 连接（`Close()` 会**尽力关闭每一个连接并聚合错误**，而非遇错即停）

> 网关 `gwServer.Stop()` 已由 `defer` 注册；后端资源由 `rpcCtx.Close()` 覆盖。两者均在 `main` 退出前执行，保证连接不泄漏。

### 4.6 常见端口

| 服务 | 端口 | 说明 |
|------|------|------|
| hc-server (REST + metrics) | 8080 | HTTP REST 入口 + Prometheus 拉取端点（/metrics） |

> 历史双进程模式的端口（hc-gateway 8080 / hc-rpc gRPC 8001 / gateway metrics 9100 / hc-rpc metrics 9101）已不再适用，对外 gRPC 接口已移除，指标统一收敛到 :8080/metrics。

## 7. 域边界与"合并单 rpc"的影响

合并到单 rpc 后，以下协作均为**进程内调用**（见 `app/rpc/internal/logic/*`）：

- 挂机结算入账：`settle()` 直接调用 `NewAddPointsLogic(...).AddPoints()`
- 任务领取发奖：`ClaimLogic.Claim` 调用 `AddPointsLogic`
- 商城兑换扣款：`RedeemLogic` / `FlashRedeemLogic` 调用 `DeductPointsLogic`
- 任务进度推进：心跳/挂机/商城等事件调用 `bumpProgress()`（更新 `user_task_progress`，进程内完成）

> 因此 **rpc 侧没有跨服务调用、没有事件总线**；若未来需要拆分微服务，只需把这些进程内调用替换为 gRPC client，域接口边界已清晰（`*Logic` + `hc.proto`）。
