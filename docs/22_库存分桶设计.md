# 库存分桶设计（P2-5：根治抢兑写热点）

> 适用模块：普通兑换 `Redeem` 的库存扣减写路径。
> 关键词：行锁热点、分桶、原子条件扣减、零超卖、幂等回填。

---

## 1. 背景与问题

普通兑换 `Redeem` 原本对 `shop_items` **单行**做原子条件扣减：

```sql
UPDATE shop_items SET stock = stock - ? WHERE id = ? AND stock >= ?;
```

- 抢兑高峰下，所有并发兑换**串行于同一行**，InnoDB 行锁竞争成为吞吐瓶颈，p99 随并发陡增。
- 读路径（`FindItemByID` / `FindItems`）可经三级缓存削峰，但**写路径无法绕过**（必须落库扣减），因此瓶颈集中在写。
- 旧方案使用 `version` 乐观锁，要求扣减前强读主库拿最新 `version`，进一步放大主库读压力（已在前序优化中改为原子条件更新，但仍集中在单行）。

---

## 2. 方案：库存分桶

将**单商品库存拆分到 N 个桶行**，把本来集中在 `shop_items` 单行的行锁竞争**分散到 N 行**。

- 桶表：`shop_item_stock_buckets`，复合主键 `(item_id, bucket)`，`stock` 为单桶库存。
- **桶是库存的权威存储**；`shop_items.stock` 仅作展示 / 兜底（读路径返回桶之和）。
- 扣减时按 `hash(userID) % N` 选**主桶**，主桶不足则**顺序尝试其余桶**（避免桶间倾斜导致“假售罄”），任一桶 `WHERE stock >= ?` 成功即返回。

```
N = 16（2 的幂，便于取模；在分散度与桶元数据量之间取平衡）
```

```
              shop_items (单行, 仅展示)
                   │  stock 由桶之和派生
                   ▼
   ┌──────┬──────┬──────┬───── ... ─────┬────────┐
   │bucket0│bucket1│bucket2│              │bucket15 │   shop_item_stock_buckets (权威)
   └──────┴──────┴──────┴───── ... ─────┴────────┘
       ▲用户A    ▲用户B    ▲用户C   不同用户分散到不同桶 → 行锁并行
```

---

## 3. 关键设计点

### 3.1 分片键 = userID
- 同一用户稳定命中同一桶（`fnv32a(userID) % N`），不同用户尽量分散到不同桶。
- 最大化降低行锁竞争：热点由“单行”降为“单桶”，N 个桶可并行扣减。

### 3.2 零超卖
- 仍由 InnoDB 行锁 + 原子条件更新保证：`WHERE stock >= ?` 在桶行上加行锁，`RowsAffected == 0` 即桶耗尽 → `ErrStockInsufficient`。
- 顺序重试其余桶后仍全失败，才判售罄（避免桶间倾斜的“假售罄”）。
- 测试已覆盖顺序扣减与高并发扣减，均零超卖。

### 3.3 桶间倾斜处理
- 主桶不足时按 `(primary + attempt) % N` 顺序尝试其余桶，任一成功即返回。
- 即使某桶先空、其他桶仍有货，也不会误报售罄。

### 3.4 无桶回退（兼容）
- 直建商品 / 尚未回填的商品：**无桶行** → `DeductStock` 自动回退到 `shop_items` 单行原子扣减（旧语义，`item.Stock` 仍准确）。
- 保证分桶改造对未建桶数据完全兼容，无迁移风险。

---

## 4. 数据模型

```sql
CREATE TABLE shop_item_stock_buckets (
    item_id BIGINT NOT NULL,
    bucket  INT   NOT NULL,
    stock   INT   NOT NULL DEFAULT 0,
    PRIMARY KEY (item_id, bucket)
);
```

- **均分策略**：`total` 均分到 16 桶，余数前置到前若干桶（`makeBuckets`），使桶之和恰等于 `total`。
- **幂等建桶**：`CreateStockBuckets` 使用 `ON CONFLICT DO NOTHING`，已存在桶行跳过、**不覆盖已扣减状态**（仅用于种子初始化）。

---

## 5. 读写路径

| 路径 | 行为 |
|------|------|
| 读 `FindItemByID` / `FindItems` | 单次 `IN` + 分组 `SUM(stock)` 回填 `Stock` 为桶之和，再派生 `SalesStatus`；开销可控（仅触碰当前商品桶）。 |
| 写 `DeductStock(ctx, id, qty, shardKey)` | 存在桶行走分桶扣减；否则回退单行。 |
| 种子 `SeedItems` | 新种子商品同步 `CreateStockBuckets`。 |
| 存量回填 `BackfillStockBuckets` | 启动期一次性为 `stock>0 且无桶` 的商品补齐分桶（幂等），使存量库也享受分桶收益。 |

`shop_items.stock` 在分桶路径下**不再随每次扣减实时更新**（避免再触碰热点列），仅作兜底与展示源；展示库存以桶之和为准。

---

## 6. 适用边界（重要）

- 分桶**仅作用于普通兑换 `Redeem`** 的库存扣减写热点。
- **限时抢购 `FlashRedeem` 走另一套配额机制**：Redis 预扣削峰 + `shop_flash_activities.sold_qty` 条件更新（`AcquireFlashQuota`），**不经过桶表**。其写热点（活动单行 `sold_qty`）不在 P2-5 范围，如需治理可另立专项（如活动配额分桶）。

## 8. 运维与限制

- **桶数固定 16**（2 的幂）。调整 N 需对存量数据重分桶，未做自动迁移。
- **库存调整的权威源是桶**：若需对某商品缩小 / 调整库存，直接改 `shop_items.stock` **不会同步到桶**（桶是权威）。应通过 `BackfillStockBuckets` 重算，使桶之和覆盖为当前真实可用库存。
- **监控建议**：分桶后行锁等待（`innodb_row_lock_current_waits` / `innodb_row_lock_time_avg`）应有明显下降；可对比改造前后抢兑 p99 与 DB 行锁指标。
