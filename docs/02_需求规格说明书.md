## 一、引言

### 1.1 项目定位

构建面向 C 端用户的**通用高并发后台框架**，承载用户注册登录、在线挂机、任务奖励、积分兑换等核心业务场景。框架需具备**通用性**——通过配置适配不同业务场景，核心能力（缓存、流量治理、可观测性）与业务逻辑解耦。

### 1.2 业务规模

| 指标 | 目标值 |
|------|--------|
| 总用户量 | 亿级 |
| 在线用户数 | 千万级（即时在线 + 挂机在线） |
| 核心写接口峰值 | ≥ 5,000 TPS |
| 全年可用性 | ≥ 99.99%（年停机 < 53 分钟） |

### 1.3 核心目标

- 高并发场景下保证**数据一致性、服务稳定性、请求低延迟**
- 缓存命中率 ≥ 95%，数据库层作为最终兜底
- **故障隔离**：任何单一组件故障不影响整体服务可用性（降级运行）

### 1.4 术语定义

| 术语 | 说明 |
|------|------|
| L1 缓存 | Ristretto 本地内存缓存，延迟 < 1ms |
| L2 缓存 | Redis/Valkey 分布式缓存，延迟 1-5ms |
| L3 存储 | MySQL/PostgreSQL/MongoDB 持久化存储 |
| TPS | Transactions Per Second，每秒事务数 |
| P99 | 99 分位延迟，即 99% 请求的响应时间上限 |
| DLQ | Dead Letter Queue，死信队列 |
| HPA | Horizontal Pod Autoscaler，水平自动扩缩容 |
| PDB | Pod Disruption Budget，Pod 中断预算 |

## 二、总体描述

### 2.1 产品视角

本框架是一个**后台服务基础设施**，提供以下核心能力：

- **用户体系**：注册、登录（邮箱 + Google OAuth）、Token 管理
- **在线挂机**：心跳维持、时长结算、多设备互踢
- **任务系统**：每日/每周/成就任务，进度追踪，奖励发放
- **积分商城**：商品浏览、积分兑换、订单管理
- **平台能力**：限流、熔断、降级、三级缓存、链路追踪、健康监控

### 2.2 核心性能指标

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| 读 P99（L1 命中） | < 50ms | Prometheus Histogram |
| 读 P99（L2 命中） | < 100ms | Prometheus Histogram |
| 读 P99（回源 DB） | < 500ms | Prometheus Histogram |
| 写 P99（不含异步） | < 200ms | Prometheus Histogram |
| 缓存命中率 | ≥ 95% | L1+L2 合并计算 |
| Kafka 消息端到端延迟 | P99 < 5s | Span 差值 |

### 2.3 用户角色

| 角色 | 说明 |
|------|------|
| 普通用户 | 注册登录、挂机、做任务、兑换商品 |
| 系统管理员 | 配置管理、商品上下架、数据运维 |
| 运维人员 | 监控告警、扩缩容、故障处理 |

### 2.4 约束与假设

- **运行环境**：Kubernetes 集群，Linux amd64 容器
- **语言版本**：Go ≥ 1.25
- **网络假设**：内网延迟 < 5ms（服务 ↔ Redis/DB），公网使用 HTTPS/TLS 1.3
- **数据假设**：读多写少（读写比约 7:3），热点数据集中在 Top 100 Key
- **兼容性**：框架适配多种数据库和消息队列，通过配置切换

## 三、功能性需求

### 3.1 用户认证模块

#### 3.1.1 用户故事

| 编号 | 描述 | 优先级 |
|------|------|--------|
| US-001 | 作为新用户，我可以通过邮箱 + 密码注册，注册成功自动登录 | P0 |
| US-002 | 作为用户，我可以通过邮箱 + 密码登录，获取 JWT Token | P0 |
| US-003 | 作为用户，我可以使用 Google OAuth 一键授权登录/注册 | P1 |
| US-004 | 作为用户，Token 过期后可通过 Refresh Token 无感续期 | P0 |
| US-005 | 作为系统，需防止机器人批量注册/撞库，异常流量触发 CAPTCHA | P0 |

#### 3.1.2 注册

- **输入**：邮箱、密码、验证码（触发 CAPTCHA 时）
- **密码强度**：≥ 8 位，大小写字母 + 数字 + 特殊字符至少 3 类
- **密码存储**：bcrypt 哈希，cost factor = 12
- **流程**：校验参数 → 检查邮箱唯一性 → 哈希密码 → 创建用户 → 签发 JWT → **异步发送注册确认邮件** → 返回
- **并发控制**：邮箱唯一索引保证
- **注册确认邮件**：用户注册成功（含 Google OAuth 新账号）后，系统**异步**向其邮箱发送一封确认邮件（见 §3.1.4）。邮件发送为 best-effort：失败仅记录告警日志，不影响注册结果与 JWT 签发（需求 §3.1.4、代码 `internal/service/auth/auth_service.go`、`pkg/mail`）。

#### 3.1.3 登录

- **邮箱登录**：校验密码 + 账号状态（仅 active 可登录）
- **Google OAuth**：授权码换 Token → 获取用户信息 → 按 google_id → email → 创建新账号的顺序匹配 → 签发 JWT
- **OAuth State 参数**：随机值存入 Redis TTL 5min，回调时校验防 CSRF
- **登录审计**：记录 IP、设备信息、登录结果到登录记录表（Elasticsearch）
- **失败处理**：错误信息不区分"用户不存在"和"密码错误"，统一返回"邮箱或密码错误"

#### 3.1.4 注册确认邮件

用户注册成功后，系统向其邮箱发送一封确认邮件，用于告知账号已创建成功（非强制激活/验证链接，仅通知性质）。

- **触发点**：
  - 邮箱密码注册成功（`AuthService.Register`）；
  - Google OAuth 首次授权创建新账号（`AuthService.GoogleOAuthLogin`）。
- **实现要点**：
  - **抽象接口**：`pkg/mail.Sender`（`Send(ctx, to, subject, bodyHTML)`），便于测试 mock 与生产替换（SMTP / 第三方 API）。内置 `SMTPSender` 基于标准库 `net/smtp`，**无第三方依赖**，支持隐式 TLS（465）与 STARTTLS（587）。
  - **发送方式**：`go` 异步 goroutine 发送，使用独立 `context.Background()`（不随请求取消而中断）；邮件 SMTP 抖动**不阻塞注册响应**、**不回滚已创建账号**。
  - **失败处理**：邮件渲染或 SMTP 失败仅 `log.Printf` 告警，不向上抛错；`mailer==nil`（即 `mail.enabled=false`）时直接跳过。
  - **模板**：`pkg/mail/template.go` 提供 HTML 模板（站点名、用户名、邮箱、注册时间）。
- **配置**（`config.yaml` 的 `mail` 段，`mail.enabled` 默认 `false`）：

| 配置项 | 说明 |
|------|------|
| `mail.enabled` | 总开关，默认 `false`（未配置不发信） |
| `mail.site_name` | 邮件展示的站点名 |
| `mail.smtp.host/port` | SMTP 服务器地址与端口（465 隐式 TLS / 587 STARTTLS） |
| `mail.smtp.username/password` | 认证凭据（为空表示匿名） |
| `mail.smtp.from/from_name` | 发件人地址与显示名 |
| `mail.smtp.use_tls` | 是否隐式 TLS |
| `mail.smtp.insecure_skip_verify` | 跳过 TLS 证书校验（仅测试/内网自签） |

- **装配**：`cmd/server/main.go` 在 `mail.enabled=true` 时构造 `mail.SMTPSender` 并注入 `NewAuthService(... mailer)`；生产启用外部依赖见 [07_集群设备部署手册.md](./07_集群设备部署手册.md) §5「外部依赖网关（邮件）」。

#### 3.1.5 Token 管理

| 机制 | 实现 |
|------|------|
| Access Token | JWT (RS256 生产 / HS256 开发)，有效期 2h |
| Refresh Token | JWT，有效期 7d |
| Refresh 轮转 | 每次 Refresh 返回新 Access + 新 Refresh，旧 Refresh 立即失效 |
| Token 黑名单 | 登出/改密码后 jti 存入 Redis `jwt:blacklist:{jti}`，TTL = Token 剩余有效期 |
| 密码变更 | Redis 记录 `password_changed_at`，签发时间早于此的 Token 全部失效 |

> 认证机制（JWT 时效 / 黑名单 / Refresh 轮转 / 改密失效）的运维细节见 [11_安全与防护.md §一](./11_安全与防护.md#一认证与授权jwt)（安全专题单一来源）。

### 3.2 防水墙（CAPTCHA）模块

#### 3.2.1 可插拔架构

```go
type CaptchaProvider interface {
    Verify(token, remoteIP string) (bool, error)
    GetScriptSrc() string
}
```

支持：腾讯验证码 / Turnstile / reCAPTCHA / hCAPTCHA，通过配置切换。

#### 3.2.2 触发策略（滑动窗口计数，Redis 存储）

| 条件 | 阈值 |
|------|------|
| 单邮箱 1 分钟内注册/登录请求 | ≥ 5 次 |
| 单 IP 1 分钟内注册/登录请求 | ≥ 10 次 |

#### 3.2.3 安全防护层级

| 层级 | 策略 | 实现 |
|------|------|------|
| L1 - IP 限流 | 单 IP 每分钟注册 ≤ 3 次，登录 ≤ 10 次 | Redis 滑动窗口 |
| L2 - 账号锁定 | 连续失败 5 次，锁定 15 分钟 | Redis `login:fail:{user_id}` |
| L3 - 递增等待 | 第 3 次失败等 5s，第 5 次等 30s，第 10 次锁 30min | 服务端延迟返回 |
| L4 - 白名单 | 验证码通过后 5 分钟内免验证 | Redis SET TTL 5min |

> 防水墙（CAPTCHA）与账号防护（IP 限流 / 账号锁定 / 失败递增等待）的完整机制见 [11_安全与防护.md §二、§三](./11_安全与防护.md#二人机验证防水墙captcha)（安全专题单一来源）。

### 3.3 在线挂机模块

#### 3.3.1 用户故事

| 编号 | 描述 | 优先级 |
|------|------|--------|
| US-006 | 作为用户，我可以开启挂机，系统按在线时长累计积分 | P0 |
| US-007 | 作为用户，挂机期间需每 30s 发心跳，超时 90s 自动离线结算 | P0 |
| US-008 | 作为用户，多设备登录时新设备上线自动终止旧设备挂机 | P1 |
| US-009 | 作为用户，可查看当前挂机状态和历史记录 | P1 |
| US-010 | 作为系统，挂机积分有每日上限，超出不计入但不中断挂机 | P1 |

#### 3.3.2 挂机生命周期

```
未挂机 ──[POST /idle/start]──> 挂机中
挂机中 ──[POST /idle/heartbeat/30s]──> 挂机中（续期）
挂机中 ──[POST /idle/stop]──> 已结算
挂机中 ──[90s 无心跳]──> 超时离线（自动结算）
```

#### 3.3.3 结算规则

- **公式**：`积分 = 有效在线分钟数 × 每分钟积分（可配置）`
- **每日上限**：默认 1440 分钟，可配置
- **幂等性**：同一段挂机时长不可重复结算
- **实现**：start/stop 操作 DB，heartbeat 仅操作 Redis（EXPIRE 90s），高频低开销

#### 3.3.4 多设备互踢

1. 新设备发起 `start` → 检测已有活跃会话（Redis `idle:active:{user_id}`）
2. 存在旧会话 → 终止并结算旧会话 → 创建新会话
3. 旧设备下次心跳返回错误码 **10403（已被踢下线）**，引导客户端停止

#### 3.3.5 离线检测

- 定时任务（Cron `*/30 * * * *`）：扫描 Redis Keys `idle:active:*`
- TTL 已过期的 Key → 触发自动结算 → 生成挂机记录 → 发送 Kafka `idle.settled` 事件

### 3.4 任务系统模块

#### 3.4.1 用户故事

| 编号 | 描述 | 优先级 |
|------|------|--------|
| US-011 | 作为用户，可查看每日/周/成就任务列表及进度 | P0 |
| US-012 | 作为用户，完成任务后可领取积分奖励 | P0 |
| US-013 | 作为系统，每日任务每天 0 点重置，周任务每周一 0 点重置 | P1 |
| US-014 | 作为系统，成就任务一次性完成，永久标记，不可重复领取 | P1 |

#### 3.4.2 任务类型

| 类型 | 重置周期 | 示例 |
|------|---------|------|
| 每日任务 | 每日 00:00 UTC | 每日登录、挂机满 30min、完成 1 次兑换 |
| 周任务 | 每周一 00:00 UTC | 累计挂机 300min、累计兑换 3 次 |
| 成就任务 | 永不重置 | 累计积分达 10,000、完成 100 次兑换 |

#### 3.4.3 进度追踪

- **事件驱动**：通过 Kafka 消息异步更新进度，解耦核心接口性能
- **进度查询**：优先查缓存（L1 → L2 → DB）
- **周期重置**：定时任务，每日/每周 00:00 UTC 清空对应周期进度

#### 3.4.4 领取奖励

- **校验**：任务已完成 AND 未领取 → 通过
- **发放**：积分入账 + 标记已领取 + 写积分流水，在同一事务中完成
- **幂等保障**：已领取任务不可再次领取

### 3.5 积分商城模块

#### 3.5.1 用户故事

| 编号 | 描述 | 优先级 |
|------|------|--------|
| US-015 | 作为用户，可浏览商品列表，按分类筛选 | P0 |
| US-016 | 作为用户，可用积分兑换商品，系统实时扣减积分并生成订单 | P0 |
| US-017 | 作为用户，可查看历史兑换订单 | P1 |
| US-018 | 作为系统，兑换需校验积分余额和库存，禁止超卖/透支 | P0 |

#### 3.5.2 兑换流程（完整时序）

```
1. 校验登录态（JWT 中间件）
2. 校验商品存在且上架
3. 校验积分余额（优先 Redis，fallback DB）
4. 加 Redis 分布式锁 redeem:lock:{user_id}，EX 5s
5. 开启 DB 事务
6. 扣减用户积分（UPDATE users SET points_balance = points_balance - ? WHERE user_id = ? AND points_balance >= ?）
7. 乐观锁扣减库存（UPDATE shop_items SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ? AND stock > 0）
8. 创建兑换订单（status = completed）
9. 写积分流水（change_type = redeem_spend）
10. 提交事务
11. 释放分布式锁（Lua 脚本原子操作）
12. 删除用户积分缓存
13. 发送 Kafka 事件 shop.redeemed
```

- **乐观锁冲突** → 回滚事务 → 返回 10302 库存不足
- **积分不足** → 返回 10301
- **锁获取超时** → 返回 10304 操作冲突

## 四、非功能性需求

### 4.1 性能要求

| 场景 | 延迟目标 (P99) | 备注 |
|------|---------------|------|
| 读 - L1 缓存命中 | < 50ms | 本地内存，无网络开销 |
| 读 - L2 缓存命中 | < 100ms | Redis 网络往返 |
| 读 - 回源 DB | < 500ms | 包含 DB 查询 + 回填缓存 |
| 写 - 业务操作 | < 200ms | 不含异步 Kafka 任务 |
| Kafka 消息端到端 | < 5s | 生产 → 消费 → 处理完成 |
| /health 探针 | < 1s | 包含所有依赖检查 |

### 4.2 可用性要求

| 组件 | 高可用策略 |
|------|-----------|
| 服务层 | Deployment replicas ≥ 3，HPA min=3/max=30，PDB minAvailable=2 |
| Redis | Sentinel / Cluster 模式，主从自动故障转移 |
| 数据库 | 读写分离 + 主从切换，从库 3s PING 不健康自动摘除 |
| Kafka | 集群 ≥ 3 Broker，replication factor=3，min.insync.replicas=2 |
| 优雅关闭 | SIGTERM → 30s 内完成请求处理 + 连接释放 |

#### 降级策略

| 故障组件 | 降级行为 |
|----------|---------|
| Redis 不可用 | L1 缓存独立工作，跳过 L2 |
| Redis L2 不可用 | 跳过 L2 直读 DB |
| DB 主库不可用 | 自动 fallback 到备选库（如 SQLite） |
| Kafka 不可用 | 消息暂存本地 JSON 文件，恢复后补偿重放 |
| 第三方验证码不可用 | 跳过验证码校验（可配置） |

### 4.3 可扩展性要求

- **水平扩展**：无状态服务通过 K8s HPA 自动扩缩，指标：CPU > 70% + 内存 > 80% + 自定义 QPS
- **数据库扩展**：分库分表按业务域隔离，单域压力过大时支持按 user_id 取模分表
- **缓存扩展**：Redis Cluster 模式支持在线增删节点
- **消息队列**：适配器模式，Kafka/RabbitMQ/RocketMQ 可配置切换

### 4.4 安全性要求

| 领域 | 措施 |
|------|------|
| 密码存储 | bcrypt 哈希，cost factor ≥ 12 |
| 传输加密 | 生产环境强制 HTTPS/TLS 1.3 |
| JWT 签名 | RS256 非对称算法，私钥签发、公钥验签 |
| 敏感脱敏 | 日志中 password、token、secret 自动替换为 `***` |
| SQL 注入 | ORM 参数化查询，禁止拼接 SQL |
| CSRF | SameSite=Strict Cookie + 自定义 Header 检查 |
| CSP | Content-Security-Policy: default-src 'self' |
| 请求体日志 | > 4KB 自动截断，/login 和 /register 不记录 body |
| 接口鉴权 | 除公开接口外，统一 JWT 中间件鉴权 |

### 4.5 可观测性要求

#### 4.5.1 链路追踪

- **SDK**：OpenTelemetry v1.44+
- **导出器**：OTLP → Jaeger / Grafana Tempo

## 五、技术架构约束

### 5.1 请求链路

```
客户端 → LB / K8s Ingress
     → Go/Gin 服务
         → 全局中间件链（Recovery → Trace → RequestInfo → RequestLogger → CORS → Metrics）
             → v1 组（RateLimit）
                 → 认证路由叠加（SecurityIPLimit + Captcha）
                 → 业务路由叠加（Auth + CircuitBreaker）
                     → L1 缓存（Ristretto, < 1ms）
                     → L2 缓存（Redis/Valkey, 1-5ms）
                     → L3 存储（MySQL/PSQL/MongoDB, 10-200ms）
```

### 5.2 三级缓存架构

| 层级 | 技术 | 延迟 | 容量/策略 | 职责 |
|------|------|------|----------|------|
| L1 | Ristretto 2.0+ | < 1ms | 最大 256MB（可配置），LFU + Window-TinyLFU 回收 | 热点数据本地缓存 |
| L2 | Redis 7.x / Valkey 8.x | 1-5ms | TTL 驱动过期，连接池 min=10/max=100，Pipeline ≤ 100 条 | 分布式共享缓存 |
| L3 | MySQL/PSQL/MongoDB | 10-200ms | 持久化存储 | 数据源 / 最终兜底 |

#### 5.2.1 缓存防护体系

| 防护类型 | 问题 | 解决方案 |
|----------|------|---------|
| **穿透** | 查询不存在的数据 | 布隆过滤器（Redis Bitmap，1 亿容量，1% 误判率）+ 空值缓存（`__NULL__`，TTL 60s） |
| **击穿** | 热点 Key 过期瞬间大量并发回源 | Redis SETNX 分布式锁（EX 10s），未获取锁的协程自旋等待（50ms × 10 次） |
| **雪崩** | 大量 Key 同时过期 | TTL = 基础 TTL × (0.8 ~ 1.2) 随机偏移 |
| **一致性** | 写后读旧数据 | 延迟双删：立即删 L1+L2 + 500ms 异步二次删 L1，失败进入死信日志 |

#### 5.2.2 热点 Key 检测

- **算法**：滑动窗口（窗口 10s），统计 Key 访问频次
- **提升策略**：Top N（默认 100）自动标记为热点 → TTL ×3 + 启用本地预取
- **广播**：L2 变更通过 Redis Pub/Sub（Channel: `cache:invalidate:{namespace}`）同步清理各 Pod 的 L1

#### 5.2.3 TTL 策略

| 数据类型 | 默认 TTL | 原因 |
|----------|---------|------|
| 用户资料 | 30 min | 变更频率低 |
| 商品列表 | 5 min | 中等变更 |
| 任务配置 | 1 h | 几乎不变 |
| 积分余额 | 1 min | 写频繁，需快速反映 |
| 热点数据 | 基础 ×3 | 降低回源频率 |
| 空值标记 | 60 s | 防止穿透同时不过期太快 |

### 5.3 流量治理组件

| 组件 | 技术方案 | 配置 |
|------|---------|------|
| **限流** | 令牌桶算法 | 全局 5000 TPS，Burst=1000；支持按接口/用户维度细粒度 |
| **熔断** | 三态熔断器（sony/gobreaker） | 失败率 ≥ 50% → OPEN（30s）→ HALF_OPEN（放量 10 个探测请求）→ 全部成功 → CLOSED |
| **降级** | 多级降级 | 读降级：跳过 L2 直读 DB；写降级：同步转异步 Kafka |
| **削峰** | Kafka 批量消费 | 8 协程并发 Worker Pool；批量攒批 100 条或 1s 触发；手动提交 offset |

#### 5.3.1 限流响应

- HTTP 429 Too Many Requests
- Header：`Retry-After: <秒>`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
- 指标同步写入 Prometheus Counter

#### 5.3.2 熔断器状态机

```
             失败率 ≥ 50%
CLOSED ────────────────────────> OPEN
  ^                                │
  │                                │ 持续 30s
  │          全部成功              v
  └── HALF_OPEN <────────────── OPEN
           │
           │ 任意失败
           └──────────────────> OPEN
```

- 按路由分组独立熔断，状态变更写入日志 + Prometheus Gauge

> 限流 / 熔断的具体机制、参数与运行时热更新，以 [11_安全与防护.md §四](./11_安全与防护.md#四限流与熔断)（安全专题单一来源）为准。
- OPEN 时返回 HTTP 503 + 错误码 10602

### 5.4 消息中间件

#### 5.4.1 架构

```
[Producer] → Kafka → [Consumer Group (8 Worker Pool)]
                         ↓
                    [处理成功] → 提交 offset
                    [处理失败] → 指数退避重试（最多 5 次）
                                    ↓
                              [全部失败] → DLQ + 本地文件持久化
```

| logging | 日志级别、输出格式（json/console）、输出目标 |
| task | 每日重置时间（UTC）、每周重置星期 |
| idle | 心跳间隔（s）、超时阈值（s）、每分钟积分、每日积分上限 |

### 8.3 热更新支持

- 缓存 TTL
- 限流速率
- 熔断器阈值
- 日志级别

- 非敏感配置：K8s ConfigMap 挂载
- 敏感配置（JWT 密钥、DB 密码、API Key）：K8s Secret 管理

### 9.3 优雅关闭

**信号**：SIGTERM / SIGINT

**关闭顺序（反向依赖，5s/步，总计 < 30s）**：

1. 停止接收新请求（HTTP Server.Shutdown，30s timeout）
2. 关闭 Kafka Consumer（停止拉取，等待处理中的完成）
3. 关闭 DB 连接池
4. 关闭 Redis 连接池
5. 关闭 Kafka Producer（flush 缓冲区）
6. 退出进程（os.Exit）

|------|------|------|
| DB | 每日全量 + binlog 增量备份 | 30 天 |
