### 7. 消费侧 DLQ 积压度量（`mq_consumer_dlq_backlog`，收尾 P2）

- **背景**：生产者侧 `mq_dlq_backlog`（§1）已能反映「待 replay 补发的消息数」。但**消费侧** `kafka_consumer.appendDLQ` 仅落盘 JSONL、无 replay 机制（毒消息 / handler 重试耗尽即存档，**人工清理**），不接任何 backlog gauge，形成全链路可观测盲区——运维看不到「有多少毒消息躺在消费侧 DLQ 等人工处理」。
- **决策**：消费者 DLQ 固化为**「存档」语义**（与生产者 replay 补发语义区分），故用 **gauge 而非 counter**：
  - 进程内只随 `appendDLQ` 落盘 `+1`（无 replay 即无 `-1`）；
  - **启动时 `initDLQBacklog` 扫描 DLQ 目录下已有 `<topic><suffix>.jsonl` 文件行数初始化**，使存量**跨重启反映磁盘真实值**——这是相对 `mq_consumer_messages_total{result=dlq}` 计数器的关键增值（counter 会随进程重置，gauge+启动扫描补齐）；
  - 人工清理文件后重启，glob 扫描不到即归零，避免「僵尸高值」误导告警。
- **改动**：
  - `mq.ConsumerMetrics` 接口新增 `SetDLQBacklog(mqType, topic string, backlog int64)`（含 `nopConsumerMetrics` 默认实现、包级 `setConsumerDLQBacklog` helper）；`mq/metrics_test.go` 的 `captureConsumerMetrics` mock 同步实现。
  - `internal/metrics` 新增 `mq_consumer_dlq_backlog` GaugeVec（标签 `type`(`kafka`)/`topic`），于 `init()` 注册；`mqConsumerMetricsAdapter` 实现该方法。
  - `internal/mq/kafka_consumer.go`：`KafkaConsumer` 增 `dlqBacklog map[string]int64`（读写均在 `dlqMu` 锁内，与落盘同锁）；`Subscribe` 建 DLQ 目录后调 `initDLQBacklog` 扫描初始化；`appendDLQ` 落盘成功后 `dlqBacklog[topic]++` 并上报；新增 `initDLQBacklog`（按 `filepath.Glob` + 每行非空计数）+ `countJSONLLines`（复用 `maxDLQLineBytes` 扫描上限，兼容大消息行）。
- **价值**：与生产者 `mq_dlq_backlog` 互补——
  - `mq_dlq_backlog` = 生产者「待补发」积压（broker 不可达时增长、replay 成功回落）；
  - `mq_consumer_dlq_backlog` = 消费者「毒消息 / 重试耗尽、待人工处理」存量（只增、跨重启、人工清理后归零）；
  - 二者结合可区分「broker 问题导致的发送端积压」与「消息内容问题导致的消费端毒消息」，告警信号更精确（`mq_consumer_dlq_backlog > 0` 持续 N 分钟 = 有毒消息待人工介入）。
- **验证**：`go build ./...` / `go vet ./internal/mq/... ./internal/metrics/...` 全绿；新增 `internal/mq/kafka_consumer_dlqbacklog_test.go`（`TestAppendDLQ*` 递增上报 + `TestInitDLQBacklog*` 启动扫描初始化）PASS；`internal/mq` + `internal/metrics` 全量测试无回归；`docs/09` 指标清单与告警查询已同步。

### 9. 健壮性加固三处（goroutine 泄漏 / panic 拖垮监听 / 重连不响应取消，本轮主动扫描发现）

- **背景**：主动扫描（code-explorer 子代理）识别出三处真实健壮性问题，均为低风险小修，按「优化原则」低成本收口。
- **改动**：
  - **限流器 cleanup goroutine 泄漏**（候选 1，`internal/middleware/ratelimit.go`）：后台清理循环原为 `for range cleanupTick.C`，而 `time.Ticker.Stop` **不关闭 channel**，`StopRateLimiter` 仅停 ticker，goroutine 永久阻塞泄漏。改为 `rateLimiter` 增 `stopCh` 字段，循环改 `select` 监听 `cleanupTick.C` 与 `stopCh`，`StopRateLimiter` 在停 ticker 后 `close(stopCh)` 真正唤醒退出；循环体抽为 `runCleanup(done)` 便于测试。
  - **缓存失效监听缺 recover**（候选 4，`internal/cache/strategy.go`）：`StartInvalidationListener` 回调若 `Invalidate` panic，会拖垮整个失效监听 goroutine——本实例 L1 缓存永远无法被广播失效刷新、产生脏数据（与「消费 handler panic 拖垮进程」同源风险）。在回调入口加 `defer recover`，单条消息异常仅告警、监听继续。
  - **Redis `Subscribe` 重连不响应 ctx 取消**（候选 5，`internal/cache/l2.go`）：重连间隔原为 `time.Sleep(2s)` 阻塞，进程关闭时即便 ctx 已取消仍要等满 2s 才退出。改为 `select` 监听 `time.After(2s)` 与 `ctx.Done()`，ctx 取消立即退出，降低优雅关闭延迟。
- **验证**：`go build ./...` / `go vet ./internal/middleware/... ./internal/cache/...` 全绿；`go test ./internal/middleware/... ./internal/cache/...` 全过；新增 `TestRateLimiter_cleanupGoroutineExitsOnStop`（确定性守护限流器泄漏修复：关闭 `stopCh` 后 goroutine 必须在 2s 内退出，否则判泄漏回归）。

### 12. 应用层有界并发 / 负载卸载 + 就绪排水（高并发高可用加固）

- **背景**：既有防护链已含「连接级上限（`MaxConns`）/ 令牌桶限流（`Ratelimit`）/ 熔断（`CircuitBreaker`）」，但请求一旦通过限流进入业务层、**无应用层在途并发上限**——短时突发（速率未超但瞬时并发极高）会把 DB 连接池打满，且优雅关闭期缺「先摘流量」步骤可能向退出中 Pod 转发请求。
- **改动**：
  - `internal/middleware/concurrency.go` 新增 `ConcurrencyLimit`：用 `golang.org/x/sync/semaphore.Weighted` 做有界信号量，`TryAcquire` **非阻塞**、达上限立即返回 503（load shedding）；系统/运维端点（`/health`、`/ready`、`/metrics`、`/debug/*`、`/swagger`）豁免以免探针被拦截。容量由 `server.concurrency_limit` 配置（0=关闭），启动期固定、重启生效（与 `MaxConns` 一致）。
  - `internal/handler/health_handler.go` 新增进程级 `serving` 原子标志与 `SetServing`；`/ready` 在 `serving=false` 时返回 503。`internal/bootstrap/app.go` 在启动后 `SetServing(true)`、优雅关闭**首步** `SetServing(false)`，使 K8s 就绪探针失败、本 Pod 从 Service 端点摘除，达成「先摘流量、再排空中途请求」的优雅下线。
  - `internal/config/config.go` 新增 `server.concurrency_limit` 字段与校验（`<0` 报错）；`config.yaml`/`config.example.yaml`/`config.stress.yaml` 同步（`stress` 设 4000）。
  - `internal/model/errors.go` 新增 `CodeServiceUnavailable=10005`（「服务繁忙，请稍后重试」），`pkg/response.ServiceUnavailable` 复用。
  - `internal/metrics/metrics.go` 新增 `http_concurrency_in_flight`（Gauge）/ `http_concurrency_rejected_total`（Counter）并注册。
- **指标与告警**：`docs/09` 指标清单 §2.1 补两项、`§四` 补 `ConcurrencyLimitRejected` 告警（5m 内 >10/s 被负载卸载拒绝）；`docs/05` §一补 `server.concurrency_limit` 等字段；`docs/03 §四·续` 补 G/H 两节；新增 [20_高并发架构设计实践.md](./20_高并发架构设计实践.md) 系统梳理高并发设计落地与容量规划；`00` 导航与 `README` 同步。
- **验证**：`go build ./...` / `go vet ./...` 全绿；新增回归测试 `internal/middleware/concurrency_test.go`（`TestConcurrencyLimit_RejectsWhenFull` 验证达上限 503 + `/health` 豁免、`TestConcurrencyLimit_Disabled` 验证未启用直通）、`internal/handler/health_handler_test.go`（`TestHealthHandler_ReadyDrain` 验证关闭期 `/ready` 返回 503 并可恢复）；`go test ./internal/middleware/... ./internal/handler/... ./internal/config/... ./internal/metrics/... ./internal/router/...` 全过。

## 三、优化原则

- 优先消除**文档漂移**与**可观测性盲区**（低成本、低风险、高收益）。
- 结构性重构（如 ES Close、DLQ 消费者 replay）按需独立评估，不混入文档主线，避免一把梭导致回归面过大。
- 所有改动以「`go build` / `go vet` / `go test` 全绿」为合入门禁。
