# 代码分析与优化记录

> 本次工作：分析项目代码、梳理三级缓存读取链路、修复缓存命中 panic 缺陷、清理无效代码、修复关闭期连接泄漏，并沉淀文档与回归测试。

## 一、背景

在排查 k6 压测（shop / idle / mixed）过程中，定位到三级缓存"命中即 panic"这一类根因（旧版 `val.(*model.X)` 直接类型断言）。此后对 repository 层做了系统性排查，并进一步对 cache / repository / service / middleware / mq / main 做了一次全局代码审查。本文记录已修复项、审查中纠正的"伪缺陷"，以及需设计评审的遗留项。

## 二、已修复的缺陷

### 2.1 `TaskRepository.FindAll` 缓存命中 panic（第一轮，已修复）

- 位置：`internal/repository/task_repo.go`
- 问题：`return val.([]model.Task), nil` 对 `cacheMgr.Get` 返回值做切片直接类型断言。
- 触发：首次回源返回 `[]model.Task`（断言成功）；第二次起命中缓存时 L1/L2 以 JSON 存储，反序列化为 `[]interface{}`，断言失败 → panic → 被熔断器 recover 后表现为 `10003 internal server error`。
- 修复：`FindAll` 改用 `cache.DecodeCached[[]model.Task](val)`。

### 2.2 `idle_repo` 无效缓存失效代码（本轮，已清理）

- 位置：`internal/repository/idle_repo.go`
- 问题：`markSettled` 曾调用 `invalidateAllActiveCache(ctx)`，该函数删除常量键 `"idle:active"`。而读取路径的实际 key 为 `idle:active:{userID}` / `idle:active:{userID}:{deviceID}`，二者永不匹配 → 该调用**既不生效也不报错**，是误导性的死代码（让人误以为"批量失效"已覆盖）。
- 澄清（重要）：**这不是脏读 bug**。精确的按用户缓存失效已在业务层 `idle_service.settleSession` 事务提交后通过 `InvalidateActiveByUser(ctx, userID, deviceID)` 正确完成（见 `idle_service.go:618`），因此结算后不会返回已结算的活跃会话。原审查 agent 将其列为"30s 脏读"属误判。
- 修复：删除 `markSettled` 中的无效调用与 `invalidateAllActiveCache` 函数，并更新 `InvalidateActiveByUser` 注释说明职责归属。

### 2.3 `main.go` 业务库连接池关闭泄漏（本轮，已修复，对应审查项 C1）

- 位置：`cmd/server/main.go`
- 问题：优雅关闭流程依次关闭了 `cacheMgr` / Kafka producer / consumer / HTTP server / log / trace，但**从未关闭 `businessDB`（`*db.RWDB`）连接池** → 进程退出前连接 / FD 泄漏（长运行 + SIGHUP 热更新场景下更明显）。
- 修复：在 `initDatabases` 之后新增 `defer businessDB.Close()`；`RWDB.Close()` 会关闭主库与所有从库连接。
- 同类遗留：见第六节 `userDB`（MongoDB client / SQLite 回退）的关闭。

### 2.4 `decode_cached_test.go` 回归测试（本轮，补建）

- 此前文档称该测试已存在，但实际文件未落地。本轮**实际创建** `internal/cache/decode_cached_test.go`，覆盖 nil / 直返原始 Go 类型 / map 中间类型 / `[]interface{}` 切片 / 空切片 五种情形，守护"命中即 panic"类缺陷不再回潮。

### 2.5 `idle_repo.Create` 设备级缓存失效缺失（真实 bug，本次会话修复）

- 位置：`internal/repository/idle_repo.go` 的 `Create`。
- 问题：`FindActiveByDevice`（`idle_repo.go:110`）带 30s 三级缓存且**负缓存**生效——查不到时会把设备级键 `idle:active:{userID}:{deviceID}` 写成空值标记（L2 的 `nullMarkerBytes`，`l2.go:122`），TTL 内再次查询直接命中空值并返回 `nil`。
- 触发链路：`Start` 幂等预检先调 `FindActiveByDevice` → 全新设备查不到 → **设备级键被负缓存为空值（30s）**；随后 `Create` 创建 active 记录，但只 `invalidateActiveCache(ctx, userID)`（失效**用户级**键 `idle:active:{userID}`），**漏掉设备级键**。于是紧随其后的 `StopDevice` 再查 `FindActiveByDevice` 命中空值缓存 → 返回 `nil` → `ErrNotIdle` → `response.Error(CodeNotIdle)`，所有结算请求被误判 `not idle`。
- 影响：任何真实客户端在 30s 内 `start` 后紧接着 `stop-device` 都会失败；k6 `idle_settle` 压测修复前 `idle_settle_ok = 0%`（全部 HTTP 200 但 `code != 0`）。旧脚本走 `/idle/stop`（`FindActiveAll`，无缓存直查 DB）未暴露此 bug，改为 `/idle/stop-device` 后才暴露。
- 修复：`Create` 写入成功后补 `r.invalidateDeviceCache(ctx, record.UserID, record.DeviceID)`，与 `settleSession` 中 `InvalidateActiveByUser` 同时失效用户+设备键的约定保持一致。

### 2.6 GORM `record not found` 日志噪音（本次会话修复）

- 位置：`internal/db/{mysql,postgres,sqlite}.go` 的 `gorm.Config.Logger`。
- 问题：三个适配器均用 `gormlogger.Default.LogMode(Warn)`，把 `ErrRecordNotFound` 当 Error 打印。`Start` 幂等预检、查询未命中这类**正常的未命中**会刷满日志（如 `idle_repo.go:119 record not found`），干扰真实故障排查。
- 修复：新增 `internal/db/gorm_logger.go` 的 `newGormLogger()`（Warn 级别 + 慢查询 200ms 阈值 + `IgnoreRecordNotFoundError: true`）；三个适配器统一改用 `newGormLogger()`，并移除不再使用的 `gormlogger` import。
- 说明：全局生效、属 GORM 最佳实践，不影响功能——`RecordNotFound` 仍会被业务代码正常捕获处理。

### 2.7 优雅退出：关闭流程可观测化 + 后台协程统一取消（本次会话优化）

- 现象：`Ctrl+C` 后感觉"关闭很慢"。但日志里 `Shutting down server...`、`Server exited gracefully`、`[scheduler] stopped` 三行时间戳**完全相同**（同一毫秒），说明这段可见流程 <1ms 就跑完——慢的地方根本不在这里。
- 根因一（日志误导）：真正耗时的资源释放此前**分散在 `main` 的各个 `defer` 里**（`pub.Close` / `consumer.Close` / `cacheMgr.Close` / `businessDB.Close` / `userRepo.Close` / `sched.Stop` / `leader.Stop`）。`defer` 按 LIFO 在 `main` 返回**之后**才执行，且**全程无日志**。`Server exited gracefully` 其实是 `main` 主体最后一行，打印时资源尚未关闭；`[scheduler] stopped` 是第一个 `defer` 的输出，排在其后即为佐证。用户看到"exited gracefully"后进程仍在静默跑 `defer`，遂产生"卡住/很慢"的观感。
- 根因二（Kafka 关闭阻塞）：`mq.type=kafka` 且 broker 不可达（如本地 `127.0.0.1:9092` 未启）时，`KafkaProducer.Close()` 的 `writer.Close()` 会 flush 待发批次而长时间阻塞；消费者 `closeReaders` 的 `CloseTimeout` 默认 10s。这些都发生在静默 `defer` 阶段，无任何日志。
- 根因三（后台协程无法优雅退出）：`RelayLoop` / Kafka `Subscribe` / `StartScanFailover` / `StartPodDiscovery` 等均以 `context.Background()` 启动，永不被取消，进程退出时被硬杀（订阅 offset 不提交、任务被硬切）。
- 修复：
  1. `internal/mq/kafka.go`：`KafkaProducer.Close()` 增加 `closeOnce` 与 **5s 超时兜底**——队列排空 + `writer.Close()` 整体超时后放弃剩余 flush 直接返回（未发出消息已落 DLQ），broker 不可达也不拖死退出。
  2. `cmd/server/main.go`：新增可取消的 `bgCtx/bgCancel`，统一驱动 `RelayLoop`、Kafka `Subscribe`、`StartScanFailover`、`StartPodDiscovery`；关闭时先 `bgCancel()` 让它们立即退出。
  3. `cmd/server/main.go`：把原先分散的 `defer` 关闭**收敛为 `main` 末尾一段有序、显式的关闭序列**（HTTP → 后台协程 → 事件驱动 → 心跳 flush → 调度器 → 选主 → Kafka → 日志/监控 → 链路追踪 → 缓存/DB），每步用 `step()` 包裹并打印 `shutdown step done{step,elapsed}`。这样"谁慢一目了然"，且 `Server exited gracefully{total}` 打印时资源**已真正全部释放**，日志与实际退出一致。
  4. `srv.Shutdown` 超时不再 `zlog.Fatal`（会跳过后续清理），改为 `Warn + srv.Close()` 兜底后继续走完关闭序列。

### 2.8 验证码决策 `needCaptcha` 阈值为 0 时恒触发（真实 bug，本次会话修复）

- 位置：`internal/middleware/captcha.go` 的 `captchaEngine.needCaptcha`。
- 问题：末尾 `return emailCount >= EmailPerMinute || ipCount >= IPPerMinute`。计数的 `if` 守卫已按 `>0` 实现（阈值 `0` 表示"禁用该维度"、不做统计，`ipCount`/`emailCount` 保持 `0`），但 `return` 未同步——当 `IPPerMinute=0` 时 `ipCount(0) >= 0` **恒为 true**，导致本意"禁用该维度"反而变成**每次请求都要求验证码**。
- 触发：将 `trigger.ip_per_minute`（或 `email_per_minute`）配为 `0` 想关闭该维度触发；实际所有请求都被判定需验证码，配合无 token 直接报错 → 变相阻断登录/注册接口。
- 修复：改为按维度分别 `>0` 判定后再比较阈值（`triggered = triggered || window.count(...) >= 阈值`），阈值为 0 的维度整体跳过，只有真正启用且达阈值的维度才触发。该 bug 由本次新增的 `TestNeedCaptcha_DisabledWhenZero` 单测暴露并守护。

### 2.9 审计/监控写入 `Error 1062 Duplicate entry` 主键冲突（真实 bug，本次会话修复）

- 位置：`internal/service/common/log_service.go` 的 `writeLog` / `writeMetric`；关系库写入路径 `internal/repository/log_repo.go`（`Create` / `CreateBatch`）、`internal/repository/monitor_repo.go`（`Record` / `RecordBatch`）。
- 问题：`LogService` 用包级原子计数器 `nextID()`（进程内从 1 自增）给每条 `AuditLog` / `MonitorMetric` 赋 `ID`，原意是供 **ClickHouse** 后端使用（`id Int64` 无默认值，不赋值会被写成 0）。但当同一 `LogRepo` / `MonitorRepo` 注入的是 **GORM/MySQL（或 SQLite）** 后端时，模型 `ID` 字段是 `primaryKey;autoIncrement`——GORM 会把非零的显式 `ID` 写进 INSERT 语句，与表的自增计数器冲突 → `Error 1062 (23000): Duplicate entry 'N' for key '...PRIMARY'`。该计数器的另一致命点：**进程每次重启归零**，必然与历史持久化主键相撞（压测/热更新 SIGHUP 后必现）。k6 压测日志中 `audit_logs.PRIMARY` 与 `monitor_metrics.PRIMARY` 的 duplicate entry 即源于此。
- 修复：保留 `LogService` 的 `ID: nextID()` 不变（ClickHouse/ES 仍拿到显式非空 id）；仅在**关系库 GORM 写入路径**用 `db.Omit("ID")` 省略 id 列，让 MySQL/SQLite 用自增主键生成 id，彻底消除与主键/自增计数器的冲突。ClickHouse 路径不受影响（其 `id` 列无唯一约束，且本就依赖显式值）；ES 路径把 `id` 仅作为 JSON body 字段存储，亦无约束。改动局限在 4 个写入入口，未触碰读路径与模型定义。
- 验证：`go build ./...`、`go vet ./internal/repository/...` 通过。仓库既有 repository 测试为 nil 守卫接口测试、不依赖真实 DB，未新增 DB 依赖测试（与现有约定一致）。

### 2.10 启动不自动建 `shop_item_stock_buckets` 表（真实 bug，本次会话修复）

- 位置：`internal/bootstrap/bootstrap.go` 的 `businessModels`（AutoMigrate 表清单）；`internal/model/order.go` 的 `ShopItemStockBucket`。
- 问题：库存分桶表 `shop_item_stock_buckets`（模型 `model.ShopItemStockBucket`，复合主键 `(item_id, bucket)`）**漏列进 `businessModels`**。因此：
  - `migration.auto_migrate=true` 时，GORM `AutoMigrate(businessModels...)` 从未见过该模型，不会创建该表；
  - 该表同时也是 `BackfillStockBuckets`（启动期回填存量分桶）与读路径 `fillItemStock`/`fillBucketStock` 的查询对象。表不存在即报错 `Error 1146 (42S02): Table 'hc_business.shop_item_stock_buckets' doesn't exist`，并导致 `Backfill stock buckets failed`（WARN）。
  - 该表虽已写入 `migrations/business/*/20260708_initial_schema.up.sql`（生产路径依赖 `make migrate DB=business`），但运行库实际未建出，且 AutoMigrate 路径也无法兜底——属于「AutoMigrate 清单与 SQL 迁移 / 代码引用不一致」的疏漏。
- 修复：把 `&model.ShopItemStockBucket{}` 补进 `businessModels`，使 `auto_migrate=true` 时 GORM 自动建表，同时让 `checkBusinessTables` 的缺失表自检覆盖该表（缺失时给出准确告警与 `make migrate DB=business` 提示）。未改动模型定义、迁移 SQL 与读/写路径逻辑。
- 验证：`go build ./...`、`go vet ./internal/bootstrap/...` 通过。

### 2.11 普通兑换削峰层对齐抢购：售罄在 DB 之前拦截 + 真售罄不回滚（性能/正确性优化，本次会话修复）

- 位置：`internal/service/shop/shop_service.go` 的 `Redeem`；`internal/cache/manager.go` 新增 `IsRedeemSoldOut`，配合既有 `ReconcileRedeem` / `TryAcquireRedeem` / `ReleaseRedeem`。
- 问题：shop k6 压测中普通兑换（`/shop/redeem`）成功 500、失败 334629，其中 `10302 数据库行锁售罄` 占 **333830**，而削峰层 `10311 削峰层售罄` 仅 **799** —— 约 99.76% 的「库存不足」空刀穿透到 `DeductStock` 行锁。根因是两层的**顺序与回滚语义**都与抢购（`FlashSale`）相反：
  - **顺序相反**：普通 `Redeem` 先 `FindItemByID`（其内部 `fillItemStock` 每次都读 DB 分桶），再才做 Redis 预扣；而抢购 `FlashRedeem` 是 **Redis 预扣（步骤 3）先于任何 DB 读取（步骤 4/5）**。于是普通兑换的削峰层永远排在 DB 读取之后，无法为售罄请求挡刀。
  - **回滚语义相反**：普通兑换 Redis 预扣成功后，只要事务未提交就 `ReleaseRedeem`（INCR）回填计数器；抢购把 Redis 当权威配额、售罄不回滚。故普通兑换在「Redis 预扣成功但 DB 行锁判售罄」的竞态窗口里，计数器被反复从 0 抬回 1，下一请求又穿过削峰层打到 DB，形成空刀振荡。
- 修复（两步对齐抢购）：
  1. **削峰层前置**：`Redeem` 在 `FindItemByID` / DB 行锁**之前**先 `IsRedeemSoldOut` 只读判断 `redeem:stock` 计数器；命中（计数器存在且 ≤0）即返回 `ErrRedeemSoldOutPeak`(10311)，**不触达 DB**。键不存在（未预扣/仍在售）则放行后续链路，由 `FindItemByID` + 行锁权威兜底。`IsRedeemSoldOut` 仅在 L2 可用且键存在时返回 true，L2 不可用时降级为纯 DB 兜底（不影响正确性）。
  2. **真售罄不回滚**：`Redeem` 的回滚 `defer` 原对一切未提交失败都 `ReleaseRedeem`（INCR）。改为仅当失败**非** `ErrStockInsufficient`（积分不足 / 订单写失败等，库存仍可用）才回滚释放名额；当 DB 权威判定**真售罄**（`ErrStockInsufficient`）时，调用 `ReconcileRedeem(itemID, 0, ttl)` 把 Redis 计数器**硬置 0**（而非 INCR 回填），使削峰层持续拦截、消除空刀振荡。此语义与抢购一致：`reconcileRedeemLoop` 周期对账同样会把售罄商品置 0，本修复关闭了两次对账之间的竞态窗口。
- 影响与正确性：
  - 在售路径行为不变（仍 `FindItemByID` → 预扣 → 行锁扣减），仅售罄路径从「DB 前置校验 10302」上移到「Redis 削峰 10311」，且 DB 库存不再被无效请求触碰。
  - `redeem:stock` 计数器为 0 **仅**在商品真售罄时出现（成功兑换递减至 0 / `ReconcileRedeem` 置 0 / 真售罄不回滚硬置 0），不会误拦在售商品；计数器 TTL 到期后被重新预热，仍由 DB 权威值对齐，无丢失销售风险。
  - 观测：`metrics.RedeemTotal{result=sold_out_peak}`(10311) 占比应从 ~0.24% 显著提升，`sold_out_db`(10302) 应趋近于 0，DB 行锁竞争压力大幅下降。
- 验证：新增 `internal/service/shop/shop_service_test.go` 两个 env-gated 集成测试（需可达 Redis，L2 不可用时自动跳过，本仓集成环境已实际运行通过）：
  - `TestRedeem_PeakLayerInterceptsBeforeDB`：Redis 计数器硬置 0 时 `Redeem` 返回 10311 且 **DB 库存未被扣减**（证明拦截在 DB 之前）；计数器=剩余库存时仍正常兑换扣减 1。
  - `TestRedeem_PeakLayerNoRollbackOnSoldOut`：锁定「真售罄硬置 0（ReconcileRedeem）」vs「旧逻辑 ReleaseRedeem(INCR) 回填为 1」的缓存原语不变式。
  - `go build ./...`、`go vet ./internal/service/shop/`、`go test ./internal/service/shop/` 全绿。

### 3.2 `none` 路径改造为接口层 no-op（真实健壮性缺口，已修复）

- 位置：`internal/mq/factory.go` + 新增 `internal/mq/noop.go`；`cmd/server/main.go` 接线。
- 问题：工厂对禁用分支返回 `nil`，"不启用事件总线"的正确性**依赖每个调用方（IdleService / ShopService / AuthService / pointsOutbox / main.go 的 degrade sender）都记得判空**。任一遗漏即 `panic`。这是把"接口契约"散落到了所有调用点。
- 修复：工厂对 `none`/未配置/连接缺失统一返回**非 nil 的 no-op 生产者/消费者**（`nopProducer`/`nopConsumer`，`Send`/`Subscribe`/`Close` 为空操作）。no-op 在接口层强制成立，调用方无需也不可能漏判空。
- 配套：`main.go` 中两处依赖"是否禁用"的逻辑改以 `mq.IsEnabled(&cfg.MQ)` 判定，确保行为与原 nil 路径完全一致、不引入回归：

- 一致性验证（关键，避免回归）：积分余额在 `none` 下仍由**进程内 Outbox 同步快路径 `tryApply` + 后台 `RelayLoop`** 保证最终一致（事件仅作冗余跨进程触发），与是否有 MQ 总线无关——故 no-op 不影响 S1 一致性。

## 三（续 3）、MQ 发送路径超时真正落实（本次会话）

此前为 RocketMQ 增加了 `send_timeout`/`send_retries`、为 RabbitMQ 加了确认模式，但发送路径并未真正把超时落到实处，存在两个健壮性问题：

### 3.9 RocketMQ `Send` 超时形同虚设
- 问题：`producer.WithSendMsgTimeout` 仅在调用方传入「无截止时间的 ctx」时由 SDK 内部生效；而 outbox relay、部分同步发送直接传 `context.Background()`，行为依赖 SDK 内部，不显式、不可靠。
- 改动：`Send` 内用新增的 `ctxWithTimeoutIfUnset(ctx, rocketSendTimeoutOf(cfg))` 派生子 ctx（已带 deadline 则原样透传）。超时真正由本项目控制，与 `mq.rocketmq.send_timeout` 对齐。

### 3.10 RabbitMQ 确认等待可能永久阻塞、冻结生产者（高优先修复）
- 问题：`Send` 持 `mu` 锁串行发布，确认等待 `select { case <-p.confirms: case <-ctx.Done(): }`。若调用方传 `context.Background()`（无 deadline），且 broker「已接收发布但确认回执丢失/极慢」，会持锁无限阻塞——所有后续发布都在等这把锁，整个生产者被冻结，事件发布彻底卡死。
- 改动：确认等待改用 `ctxWithTimeoutIfUnset(ctx, rabbitSendTimeoutOf(cfg))` 派生的 `confCtx`，新增 `case <-confCtx.Done():` 超时分支（默认 10s，仅安全网；broker 关 channel 会立即返回零值回执，不会真等到超时）。`RabbitMQConfig` 新增 `send_timeout`（默认 10s）并落入 `config.yaml`。
- 共享工具：新增 `internal/mq/ctx.go`（`ctxWithTimeoutIfUnset`）+ `ctx_test.go`（两套行为：有 deadline 原样且 cancel 为空操作 / 无 deadline 派生带截止子 ctx），两处生产者复用，避免重复实现与引入 import 环。

### 3.11 配套
- 配置：`config/config.yaml` 补 `mq.rabbitmq.send_timeout: 10s`（含注释说明安全网语义）。
- 文档：`docs/05_配置参考.md` 补 `mq.rabbitmq.send_timeout` 行。
- 验证：`go build ./...` / `go vet ./...` / `gofmt`（含 config.go 因新增字段触发的对齐，已 `gofmt -w` 修正）全通过；`internal/mq` 测试全绿（新增 `TestCtxWithTimeoutIfUnset_*`）。

## 三（续 4）、RabbitMQ 生产者 channel 池化 + Kafka 统一发送超时（本次会话）

### 3.12 RabbitMQ 单 channel 串行 → channel 池提升吞吐
- 问题：原 `RabbitMQProducer` 为单连接单 channel，所有 `Send` 共享一把 `mu` 锁串行发布并各等一条 broker 确认回执。吞吐被「一次发布 + 一次 confirm RTT」串行化（约单通道往返延迟），高并发下成为瓶颈。
- 改动：改为**单连接 + N channel 池**（默认 `defaultRabbitPoolSize=8`，配置 `mq.rabbitmq.pool_size`，映射 `rabbitPoolSizeOf`）。
  - 每 channel 各自持锁串行发布 + 独立 `NotifyPublish` 确认流，确认顺序 = 发布顺序，读取一个 `Confirmation` 即对应本条消息（可靠性不变）。
  - `Send` 从 `pool`（缓冲 `chan *rabbitChannel`）取空闲 channel，`release` 归还；池空（全部在途）时阻塞于取 channel，形成**有界并发背压**（并发度上限 = PoolSize）。
  - `acquire` 受 `ctx` 取消约束（关闭时不再无限等待空闲 channel）。
  - 失效 channel 自愈：`recreate` 在「发布错误 / 确认未返回 Ack」时重建同一池槽的 channel（调用方须持 `rc.mu`），避免带病复用污染连接池；连接级故障则保留原槽（后续发布仍失败，与旧版一致，不引入自动重连）。
  - `Close` 关闭池中全部 channel + 连接，加 `closeOnce` 幂等。
- 收益：发布并发度从 1 提升到 PoolSize，吞吐近似线性提升；确认等待超时仍是「仅冻结该 channel」，不再冻结整个生产者。

### 3.13 Kafka 生产者统一发送超时上界（与 RocketMQ/RabbitMQ 对齐）
- 问题：Kafka 生产者 `sendOne` 实际写发生在 `loop`/`溢出池`/`replay` 路径，统一传 `context.Background()`（无 deadline），发送上界依赖 writer 内部 `WriteTimeout`（= `DeliveryTimeout`）——行为受控但「隐式、依赖 SDK 内部」，与另外两个生产者的显式 `send_timeout` 不统一。
- 改动：`sendOne` 内用 `ctxWithTimeoutIfUnset(ctx, kafkaSendTimeoutOf(p.cfg))` 派生子 ctx（已带 deadline 则透传），`kafkaSendTimeoutOf` 复用 `Producer.DeliveryTimeout`（默认 5s）。超时真正由本项目控制，三套生产者语义一致。
- 共享：复用上一轮新增的 `internal/mq/ctx.go`（`ctxWithTimeoutIfUnset`）。

### 3.14 配套与验证
- 配置：`config/config.yaml` 补 `mq.rabbitmq.pool_size: 8`（含注释说明并发度上限语义）。
- 文档：`docs/05_配置参考.md` 补 `mq.rabbitmq.pool_size` 行，并修正 `mq.rabbitmq.send_timeout` 描述为「仅冻结该 channel」。
- 测试：新增 `internal/mq/helpers_test.go`（`TestRabbitPoolSizeOf` / `TestKafkaSendTimeoutOf`），原 `rabbitmq_test.go` 空 URL 分支不受影响。

## 三（续 5）、MQ 吞吐/可靠性优化（按 QPS 评估 1~5 落地）

> 背景：依据四队列（kafka/rabbitmq/rocketmq/memory）的 QPS 评估，逐项落地 5 项优化。

### 3.15 RocketMQ 生产者异步化（对齐 Kafka，最高优先级）
- 问题：原 `RocketMQProducer.Send` 为**同步 `SendSync`**，会阻塞调用方（shop_service / points_outbox 的 `_ = publisher.Send(...)` 虽语义 fire-and-forget，但实现上阻塞到 broker 往返），且吞吐被 `1/延迟` 钳制。
- 改动：改为**异步模型**（与 Kafka 生产者一致）：`Send` 仅入队即返回；后台 `loop` 协程经 `SendSync` 真正发送；队列满转入有界溢出池后台发送（`sendSem` 限流、`wg` 跟踪）；溢出池也打满则降级到**本地 DLQ**（`replayLoop` 每 30s 在 broker 恢复后自动补发，不丢消息）。`Close` 关闭信号 + 5s 兜底超时。
- 配置：`RocketMQConfig` 新增 `queue_size`(8192) / `max_overflow_workers`(256) / `dlq_enabled` / `dlq_local_path`（`config.yaml` 已开启 DLQ）。
- 可靠性：`SendSync` 仍保留 `send_timeout` 超时 + `send_retries` 客户端重试，故「异步」仅解耦调用方与 broker 往返，不牺牲送达保证。

### 3.16 共享本地 DLQ 存储（Kafka / RocketMQ 复用）
- 抽出 `internal/mq/dlq.go` 的 `dlqStore`（按 topic 分文件 JSONL），Kafka 与 RocketMQ 生产者共用，统一「broker 不可达落盘、恢复后 replay 补发」语义，消除两处重复实现，DLQ 文件格式跨实现一致。

### 3.17 Kafka 消费并发下限上调
- 原 `worker_pool_size` 缺失时回落 `1`（单 worker 锁死消费吞吐）。新增 `defaultKafkaWorkerPoolSize=8` 作为下限；`config.yaml` 由 16 上调至 **32**。

### 3.18 RabbitMQ 生产者池默认上调 + Memory 消费并发可配
- RabbitMQ `pool_size`：本仓库 `config.yaml` 由 8 上调至 **32**（代码默认仍为 8，高 QPS 可继续上调，受 broker 每连接 channel 上限约束）。
- Memory 消费者：新增 `mq.consumer.concurrency`（默认 1，每 topic 串行）；现可配置每 topic 处理 goroutine 数缓解串行瓶颈。Memory 仍属 at-most-once（缓冲满即丢弃），仅限本地开发/测试，已在 `NewMemoryProducer`/`NewMemoryConsumer` 加一次性 WARN 提示。

### 3.21 RabbitMQ 生产者异步化（对齐 Kafka / RocketMQ）
- 问题：RabbitMQ 生产者 `Send` 为**同步等待 publisher confirm**（逐条取 channel → 持锁发布 → 等 broker 落盘回执）。在 broker confirm 慢 / 网络 RTT 高时，`Send` 阻塞调用方（shop_service / points_outbox 的 `_ = publisher.Send(...)` 虽语义 fire-and-forget，但实现上阻塞到 broker 往返），吞吐被 `1/延迟` 钳制，且确认等待超时仅冻结该 channel（非整生产者，但仍拖慢关键路径）。
- 改动：改为**异步模型**（与 Kafka/RocketMQ 完全一致）：
  - `Send` 仅入队即返回（`queue`，默认 8192）；队列满转入有界溢出池后台发送（`sendSem` 限流、`wg` 跟踪）；溢出池也打满则降级到**本地 DLQ**（`replayLoop` 每 30s 在 broker 恢复后自动补发，不丢消息）。
  - 后台 `pool_size` 个 `worker` 协程并发消费队列，经 channel 池发布并等待 broker 确认（publisher confirm）；把「等待 broker 确认」从调用方线程移到 worker，并发度上限仍 = `pool_size`（每 channel 串行确认，确认顺序一致，可靠性不变）。
  - 复用共享 `dlqStore`（`dlq.go`）做降级；`Close` 关闭信号 + 5s 兜底超时（超时返回 error，worker 由连接关闭自然退出，进程退出无 goroutine 泄漏）。
  - `publishOne` 仅负责「序列化 + 发布 + 等确认」并返回 error，**不在内部记计数/落 DLQ**，以便 `replay` 复用而不重复追加（与 RocketMQ 结构一致）；marshal 失败标记为 `errRabbitMarshal`，不落 DLQ（无法补发）。
- 配置：`RabbitMQConfig` 新增 `queue_size`(8192) / `max_overflow_workers`(256) / `dlq_enabled` / `dlq_local_path`（`config.yaml` 已开启 DLQ 并配 `./data/dlq/`）。`pool_size` 语义扩展为「= 后台 worker 数」。
- 可靠性：worker 内仍等 broker confirm（`send_timeout` 默认 10s 兜底），失败 recreate channel / 降级 DLQ，故「异步」仅解耦调用方与 broker 往返，不牺牲送达保证；调用点均已 `_ = Send(...)`，不依赖同步返回值。
- 测试：`helpers_test.go` 新增 `TestRabbitAsyncQueueCfg`（异步队列/溢出池配置解析）；原 `rabbitmq_test.go` 空 URL 分支不受影响。
- 验证：`go build ./...` / `go vet ./...` / `gofmt` / YAML 校验 / `internal/mq` 测试全绿。

### 3.22 Producer.SendSync（同步发送，关键链路拿投递结果）
- 动机：异步 `Send` 失败一律降级 DLQ 且不返回 error（调用点均为 `_ = Send(...)`）。但关键链路（如支付成功事件）需在"发送失败"时立即决策（回滚/重试），异步无法满足。故在 `Producer` 接口新增 `SendSync`。
- 语义：`SendSync` **阻塞等待 broker 确认后返回 error**；**失败不降级 DLQ**，直接把投递结果交还调用方决策（要 DLQ 兜底就继续用 `Send`）。三种队列实现：
  - `kafka`：直调 `writer.WriteMessages`（受 `DeliveryTimeout` 超时上界 + 熔断器），返回 error。
  - `rocketmq`：直调底层 `SendSync`（受 `send_timeout` + 客户端重试），返回 error。
  - `rabbitmq`：直调 `publishOne`（等 publisher confirm），返回 error。
  - `memory` / `noop`：与 `Send` 等价（进程内 / 丢弃计数）。
- 安全网：`adapter.go` 增加 5 个编译期断言 `var _ Producer = (*XxxProducer)(nil)`，任一实现漏掉 `SendSync` 会编译失败。
- 测试：`memory_test.go` 新增 `TestMemoryMQ_SendSync`（往返验证）；`noop_test.go` 的 `TestNoopProducer_SendNoop` 覆盖 `SendSync` 空操作。
- 验证：`go build` / `go vet` / `gofmt` / `internal/mq` 测试全绿。

### 3.23 本地 DLQ 健壮性加固（防磁盘爆 / OOM / 并发丢消息）
- 背景：Kafka/RocketMQ/RabbitMQ 生产者共用 `dlq.go` 的本地文件 DLQ（broker 不可达时落盘、恢复后 replay 补发）。审查发现三处隐患：
  1. **并发数据丢失（真实 bug）**：`replayFile` 读改写整个文件时**未持锁**，而 `append` 持锁追加——replay 的 `os.WriteFile` 会覆盖 replay 期间并发 `append` 追加的新行，导致丢消息。
  2. **磁盘无限增长**：`append` 对 DLQ 文件无大小上限，broker 长期不可达会把磁盘写满。
  3. **OOM 风险**：`replayFile` 用 `os.ReadFile` 一次性全量读入内存，大文件可能 OOM，且每 30s 全量重写。
- 改动（全部集中在 `dlq.go`；`newDLQStore` 增加 `mqType` 参数用于超限丢弃计数）：
  - **单文件字节上限**（`maxBytes`，默认 256MB）：`append` 预估追加后超限则丢弃本条并 `recordDropped` + 告警，保留较早消息。
  - **rename 快照式 replay**：`replayFile` 先在持锁下原子 `os.Rename` 主文件到 `.replaying` 快照（瞬时），随后耗时的 `relay`（等 broker）在快照上流式进行、**不持锁**，故不阻塞并发 `append`（append 立即在新主文件继续追加），根治并发覆盖丢失。
  - **流式补发 + 批量上限**：用 `bufio.Scanner`（单行上限 8MB）逐行读，避免全量入内存；单轮每文件最多补发 `replayBatchMax`（默认 1000）条，避免一次 tick 猛打 broker / 长时间占用协程；失败/超批/损坏行经 `writeBack` 持锁追加回主文件（不丢）。
  - **崩溃遗留恢复**：`replayAll` 先 `recoverLeftovers` 把上次进程崩溃遗留的 `.replaying` 快照并回主文件；扫描损坏（超长行）保留为 `.corrupt` 供排查，绝不静默丢弃。
- 测试：新增 `dlq_test.go` —— `TestDLQ_MaxBytesDropsMessage`（大小上限）、`TestDLQ_ReplayBatchLimit`（批量上限分轮补完）、`TestDLQ_ReplayFailureKeepsRemaining`（失败保留、恢复补完）、`TestDLQ_ConcurrentAppendReplayNoLoss`（并发 append+replay 零丢失，`-race` 通过）、`TestDLQ_RecoverLeftover`（崩溃快照恢复）、`TestDLQ_DisabledNoop`。
- 验证：`go build` / `go vet` / `gofmt` 通过；`internal/mq` 测试全绿；`-race` 下 DLQ 测试无数据竞争。
- 测试修复（3.24）：`TestSend_OverflowSaturatedToDLQ` 此前在 `-race` 全量并测时对时序敏感 —— 测试在 `Send` 循环后**立即读 DLQ 文件**，但后台 `loop` 协程尚未处理完队列里那条缓冲消息（`sendOne` 失败落 DLQ），`-race` 放大 `loop` 延迟导致读到行数不足 90。修复：断言前先 `waitQueueDrain`（轮询 `len(p.queue)==0` 确认后台 loop 已取出所有缓冲消息），再 `waitForDLQCount` 轮询文件行数达标。修复后 `-race` 连跑 5 次全绿、整套 `internal/mq` 测试 `-race` 通过。新增辅助函数 `waitQueueDrain` / `waitForDLQCount` 位于 `kafka_test.go`。

### 3.25 消费重试指数退避被跳过（真实 bug，跨三种队列）
- 背景：消费失败重试默认走 `retryProcess`（RabbitMQ / 内存消费者复用）或 Kafka 消费者自带的 `process`。二者都**复用一个 `time.Timer`** 实现指数退避。
- 根因（真实 bug）：首次 `handler` 执行耗时**超过 `base` 延迟**时，该 `time.Timer` 在第一次尝试期间就已触发、`timer.C` 留下残留值；`attempt==1` 的 `timer.Reset(delay)` + `select{ case <-timer.C }` 会**立即读到残留值而跳过退避**。后果：下游正处故障/高负载时，重试反而无退避猛打，违背指数退避初衷（甚至加剧雪崩）。仅首次 handler 较慢时触发，故此前未被察觉。
- 修复：抽出 `sleepWithContext(ctx, d)` 辅助（`ctx.go`）——每次创建独立定时器并 `defer Stop`，既**不泄漏**（区别于 `time.After`），又从根上消除"复用 Timer + 残留值"导致的跳退避。两处重试逻辑统一改用它：
  - `retry.go` 的 `retryProcess`；
  - `kafka_consumer.go` 的 `process`（删去原先的 `time.NewTimer` + `Stop` + `Reset` 复用块）。
- 测试：新增 `retry_test.go` —— `TestRetryProcess_BackoffNotSkipped`（首次 handler 故意慢于 base，断言相邻两次重试间真正等待了 base 退避，直接锁死该 bug）、`TestRetryProcess_ExhaustsAndReturnsErr`（耗尽返回末次错误）、`TestRetryProcess_CtxCancelReturnsErr`（ctx 取消立即返回 `context.Canceled`）。`-race` 连跑 3 次全绿。
- 验证：`go build` / `go vet` / `gofmt` 通过；`internal/mq` 全套测试（含 `-race`）通过。

### 3.26 Producer：消除 broker 恢复瞬间的「队列→loop→DLQ」额外一跳
- 背景：生产者异步发送路径为 `Send` → 队列 → `loop` → `sendOne`（经熔断器）→ 失败则落 DLQ → `replayLoop` 补发。
- 根因（真实设计缺陷）：broker 不可达触发熔断器连续 5 次失败后进入 OPEN；此后 `loop` 取出的消息被 `breaker.Execute` 返回的 `ErrOpenState` 判为「发送失败」并**立即落 DLQ**。但 broker 可能在熔断器仍 OPEN 的窗口内已经恢复——此时本可直接发出的消息却被落盘进 DLQ、再等 replay ticker（30s）补发，多走「队列→loop→DLQ→replay」一跳，引入可达 replay 间隔的额外延迟（不影响最终送达，但抖动明显、且白白经历一次落盘/重放 IO）。
- 修复：区分「熔断打开」与「真实发送错误」——
  - `sendOne` 在 `gobreaker.ErrOpenState` / `ErrTooManyRequests` 时返回新增 sentinel `errBreakerOpen`，**不在此降级 DLQ**，交由调用方决定去向；其余真实错误仍按原语义落 DLQ（抽出 `fallbackToDLQ` 统一出口）。
  - `loop` 正常路径收到 `errBreakerOpen` 时调用新增 `requeue`：把消息放回队列尾部并 `sleepWithContext(ctx, requeueBackoff=200ms)` 退避，等待熔断器半开探测成功后由 `loop` 直接发出——**消除 DLQ 那一跳**；队列满（内存缓冲耗尽）时 `requeue` 才降级 DLQ 由 replay 补偿，防消息在内存无限堆积。
  - 溢出池 goroutine 与关闭排空分支保留「失败即落 DLQ」语义（两者无「等待恢复」语义：溢出池落 DLQ 避免 goroutine 无限重投占满 `sendSem`；关闭时落 DLQ 确保不丢消息）。
  - `relay`（replay 路径）行为不变：breaker OPEN 时返回 `ErrOpenState`，`drainSnapshot` 照常写回主文件待下次探测。
- 附带修复（配置被静默覆盖的真实 bug）：`NewKafkaProducer` 原用 `maxInt(pc.QueueSize, 8192)` / `maxInt(pc.MaxOverflowWorkers, 256)`，会把**小容量 / 0 配置静默覆盖**（如测试 `QueueSize=1` 变 8192、`MaxOverflowWorkers=0` 变 256），导致「满队列溢出」「禁用溢出池」等行为失效。改为：仅对 `<=0`（未配置）回退默认，**正数配置（含 `MaxOverflowWorkers=0`=禁用溢出池）真正生效**；并在 `config.loadFromFile` 补默认值应用（与下限一致，同时覆盖启动与热更新重载路径）。
- 测试：新增 `TestSendOne_BreakerOpenNoDLQ` 锁死核心不变量——连续 5 次失败使熔断器 OPEN 后，`sendOne` 返回 `errBreakerOpen` 且**不落 DLQ**（before==after 行数）；`-race` 连跑稳定通过。`TestSend_OverflowSaturatedToDLQ` 因配置覆盖 bug 修复而恢复确定性（小队列 + 禁用溢出池 → 队列满直接 DLQ，goroutine 不增长）。
- 验证：`go build` / `go vet` / `gofmt` 通过；`internal/mq`、`internal/config` 全套测试（含 `-race`）通过；发布配置 `config.yaml` 经 `TestLoadShippedConfig` 仍通过。

### 3.27 Consumer：ordered_commit 跨分区一致性澄清 + 同步落盘 + 消费侧 Outbox/Dedup
- 背景：用户指出 `ordered_commit` 模式在「跨分区一致性」上的语义不清。经分析明确：**Kafka 不保证跨分区顺序/原子提交，`ordered_commit` 只保证「分区内」严格有序与进度，不提供任何跨分区一致性**——各分区 readerLoop 是独立 goroutine，彼此无协调、无全局顺序。无论 true/false，本机制都是 per-partition 的。
- #1 文档修正（消除过强表述）：原 `config.go` / `docs/05` 称 ordered_commit「**彻底消除**崩溃丢消息窗口」是不准确的——
  - 旧实现 offset 仅写内存、依赖 5s 周期落盘，进程在「已处理未落盘」窗口崩溃仍会重放（at-least-once，非 exactly-once）；
  - 且「跨分区一致性」根本不在此机制能力范围内。已改写为「仅保证分区内 + ordered 模式把崩溃重放窗口缩到最小」，并补充「真正不丢消息需同 key 同分区 + 注入 ConsumerProgressStore」的边界说明。
- #2 ordered_commit 同步落盘（缩小崩溃重放窗口）：
  - 抽出 `commitOffset`，`ordered_commit=true` 时 `ConsumerProgressStore.Commit(sync=true)` → 文件存储在返回前即 `flush()` 落盘（等价「处理完即提交」）；并发模式 `sync=false` 仍走后台 5s 周期落盘（吞吐优先）。两种模式均「只增不减」。
  - 测试 `TestFileProgressStore_SyncFlush` 锁死不变量：sync commit 返回后 offset 已落在文件（不经 5s 周期）。
- #3 消费侧事务/Outbox（跨分区幂等去重）：新增 `ConsumerProgressStore` 抽象与两种实现，使消费进度/去重可插拔——
  - `FileProgressStore`（默认）：兼容旧 `offsetStore` 本地 JSON 行为，新增 `Seen` 返回 false（不做跨分区去重）。
  - `SQLProgressStore`（gorm，新增）：`kafka_consumer_progress`（每分区一行，offset 只增不减 upsert）+ `kafka_consumer_dedup`（event_id 唯一，跨分区幂等去重），二者在单事务内原子提交；`NewSQLProgressStore(db)` 自动建表（幂等）。建议传入与业务写**同一实例**的 `*gorm.DB`，让 handler 在同一 DB 事务内提交业务数据并（经本 store）推进 offset，达到消费侧 exactly-once；并新增 `WithProgressStore` 注入入口。
  - `handle` 在解析出 `EventID` 后先 `Seen` 查询，**跨分区/重启重投的同 event_id 直接跳过**（offset 仍推进），与 producer 侧 `event_dedup` / `points_outbox` 的「恰好一次」语义对称。
  - 迁移：已整合到 `migrations/business/{postgres,sqlite,mysql}/20260708_initial_schema.up.sql`（消费侧进度表 kafka_consumer_progress / kafka_consumer_dedup）。
- 测试：`TestFileProgressStore_SyncFlush`（#2）、`TestFileProgressStore_OnlyIncrease`、`TestSQLProgressStore_RoundTrip`（#3：offset 推进 / 只增不减 / event_id 跨分区去重 / FlushInterval=0）。`internal/mq` 全套（含 `-race`）、`internal/config` 全套通过。
- 边界声明（重要）：本实现仍非 Kafka 事务级 exactly-once。若要求「业务写与 offset 原子提交」，必须由 handler 在同一 DB 事务内完成业务写并调用注入的 `SQLProgressStore.Commit`（框架提供原语，不隐式提供）。真正的「跨分区原子提交」在 Kafka 模型下不可达，只能靠同 key 同分区 + 本机制逼近。

### 3.28 三队列（Kafka/RabbitMQ/RocketMQ）能力对比与对齐补全
- 背景：用户要求持续完善队列逻辑、补全三个生产级队列（Kafka/RabbitMQ/RocketMQ）的能力并分析差异。经逐文件核对，三者 producer 已大体对齐（异步队列 + 溢出池 + 本地 DLQ + replay + SendSync），但 consumer 端能力分散、且 RabbitMQ/RocketMQ 生产者缺熔断器。本次补全以「统一能力基线」为目标，同时尊重各 MQ 的模型本质差异（分区 vs 队列）。
- 三队列能力对比（Producer）：
  | 能力 | Kafka | RabbitMQ | RocketMQ |
  |---|---|---|---|
  | 异步队列+溢出池 | ✅ | ✅(channel池+worker) | ✅ |
  | 熔断器 gobreaker | ✅(requeue避免恢复瞬间降级DLQ) | ✅(**本期补**) | ✅(**本期补**) |
  | 本地DLQ+replay | ✅ | ✅ | ✅ |
  | SendSync | ✅(带熔断) | ✅ | ✅ |
  | Broker确认 | RequiredAcks | Publisher Confirm | SendResult |
- 三队列能力对比（Consumer）：
  | 能力 | Kafka | RabbitMQ | RocketMQ |
  |---|---|---|---|
  | 重试 | 本地+DLQ | 本地+broker DLX | 仅broker %RETRY% |
  | 死信 | 本地文件DLQ | broker DLX+DLQ队列 | broker %DLQ% |
  | ordered_commit（分区串行+同步落盘） | ✅ | 不适用(无分区) | 不适用(无分区) |
  | 幂等去重 Seen | ✅(ConsumerProgressStore) | ✅(**本期补**) | ✅(**本期补**) |
  | 毒消息处理 | ✅落本地DLQ | ✅Nack→DLX | ⚠️→✅(**本期修复**) |
- 本次补全：

### 3.29 熔断打开时的生产者语义对齐 + 修复 RocketMQ 指标双重计数（续 3.28）
- 背景：3.28 已完成三队列「熔断保护 / 消费去重 / 毒消息」的能力对齐。本轮复审发现两处仍需补全的真实问题：
  - #D 熔断打开语义三队列不一致：Kafka 在熔断打开时把消息 `requeue`（留在内存队列等 broker 恢复，避免无谓落本地 DLQ 与依赖 30s replay 的额外延迟）；而 RabbitMQ / RocketMQ 旧实现把「熔断打开」与「真实发送失败」一视同仁，直接降级本地 DLQ——broker 短暂抖动期会疯狂写盘、且恢复须等下一轮 replay 才补发（延迟高、抖动明显）。
  - #E RocketMQ 生产者 `recordSend` 双重计数：`sendOne` 与 helper `sendSyncMsg` 各自 `recordSend`，每条消息成功/失败各记 2 次，发送成功率指标虚高约 2 倍（Kafka / RabbitMQ 无此问题）。
- 本次补全：
  - 抽出共享判定 `isBreakerOpen(err)`（`kafka.go`）：仅 `errBreakerOpen` 哨兵与 `gobreaker.ErrOpenState` / `gobreaker.ErrTooManyRequests` 视为「熔断打开」；nil 与普通错误均不算。三队列生产者统一据此分流。
  - #D 三队列主发送路径对齐为 `requeue`：RabbitMQ / RocketMQ 生产者 `sendOne` 在熔断打开时**返回该错误、不降级 DLQ**；主 loop / worker 捕获到 `isBreakerOpen` 后 `requeue`（带回退退避 + 队列满时降级 DLQ，与 Kafka `requeue` 同参 `requeueBackoff` / `errProducerOverflow`）。溢出池与关闭排空路径无「等待恢复」语义，仍直接降级 DLQ（与 Kafka 溢出路径一致）。新增 `requeue` / `fallbackToDLQ` 方法（两队列各一份，逻辑与 Kafka 对齐）。
  - #E 修复 RocketMQ 双重计数：删除 `sendOne` 内两处 `recordSend`，发送计数统一由 `sendSyncMsg`（被 `sendOne` / `SendSync` / `relay` 共用）记一次。熔断打开时 `sendSyncMsg` 不会被调用，故不计发送（与 Kafka 一致：熔断打开不计为一次发送尝试）。
  - 顺带修复 Kafka `loop` 潜在死循环：旧实现 `sendOne` 对**任何** error 都 `requeue`，marshal 错误（不可重试）会无限重入队列。改为仅 `isBreakerOpen` 时 `requeue`，marshal 错误直接丢弃（仅错误日志），消除死循环。
- 三队列生产者「熔断打开」行为最终对齐：

  | 路径 | Kafka | RabbitMQ | RocketMQ |
  |---|---|---|---|
  | 主 loop / worker 遇熔断打开 | requeue（等恢复） | requeue（等恢复） | requeue（等恢复） |
  | 溢出池遇熔断打开 | 降级 DLQ | 降级 DLQ | 降级 DLQ |
  | 关闭排空遇熔断打开 | 降级 DLQ | 降级 DLQ | 降级 DLQ |
  | 真实失败 | 降级 DLQ | 降级 DLQ | 降级 DLQ（单计数） |
  | 熔断打开是否记发送计数 | 否 | 否 | 否（修复前：是×2） |

### 3.30 消费侧本地重试对齐 + 生产者指标/降级口径一致性补全（续 3.29）
- 背景：3.28/3.29 已完成熔断保护、消费去重、毒消息、熔断打开语义、RocketMQ 双重计数的对齐。本轮复审发现消费侧与生产者指标口径仍有 4 处需补全的一致性问题：
  - #1 RocketMQ 消费者缺「本地重试」层：Kafka 消费者（`process` 内指数退避重试后落本地 DLQ）、RabbitMQ 消费者（`retryProcess` 本地重试后 Nack→broker DLX）都有本地重试兜底，唯独 RocketMQ 消费者把**任何** handler 失败直接返回 `ConsumeRetryLater` 交给 broker `%RETRY%`——瞬时错误（DB 抖动、下游超时）也走一轮 broker 往返，既慢又加重 broker 重试压力。
  - #2 RabbitMQ 异步 `sendOne` 把 marshal 错误计为发送失败：Kafka/RocketMQ 异步 `sendOne` 在 marshal 失败时**早于** `recordSend` 返回（不计发送），且三队列 `SendSync` 路径 marshal 失败亦直接返回不计数。RabbitMQ 是唯一把「生产者侧序列化错误」计入「发送成功/失败」指标的，口径不一致。
  - #3 Kafka 溢出路径对 marshal 错误落 DLQ：`sendOne` 仅 marshal / 熔断打开返回非 nil；旧溢出路径对**任何**非 nil 都 `fallbackToDLQ`——marshal 属于不可补发的极端错误（replay 时 `toKafkaMessage` 仍会失败），落盘只会占用 replay 轮询，永不可补发。
  - #4 `consumerRetryOf` 注释过时：仍写「rocketmq 交由服务端重试，不使用此处参数」，与现状（rocketmq 已走顶层 `cfg.Consumer` 取参）不符，且 #1 修复后 RocketMQ 将正式复用该参数。

- 本次补全：
  - #1 RocketMQ 消费者补齐本地重试：`handleMessages` 对每条消息先用 `retryProcess(ctx, &msg, handler, consumerRetryOf(r.cfg))` 就地指数退避重试；仅当本地重试耗尽才返回 `ConsumeRetryLater` 交 broker `%RETRY%/%DLQ%` 兜底。毒消息（unmarshal 失败）仍在本地重试之前直接 `ConsumeRetryLater`（broker 最终进 `%DLQ%`，与 3.28 的修复一致）。这样三队列消费侧均为「本地重试 → 各自降级（Kafka 本地 DLQ / RabbitMQ broker DLX / RocketMQ broker %RETRY%）」两层结构，语义对齐。
  - #2 RabbitMQ 异步 `sendOne` 的 marshal 分支去掉 `recordSend`，仅保留错误日志；指标口径与 Kafka/RocketMQ 异步路径及所有 `SendSync` 路径一致（marshal 不计发送）。
  - #3 Kafka `Send` 溢出路径改为仅 `isBreakerOpen(err)` 时 `fallbackToDLQ`，与 RabbitMQ/RocketMQ 溢出路径（都 `isBreakerOpen` 判断）对齐；marshal 等不可补发错误直接丢弃（其错误日志已在 `sendOne` 内打印）。
  - #4 更正 `consumerRetryOf` 注释：明确三队列消费侧都先本地重试、再各自降级，本函数即提供统一的「本地重试次数 + 退避上下界」；kafka 消费者自身内联同语义、仅供其它类型复用同一口径。

- 三队列消费侧「重试/死信」最终结构对齐：

  | 维度 | Kafka | RabbitMQ | RocketMQ |
  |---|---|---|---|
  | 本地重试（指数退避） | ✅ process | ✅ retryProcess | ✅ retryProcess（本轮新增） |
  | 本地重试耗尽后降级 | 本地文件 DLQ | broker DLX（Nack） | broker %RETRY%/%DLQ% |
  | 毒消息 | 本地 DLQ + 推进 offset | broker DLX | broker %RETRY%→%DLQ% |
  | 消费侧幂等去重 Seen | ✅（SQL store） | ✅（SQL store） | ✅（SQL store） |
  | 本地重试参数来源 | mq.kafka.consumer.* | mq.consumer.*（回退 kafka） | mq.consumer.*（回退 kafka） |

- 验证：`go build` / `go vet` / `gofmt` 通过；`internal/mq` 全套（含 `-race`）通过，本轮新增 2 个用例（`TestRocketMQConsumer_LocalRetryThenSuccess`、`TestRocketMQConsumer_LocalRetryExhaustedReturnsRetryLater`）全绿。

### 3.31 RocketMQ DLQ 补发计数对齐 + errProducerOverflow 通用化（续 3.30）
- 背景：3.30 完成消费侧本地重试与生产者指标口径对齐后，复审 DLQ replay（`relay`）补发路径与共享哨兵，发现两处仍需补全：
  - #A RocketMQ `relay` replay 失败被计入「发送失败」指标：`relay` 复用 `sendSyncMsg`（成功/失败都 `recordSend`），而 Kafka / RabbitMQ 的 `relay` 仅成功计 `success`、失败不计。broker 持续不可达时每 30s replay 一批 DLQ，RocketMQ 会把每条补发失败计为发送失败，发送失败率虚高（Kafka / RabbitMQ 无此问题）。
  - #B `errProducerOverflow` 错误信息写死 "kafka producer: queue full..."：该哨兵被三队列生产者共用（Kafka / RabbitMQ / RocketMQ 的 `requeue` 队列满降级与 `Send` 溢出池打满降级都用），在 RabbitMQ / RocketMQ 的降级日志里出现 "kafka producer" 字样明显错。

- 本次补全：
  - #A 拆分 RocketMQ 生产者底层发送：抽出 `sendSyncRaw(ctx, m)`（不记指标，breaker 由调用方包裹），`sendSyncMsg`（正常发送路径，成功/失败各记一次）改为复用 `sendSyncRaw` + `recordSend`；`relay` 改用 `sendSyncRaw`，仅补发成功时 `recordSend(success)`、失败不计——对齐 Kafka / RabbitMQ 的 `relay` 计数口径（补发是「历史失败消息的重试」而非「一次新的发送尝试」，且该失败已由先前的 `recordDLQ` 计数）。`sendOne` / `SendSync` 仍走 `sendSyncMsg`，正常发送计数不变。
  - #B `errProducerOverflow` 错误信息改为通用 "mq producer: queue full and overflow workers saturated"，三队列共用时不再误显示 "kafka producer"。

- 三队列 `relay`（DLQ 补发）计数口径最终对齐：

  | 路径 | Kafka | RabbitMQ | RocketMQ |
  |---|---|---|---|
  | 补发成功 | recordSend(success) | recordSend(success) | recordSend(success) |
  | 补发失败 | 不计 | 不计 | 不计（#A 修复前：计 failure） |
  | 熔断打开（补发短路） | 不计 | 不计 | 不计 |

- 验证：`go build` / `go vet` / `gofmt` 通过；`internal/mq` 全套（含 `-race`）通过，本轮新增 1 个用例（`TestRocketMQProducer_RelayCountsAlignedWithKafkaRabbit`）全绿。

### 3.39 消费侧 handler panic 直接拖垮进程（本次会话，源于启动 WARN/消费协程排查）
- 背景：排查 memory MQ 告警与消费启动流程时，发现所有 MQ 适配器的消息处理协程都缺少 panic 兜底。`internal/mq/retry.go` 的 `retryProcess`（memory / rabbitmq / rocketmq 三套适配器共用的重试层）只捕获 `error`、不捕获 panic；而 `memoryConsumer.Subscribe`（`memory.go:136`）与 `kafkaConsumer.process`（`kafka_consumer.go:388`）起的处理 goroutine 也都没有 `recover()`。Go 语义下，任何一条消息的 handler 发生 panic（如 `Payload` 类型断言失败、nil 解引用），都会直接从消费协程上抛、拖死整个进程——这是「dev/生产跑着跑着突然崩、且堆栈指向消费链路」的典型根因，且 kafka 模式同样存在（此前 `## 三` 其它小节加固过关闭/取消/DLQ，但漏了 panic 兜底）。
- 根因：消费重试层与具体适配器都把 handler 当成「只返回 error」的契约，忽略了 handler 内部可能 panic；没有在调用点做 `recover()` 兜底，导致单条毒消息/异常消息即可击穿进程。
- 改动（运行期行为更稳健，且不改变正常成功/可重试失败路径的既有语义）：
  1. `mq/retry.go`：新增包级 sentinel `errHandlerPanic` 与公共辅助 `callHandlerSafe(ctx, msg, handler)`——内部 `defer recover()` 将 handler 的 panic 转成 `fmt.Errorf("%w: %v", errHandlerPanic, r)` 返回。`retryProcess` 改用 `callHandlerSafe` 调用 handler；当返回的错误 `errors.Is(err, errHandlerPanic)` 时**直接当失败返回、不重试**（panic 通常是确定性 bug，重试无意义、还可能重复执行带副作用的逻辑）。memory / rabbitmq / rocketmq 三套适配器经此一处改动即全部受益。
  2. `mq/kafka_consumer.go`：Kafka 有自己的 `process`（未走 `retryProcess`），同样改用 `callHandlerSafe`；panic 转 error 后 `errors.Is(err, errHandlerPanic)` 为真时 `goto dlq` 直接落 DLQ（不重试），与 Kafka 既有「失败→DLQ」语义一致，且进程不再崩溃。
- 单测：
  - `mq/retry_test.go`：`TestRetryProcess_PanicRecovered` 验证 handler panic 被 `retryProcess` 转成 `errHandlerPanic` 包装的错误返回、`errors.Is` 可识别、且**不重试**（handler 仅执行 1 次）、调用 goroutine 不崩。
  - `mq/kafka_consumer_test.go`：`TestProcess_PanicGoesToDLQ` 验证 Kafka `process` 在 handler panic 时不外泄（`recover` 捕获），且消息被捕获进 DLQ（DLQ 记录携带 `handler panic` 字样）。
  - `mq/memory_test.go`：`TestMemoryMQ_PanicHandlerDoesNotCrash` 端到端验证 memory 模式下，handler panic 不会拖垮订阅 goroutine——先发 panic 消息、再发正常消息，consumer 仍存活并处理了正常消息（`normal` 计数达到 1）。
- 收益：从根上消除「单条消息 handler panic 拖垮整个 MQ 消费进程」的可用性风险，四套适配器（memory / kafka / rabbitmq / rocketmq）一致受保护；失败时仍按各自既有策略（日志 / Nack / DLQ）处理，无行为回退。
- 验证：`gofmt -w` / `go build ./...` / `go vet ./internal/mq/...` 全绿；`go test ./internal/mq/...` 全过（三处新增 panic 测试 `-v` 均 PASS）。

### 3.41 GORM 三个 repo 写路径 nil 指针防御（§3.40 待办①，本轮"持续分析优化"方向1 续作）

### 3.42 ES bulk 逐条失败聚合 + 单条失败跳过；bootstrap fallback 连接泄漏修复（§3.40 待办①②③）
- 背景（§3.40 待办三条，本轮收口）：
  - ① bulk 逐条失败被吞：ES `CreateBatch` 只查 `res.IsError()`（传输层 HTTP 状态）。当 ES 返回 HTTP 200 但个别文档因 mapping 冲突 / 版本冲突等失败时，响应体 `errors=true` 且 `items[].error` 带详情，`IsError()` 为 false 被静默吞掉——脏数据写入失败却上报成功，监控/审计面出现「假成功」。注：§3.40 待办误标为「CH `RecordBatch`」，但 CH 走原生 `batch.Send()`（整批单错误、无 items 语义），该隐患实际只存在于 ES `CreateBatch`。
  - ② fallback 连接泄漏：bootstrap 的 `InitDatabases` 在 CH/ES/MongoDB 连接失败（或 CH 已连上但 `EnsureTable` 失败）回退 SQLite 时，局部 `chAdapter`/`esAdapter`/`mongoAdapter` 从未 `Close()`。若 `Connect` 半成功已建连、或 CH `EnsureTable` 失败分支回退，原连接逃逸泄漏。
  - ③ 单条 marshal 失败拖垮整批：ES `CreateBatch` 任一条 `json.Marshal` 失败即 `return` 整个批量，其余正常日志被全部丢弃。
- 根因：① 用传输层错误码代替了 bulk 语义（ES bulk 的成功是「请求成功」而非「文档成功」）；②③ 回退/fallback 路径缺少「释放已分配资源」的对称收尾（与 §3.40 资源泄漏同源）。
- 改动（运行期更正确、更稳健，正常路径语义不变）：
  1. `internal/repository/log_repo_es.go`：

     - 抽出 `aggregateBulkErrors(body io.Reader) error`：解码 bulk 响应体，若 `errors=true` 则遍历 `items[].error` 聚合成单条 error（含 action/status/type/reason）返回；`errors=false` 返回 nil；非法 JSON 返回 decode 错误。
     - `CreateBatch` 在 `res.IsError()`（传输层）之后调用 `aggregateBulkErrors(res.Body)`，覆盖 HTTP 200 下的逐条失败（待办①）。

  2. `internal/bootstrap/bootstrap.go`：CH/ES/MongoDB 三处 fallback 分支补 `adapter.Close()`（用 `_ =` 忽略关闭错误，避免掩盖原 fallback 原因）：

     - ES `Connect` 失败分支；
     - MongoDB `Connect` 失败分支。
     - 三 adapter 的 `Close()` 均对「未连接（conn/client 为 nil）」安全返回，故半成功未建连时调用亦无害。

  - `internal/repository/log_repo_es_test.go`：`TestAggregateBulkErrors` 直接喂入 bulk 响应 JSON 验证三情形——全成功返回 nil、部分失败聚合为 `(1/2)` 错误、非法 JSON 返回 decode 错误（无需真实 ES）。

- 收益：① 消除「ES 写入假成功」——逐条失败现被正确上报，监控/审计数据可靠性提升；③ 单条坏日志不再连累整批；② 关闭回退路径的连接泄漏，与 §3.40 `Databases.Close`/探活协程收口形成完整资源生命周期闭环。

### 3.47 修复：scheduler 定时任务因「nil 底层指针接口」陷阱 panic

#### 故障现象
```
ERROR scheduler/scheduler.go:159 [scheduler] job "idle-timeout-scan" panic recovered:
runtime error: invalid memory address or nil pointer dereference
... sync/atomic.(*Int32).Add ← sync.(*RWMutex).RLock ← cluster.(*LeaderElector).IsLeader
    leader.go:117 ← bootstrap.idleTimeoutScan (app.go:510) ← initScheduler (app.go:551)
```
`scheduler.exec` 自带 `recover`（§3.39），故仅单任务报错、未击垮进程，但 `idle-timeout-scan` / `daily-task-reset` / `weekly-task-reset` / `event-dedup-cleanup` 四个「选主门控」任务在**未启用选主**环境下全部无法正常执行。

#### 根因：Go 接口 nil 陷阱
- `App.leader` 字段为具体类型 `*cluster.LeaderElector`（`app.go:62`），在 `Idle.LeaderElection.Enabled==false` 或 L2 不可用降级分支（`app.go:430-431`）中**未赋值**，保持零值 `nil` 指针。
- 调用处 `idleTimeoutScan(ctx, a.idleSvc, a.leader)`（`app.go:551`）把该 `nil` 指针直接传给参数 `leader leaderElector`（接口类型）。Go 中 `(*LeaderElector)(nil)` 赋给接口后**接口非空**（携带 `*LeaderElector` 类型信息）、底层指针为 `nil`。
- 于是 `idleTimeoutScan` 内 `leader != nil` 误判为 `true`，随即调用 `leader.IsLeader()`；方法接收者 `e` 为 `nil` 指针，访问 `e.mu.RLock()`（值类型字段）触发 `atomic.Int32.Add` 踩 nil → panic。

#### 修复（两层）
1. **调用方（根因）**：`initScheduler` 开头定义局部 `var le leaderElector`，**仅当 `a.leader != nil` 时才 `le = a.leader`**，否则保持真正的 `nil` 接口；四个闭包调用点（`idle-timeout-scan` / `daily-task-reset` / `weekly-task-reset` / `event-dedup-cleanup`）改用 `le`。这样未启用选主时传入的是真 `nil` 接口，`leader != nil` 正确早退/执行判定。
2. **纵深防御（接口方法 nil 守卫）**：`LeaderElector.IsLeader()` 加 `if e == nil { return true }` 守卫，无选主（接收者 nil）语义等价于「无选主约束、各 Pod 正常执行」，即使再有 nil 底层指针接口路径也不会 panic（与 §3.40 不可信配置、§3.46 密钥断言同属「非空底层 nil」一类防御）。

#### 测试
- 新增 `TestSchedulerLeader_NilUnderlyingPointer`（`bootstrap_test.go`）：直接以 `var nilLE *cluster.LeaderElector` 构造 nil 底层指针接口，分别传入 `idleTimeoutScan` / `resetPeriodIfLeader` / `cleanupDedupIfLeader`，断言**不 panic 且正常执行**（n==count / resetCalls==1 / dedupCalls==1）。该用例在修复前会因 `IsLeader` 踩 nil 而 panic，是有效回归测试。
- 既有 `TestIdleTimeoutScan_Gating` / `TestResetPeriodIfLeader_Gating` / `TestCleanupDedupIfLeader_Gating` 仍全绿。

### 3.48 修复：idle-settle 压测 p99=15.47s 长尾（请求缺超时 → DB 连接池等待无限挂起）

#### 故障现象（make k6-test-idle-settle）
- 全部请求成功：`http_req_failed=0.00%`、`idle_settle_ok=99.99%`、`settle status is 200` 通过。
- 唯一失败阈值：`http_req_duration` 的 `p(99)<3000`，实测 **p(99)=15.47s**（中位 20ms、p90 179ms、p95 853ms、max 19.43s）。
- 形态：p50→p90→p95 温和抬升、p95→p99 陡增 18×，属典型「资源池饱和 → 队列等待」长尾。

#### 根因（代码层）
1. **请求全程无超时兜底**：`router.Setup`（`router.go:21`）的全局中间件链（Recovery/Trace/RequestInfo/RequestLogger/CORS/Metrics）**没有请求超时**，gin 亦无默认请求超时（handler 搜 "timeout" 0 命中）。
2. **`ctx` 被透传到 DB 等待**：`IdleService.settleSession`（`idle_service.go:534`）把请求 `ctx` 传给 `businessDB.Transaction(ctx,…)`、`GetDailyPoints(ctx,…)`、`userRepo.UpdatePoints(ctx,…)`（经 `applyAsync→tryApply`，`points_outbox.go:53/58`）。
3. **连接池饱和 → 无限等待**：`max_open_conns` 默认 100（`mysql.go:48`/`postgres.go:43`）。500 VU（SETTLE_DELAY=1s → ~250 结算/s + ~250 start/s）下，每个 settle 串行占用 businessDB（读+事务3 语句+Claim）+ userDB（UpdatePoints）连接；一旦峰值并发超过池容量，`database/sql` 会让新请求**无限等待空闲连接**。因 ctx 无 deadline，该等待**无上界** → 出现 15–19s 长尾（仅顶端 ~1% 命中，与 p99 形态吻合）。
4. **非 MQ 阻塞**：已核 `KafkaProducer.Send`（`kafka.go:138`）为异步入队（`select{case p.queue<-msg:return}`），`WriteTimeout` 仅作用于后台写 goroutine，不阻塞调用方；`emitIdleSettled` 不会拖慢请求（排除误改）。`GetDailyPoints` 热路径是 O(1) Redis，仅冷启动/Redis 故障才回退 DB SUM。

#### 修复（请求超时中间件）
- 新增 `middleware/timeout.go` 的 `Timeout(cfg)`：为 `c.Request` 的 ctx 注入 `context.WithTimeout`（默认 10s，可经 `server.request_timeout` 配置）。
- 机理：`database/sql` 在等待连接池时会监听 ctx，deadline 到达即取消等待并返回 `context.DeadlineExceeded`——把「连接池饱和 → 无限挂起」的 15–19s 悬崖**收敛为有界 504**。采用同 goroutine 执行 `c.Next()`（非独立 goroutine），确保前序 `Recovery` 仍能在同一调用栈捕获 panic，不引入逃逸协程崩溃风险。
- 仅在「确因超时中断且尚未写响应」时回 504（`ctx.Err()==DeadlineExceeded && !c.Writer.Written()`），不覆盖 handler 已正常写回的响应。
- `ServerConfig` 新增 `RequestTimeout time.Duration`（`mapstructure:"request_timeout"`）；`router.go` 在 `Recovery` 之后、其余中间件之前 `r.Use(middleware.Timeout(cfg))`。
- `model` 新增 `CodeGatewayTimeout=10705`（"请求处理超时"），经 `response.ErrorWithHTTPStatus(c,504,…)` 返回。
- 测试 `middleware/timeout_test.go`：慢 handler（模拟 ctx 取消的 DB 等待）→ 504；快 handler / 零配置默认兜底 → 200。

#### 配套（运维侧，k6 脚本注释已点明）
- 该阈值 `p(99)<3000` 本就是「结算事务合理量级」的**告警线**；远超此值说明 **DB/锁成为瓶颈，需查慢查询或扩容**（`idle_settle.js:45-46`）。
- **请求超时是「防无限挂起」的安全网**，要让 p99 真正 <3s，还需：① 把 `database.business.max_open_conns` / `database.user.max_open_conns` 按 500 VU 并发（每 settle 短暂占用 ~2–3 条连接）上调（如 200–300）；② 确保 L2(Redis) 在线，使 `GetDailyPoints` 维持 O(1) 而非回退 DB SUM；③ **[已落地] 把 `applyAsync` 的同步 `userDB.UpdatePoints` 改为有界 goroutine 异步**（见下「修复 3」，outbox+relay 已保证最终一致）。

### 3.49 深层代码优化：消除 TOCTOU 竞态、N+1 批量 UPDATE、Context 传播与空闲连接回收

以下优化基于对全仓库层（repository）与服务层的深度分析，聚焦并发安全性、DB 往返次数、链路追踪与连接池健康。

#### 3.49.1 消除 TOCTOU 竞态：`IncrProgress` 与 `UpsertProgress`

**问题**：`task_repo.go` 中 `IncrProgress`（原 L151-175）和 `UpsertProgress`（原 L122-134）均采用「先读后写」模式——先 `FindProgress` 查出现有行，再 `Save` 回写。多个并发请求可能读到相同的 `existing`，导致进度覆盖或丢失。

**修复**：
- `UpsertProgress`：改用 `clause.OnConflict` 原子 upsert（`DoUpdates`），利用已有 `uniqueIndex idx_user_task_period` 消除竞态，同时移除 `db.UseMaster` 回调（OnConflict 本身就是写操作，走主库）。
- `IncrProgress`：分两步原子操作：
  1. `INSERT ... ON CONFLICT DO NOTHING` 确保行存在（幂等）；
  2. `UPDATE SET current_progress = current_progress + ?` 原子累加，`CASE WHEN` 在达到 target 时同步标记 `is_completed`/`completed_at`。`WHERE is_claimed = false` 防止已领取行被错误累加。

**影响**：`UpsertProgress` 从 2 次 DB 往返（读+写）降为 1 次；`IncrProgress` 从 2 次降为 2 次（但消除了读-写间的竞态窗口）。

#### 3.49.2 消除事务内 N 次 UPDATE：`BatchUpdateHeartbeat`

**问题**：`idle_repo.go` 中 `BatchUpdateHeartbeat`（原 L334-355）在单事务内逐条 `UPDATE`，N 条心跳数据产生 N 次网络往返。虽已在事务内，但每次 `UPDATE` 仍是一次独立的客户端-服务器交互。

**修复**：改为单条 SQL 使用 `CASE WHEN` 批量更新：
```sql
UPDATE idle_records SET
  last_heartbeat_at = CASE WHEN (user_id=? AND device_id=?) THEN ? ... ELSE last_heartbeat_at END,
  updated_at = ?
WHERE (user_id=? AND device_id=? AND status='active') OR ...
```
**影响**：N 次网络往返降为 1 次，对大批量心跳聚合场景（高并发设备数）改善显著。

#### 3.49.3 修复 Context 传播缺失：`AppendOutboxInTx` / `AppendInTx`

**问题**：`points_outbox.go:57` 和 `points_outbox_repo.go:30` 的 `AppendOutboxInTx` / `AppendInTx` 使用 `tx.WithContext(context.Background())` 覆盖了 `tx` 原有的调用方 ctx，导致：
- 链路追踪（trace_id）在 outbox INSERT 这段丢失；
- 无法通过 ctx 超时/取消来控制事务内操作。

**修复**：直接使用 `tx.Create(rec)`，`tx` 已由 `businessDB.Transaction(ctx, fn)` 携带调用方 ctx，无需额外 `WithContext`。

#### 3.49.4 添加空闲连接回收：`ConnMaxIdleTime`

**问题**：`mysql.go` 和 `postgres.go` 的适配器仅设置了 `SetMaxIdleConns`、`SetMaxOpenConns`、`SetConnMaxLifetime`，未设置 `SetConnMaxIdleTime`（Go 1.15+）。空闲连接可能永久占用连接池，尤其在流量波谷后，积压的空闲连接不会释放。

**修复**：在 `WithMySQLPool` / `WithPostgreSQLPool` 中增加 `connMaxIdleTime` 字段，默认 5 分钟；`Connect` 中调用 `sqlDB.SetConnMaxIdleTime()`。

**影响**：流量波谷后自动释放空闲连接，避免连接池被无效连接占满。

- `go build ./...`：BUILD:0
- `go test ./...`：全量 PASS（含 `repository`、`service`、`db` 等所有受影响包）
- `golangci-lint`：无新增问题

### 3.50 消除 N+1 查询：Task 进度批量查、Status 心跳批量查、evict 冗余查询

#### 3.50.1 `task_service.go` List / Progress 的 N+1

**问题**：`List` 和 `Progress` 先调用 `FindAll` 获取所有任务，再对每个任务逐一调用 `FindProgress`。7 个任务产生 1+7=8 次 DB 查询。

#### 3.50.2 `idle_service.go` Status 的 N+1 Redis 调用

### 3.54 Kafka 订阅分区查询失败的韧性收口（收口 §6.5 #7，本轮）

- 背景（§6.5 #7 已知限制）：无消费组模式下 `Subscribe` 逐 topic 调 `partitions()` 查询分区，任一 topic 查询失败（topic 未创建 / broker 未开 `auto.create.topics.enable` / 首节点瞬时不可达）即 `return err`，整个消费端启动失败——不及消费组「部分 topic 就绪也能跑」的韧性，一个 topic 缺失会拖垮全部订阅。

  - **零 reader 兜底**：韧性模式下若【全部】 topic 都失败（`len(readers)==0`），仍返回错误（`errors.Join` 聚合各 topic 失败原因），避免「订阅静默成功却什么都不消费」的隐蔽故障；另兼顾「多实例分区分配后本实例恰好未分到分区（`instance_count` > 分区总数）」也明确报错而非空转。
- 与现有能力的关系：跳过的 topic 需重启（或后续 P2 分区扩容热感知落地后）再生效；本改动只解决「部分 topic 未就绪不应拖垮整体启动」这一层韧性。
- 配置：`config/config.yaml` 与 `config/config.example.yaml` 的 `mq.kafka.consumer` 段补 `partition_fetch_strict: false`（含注释）。
- 测试（新增 `internal/mq/kafka_consumer_resilience_test.go`，白盒、指向不可达 broker + 短超时 ctx，无需真实 Kafka）：`TestSubscribe_StrictFailFast`（严格模式任一失败即报 `read partitions for topic`）、`TestSubscribe_ResilientAllFail`（韧性模式全部失败仍报 `nothing to consume`）。

### 3.63 Kafka 无消费组多实例分区分配：越界配置在启动/热更新期拦截（加固 §3.53 / §6.5 #1，本轮）

### 3.64 `emitIdleSettledAsync` 派生 ctx 被提前取消（真实 bug，本轮）

- 背景：`IdleService.emitIdleSettledAsync` 在后台 goroutine 发布 `idle.settled` 事件，注释意图「用 `context.Background()` 派生的『带超时』ctx，避免请求 ctx 在发布完成前被取消」。旧实现为：
  ```go
  dctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
  defer cancel()          // ← 在【外部函数】 emitIdleSettledAsync 内
  go s.emitIdleSettled(dctx, rec)  // go 不阻塞，外部函数立即返回
  ```
  由于 `go` 语句不阻塞，`emitIdleSettledAsync` 在启动 goroutine 后**立即返回**，`defer cancel()` 随即执行 → `dctx` 在 `emitIdleSettled` 运行之前就已被取消。整段「5s 超时」语义被**彻底架空**。
- 后果（高严重度）：`mq.Producer.Send` 链路对 ctx 的响应因后端而异：
  - **RabbitMQ**：`Send` 的确认等待 `select { case <-rc.confirms: case <-confCtx.Done(): }` 中 `confCtx` 由 `ctxWithTimeoutIfUnset(dctx, …)` 派生——`dctx` 已取消（无 deadline）会派生一个**继承取消态**的子 ctx，`confCtx.Done()` 立即就绪，`Send` 立即返回 error → **idle.settled 事件几乎必然丢失**（结算事件不发布，依赖其触发下游的积分/通知链路断流）。
  - **Kafka 异步**：`Send` 入队不读 ctx，故不直接失败；但「5s 超时」设计意图同样落空，且若未来 Kafka 路径引入 ctx 检查将同遭影响。
  - `mq.Producer` 的 `Send` 失败在 `emitIdleSettled` 中被 `_ = err` 吞掉（事件为 best-effort），故线上**无报错、静默丢事件**，极难察觉。
- 修复（零新增依赖，与 `points_outbox.go` 的 `applyAsync` 正确模式对齐）：把 `cancel` 移入 goroutine，使其仅在 `emitIdleSettled` 完成后执行：
  ```go
  dctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
  go func() {
      defer cancel() // cancel 必须在 goroutine 内（emitIdleSettled 完成后）执行
      s.emitIdleSettled(dctx, rec)
  }()
  ```
  `ctxWithTimeoutIfUnset` 对已带截止的 `dctx` 会原样透传（返回 `cancel=noop`），不影响；`dctx` 的 5s 超时定时器在 goroutine 结束（`cancel`）后才释放，无泄漏。
- 测试：`internal/service/idle_service_async_test.go` 新增 `TestEmitIdleSettledAsync_ContextNotPrematurelyCancelled`：用 `ctxCapturingProducer`（实现的 `Send` 把 `ctx.Err()` 写入通道）注入 `IdleService.publisher`，调用 `emitIdleSettledAsync` 后断言 `Send` 收到的 ctx **未取消**（`err == nil`）。**已验证该测试对旧 bug 版确定性失败**（临时还原 `defer cancel()` 在外部函数 → 测试报 `context canceled`），修复后通过，确为有效守卫而非恒成立。
- 验证：`gofmt -w` / `go build ./...` / `go vet ./internal/service/...` 全绿；`go test ./internal/service/... -run TestEmitIdleSettledAsync_ContextNotPrematurelyCancelled -race -count=1` PASS。

### 3.65 `memoryAccountLockStore` 清理协程永久泄漏（真实 bug，本轮）

- 背景：`service.NewMemoryAccountLockStore()` 启动一个后台 `go s.cleanup()` 周期性清理过期失败计数条目。旧 `cleanup()` 是 `for range tick.C { ... }`——`tick.C` 关闭后 `range` 才退出，但**没有任何代码调用 `tick.Stop()` 或向协程发停止信号**，故该协程**永不退出**：
  - **测试**：`account_lock_test.go` 每次执行都 `NewMemoryAccountLockStore()` 一次，泄漏一个 goroutine（多轮/子测试累积）；

- 修复（零新增依赖）：
  - `NewMemoryAccountLockStore(ctx context.Context)` 改为接收生命周期 ctx；`cleanup(ctx)` 的循环改为 `select { case <-ctx.Done(): return; case <-tick.C: ... }`，ctx 取消即 `return`（配合 `defer tick.Stop()` 释放定时器），协程干净退出。
  - `bootstrap.App.initLockStore(ctx)` / `initAuthService(ctx, ...)` 透传启动期的 `bgCtx`（来自 `initServices(bgCtx)`），使 Redis 不可用回退时清理协程随优雅关闭一并停止，与既有后台协程生命周期对齐。
  - `AccountLockStore` 接口签名不变（Redis 实现 `a.cacheMgr` 不受影响），仅具体构造器入参增加 ctx。
- 测试：

### 3.66 注册确认邮件 goroutine 缺 recover / 无超时（真实健壮性+资源 bug，本轮）

- 背景：`AuthService.sendRegisterConfirmation` 在后台 `go func()` 中异步发送注册确认邮件（best-effort，不阻塞注册）。旧实现有三处薄弱点：
  1. **无 `recover`**：若 `s.mailer.Send`（或 `mail.BuildConfirmRegisterHTML`）panic，未捕获的 panic 会**直接终止整个进程**——仅因一封注册确认邮件就拖垮认证服务（及其它所有 HTTP 请求）。这是后台 fire-and-forget goroutine 的典型隐患。
  2. **`Send` 使用 `context.Background()` 无超时**：SMTP 服务器挂起/网络分区时，`Send` 阻塞不退，goroutine **永久泄漏且占用一条 SMTP 连接**；注册洪峰下累积内存与连接，逐步拖垮进程。

- 修复（零新增依赖）：
  - 在启动 goroutine **前**捕获 `siteName := s.cfg.Get().Mail.SiteName`，goroutine 内只读已被捕获的局部变量，消除配置热加载竞态与潜在 nil 解引用；
  - goroutine 入口加 `defer func(){ if r := recover(); r != nil { log.Printf(...) } }()`，任何 panic 仅告警、绝不击垮进程；
  - `Send` 改用 `sendCtx, cancel := context.WithTimeout(context.Background(), registerMailSendTimeout)`（新增常量 `registerMailSendTimeout = 10s`，与 `googleHTTPClient` 一致），`defer cancel()` 保证超时后释放——SMTP 挂起时 goroutine 在 10s 内退出，不再永久泄漏。

- 验证：`gofmt -w` / `go build ./...` / `go vet ./...` 全绿；`go test ./internal/service/... -run TestSendRegisterConfirmation -race -count=1` PASS，`go test ./internal/service/... -race -count=1` 整体 ok。

## 五、DecodeCached 还原语义（修复后）

`cacheMgr.Get` 返回的 `interface{}` 动态类型随路径不同：

| 路径 | 动态类型 |
|------|----------|
| 未命中、回源直返 | 原始 Go 类型（`*model.X` / `[]model.X`） |

## 六、遗留问题（需设计评审，暂未改）

### 6.1 跨库一致性：兑换 / 结算 / 领取的积分更新在事务外（S1，高优先级） ✅ 已修复

- 现象：
  - `shop_service.Redeem`：在 `businessDB` 事务内完成"扣库存 + 建订单 + 写积分流水"，事务**提交后**才调用 `userRepo.UpdatePoints(ctx, userID, -totalPoints)`（位于 `userDB`，MongoDB/SQLite），**不在同一事务**。
  - `idle_service.settleSession`：在 `businessDB` 事务写积分流水，**提交后**才 `userRepo.UpdatePoints`（事务外）。
  - `task_service` 领取奖励同理（`businessDB` 事务标记领取 + 写流水，提交后更新 `userDB` 余额）。
- 风险：若 `businessDB` 事务已提交、但 `userDB.UpdatePoints` 失败（网络抖动 / 超时），则出现不一致：
  - 兑换：库存已扣、订单已建、流水已写，但用户积分**未扣** → 用户白嫖或积分透支。
  - 结算：积分流水已落 `businessDB`，但用户余额**未加** → 用户"应得奖励"丢失。
- 根因：积分余额（userDB）与业务流水（businessDB）分属两个存储，无法用单机 ACID 事务保证原子。
- 实现（Transactional Outbox，已落地）：
  1. 新增 `points_outbox` 表（`model.PointsOutbox` + `repository.PointsOutboxRepository` + mysql/sqlite/postgres 迁移）。
  2. `Redeem` / `settleSession` / `Claim` 在各自 `businessDB` 事务内**同提交**一条 `pending` outbox 记录（与库存/订单/流水原子）。
  3. 事务提交后由 `pointsOutboxApplier` 负责投递，三类竞争者通过 `Claim(event_id)`（`UPDATE ... WHERE status='pending'` 条件更新）**恰好一次**认领并原子更新 `userDB` 余额：
     - **同步快路径** `applyAsync`：请求内即时尝试，用户无感延迟；
     - **Kafka 消费者** `ApplyPointsAdjust`：订阅新增 `user.points` 主题，复用既有 DLQ 降级；
     - **后台 relay** `RelayLoop`：定时扫描 `pending` 且超时的记录重试，是不依赖 Kafka 的兜底（覆盖无 Kafka / 发布前崩溃 / 同步路径 userDB 暂不可用）。
  4. `userDB` 更新失败时 `Requeue` 回 `pending`，由 relay/消费者重试 → **最终一致**；请求不再因积分库抖动而失败。
  5. `event.EventUserPointsAdjust` + `UserPointsAdjustPayload` + `config.topics.user_points`，生产者/消费者均已接线。

### 6.2 Kafka Consumer `reader.Close()` 无超时（C2，低） ✅ 已修复

- 位置：`internal/mq/kafka_consumer.go` `Subscribe` 末尾 `return c.reader.Close()`。
- 现象：kafka-go 的 `Reader.Close()` 不接受 `context`，若 broker 不可达可能阻塞关闭协程，使 `Subscribe` 在关闭期挂起。
- 实现：`Close()` 保留 `closeCh → cancel()` 解阻塞 `FetchMessage`；`Subscribe` 末尾在 `c.wg.Wait()` 之后，将 `c.reader.Close()` 放入 goroutine 并以 `select` + `time.After(closeTimeout)` 兜底（`close_timeout` 默认 10s），超时即放弃关闭返回，优雅关闭不再被拖死。`KafkaConsumerConfig` 新增 `CloseTimeout` 配置项（yaml `consumer.close_timeout`）。

### 6.3 Kafka Producer 队列满时无限起 goroutine（C3，中） ✅ 已修复

- 位置：`internal/mq/kafka.go` `Send`。
- 现象：队列（`QueueSize`，默认 8192）持续满载时，每次 `Send` 都 `go p.sendOne`，在持续背压下 goroutine 数量**无上界**增长（虽为短生命周期，但并发量失控时可能耗尽资源）。
- 实现：
  1. 新增 `sendSem chan struct{}`（容量 `MaxOverflowWorkers`，默认 256）作为溢出池信号量；队列满时仅当取到槽位才起一个 `sendOne` goroutine，将并发量限制在有限范围。
  2. 溢出池也打满（Broker 持续不可达）时不再起 goroutine，直接降级到本地 DLQ（`errProducerOverflow` sentinel，由 replay 补偿），既不阻塞调用方也不丢消息。
  3. 溢出 goroutine 现计入 `p.wg`（`wg.Add`/`Done`），`Close()` 的 `wg.Wait()` 会等待其在途发送完成后再 `writer.Close()`，避免向已关闭的 writer 写入。
- 配置：`KafkaProducerConfig` 新增 `MaxOverflowWorkers`（yaml `producer.max_overflow_workers`，默认 256）。

### 6.4 `userDB` 连接关闭（C1 延伸，低） ✅ 已修复

- 位置：`cmd/server/main.go` `initDatabases`。
- 现象：`businessDB` 已修复关闭；但 `userRepo` 底层（MongoDB client 或 SQLite 回退）在关闭流程中未被显式关闭。
- 实现：`UserRepository` 接口新增 `Close()`；`gormUserRepository.Close()` 关闭 `sql.DB`，`mongoUserRepository.Close()` 断开 MongoDB client；`main` 关闭流程 `defer userRepo.Close()`。优雅关闭不再泄漏 userDB 连接池。

### 6.5 Kafka 消费者无消费组模式（KRaft 4.0 兼容）的已知限制（高/中优先级，暂未改）

- **背景 / 根因**：`kafka-go v0.4.51` 的 group coordinator 协议与 **Kafka 4.0 KRaft** 不兼容——只要 `ReaderConfig` 带 `GroupID`，`FetchMessage` 就在 coordinator 握手阶段返回 `UNKNOWN_SERVER_ERROR(-1)` 且无法自愈（已实测：即便改为「每 topic 独立 Reader + 共用 GroupID」仍复现）。可达的 Go 代理（`goproxy.cn` 最高仅镜像到 `v0.4.51`，`goproxy.io` 更旧为 `v0.4.50`，官方 `proxy.golang.org` 本网络不可达）**无法升级客户端**。因此当前实现改为「**无消费组 + 按分区直读**」（`internal/mq/kafka_consumer.go`）：对每个 `(topic, partition)` 建一个不带 `GroupID` 的 `Reader` 直连分区，完全不经过 coordinator；offset 由本地 `offsetStore` 持久化（默认 `./data/kafka-offsets.json`，每 5s 落盘 + 关闭时落盘），重启续读。该改法已验证不再报 `-1 Unknown`。

- **已知限制（按优先级）**：

  1. ~~**【高】多实例重复消费 / 无法水平扩展**~~ ✅ 已修复（见 §3.53）：无 group coordinator 分配 partition，N 个实例会各自消费全部 partition，消息被重复处理。现已支持 `mq.kafka.consumer.instance_id` / `instance_count` 静态分区分配（`partition % instanceCount == instanceID`），多副本 Pod 各持互不重叠的分区子集，实现水平扩展。（越界配置 `instance_id>=instance_count` 现由 `config.Validate` 在启动/热更新期拦截，避免运行期退化全量消费导致重复消费，见 §3.63。）
  2. **【高】offset 持久化为本地文件，非分布式**：路径 `offset_store_path`（默认 `./data/kafka-offsets.json`）。多实例各自写本地文件、互不共享；容器重建 / 调度到新节点后文件丢失 → 重启从头或从最新重读（视 `start_from_latest`）。且落盘为「每 5s 一次 + 关闭时」，进程被 `kill -9` 会丢失最近窗口的 offset → 重新消费。多实例若错误共用同一路径，`flush` 会互相覆盖 → offset 损坏。**现已由框架自动按实例区分 offset 文件路径（见 §3.53 `instanceOffsetPath`），`instance_count>1` 时无需手工改路径**；且**分布式 offset 能力已具备（P1 路径）**——`WithProgressStore` 注入 `SQLProgressStore`（与业务库同实例）即获跨节点持久、容器重建不丢（见 §3.27 / `consumer_progress.go`），默认文件存储仍定位单节点。**本轮补充**：新增 `offset_flush_interval`（见 §3.58）可缩短文件存储的崩溃重放窗口。要彻底消除「跨容器持久」须改用 SQL 存储（配置接入点需由 bootstrap 注入，非默认），故本项标记为「P1 路径已具备、默认文件存储仍本地」。
  3. ~~**【中】at-least-once 重复窗口**~~ ✅ 已收敛（见 §3.58）：offset 在处理成功后由后台 goroutine 落盘，`handle` 与 `store.set` 非原子，进程崩溃会重放「处理中 + 最近窗口」的消息。现新增 `mq.kafka.consumer.offset_flush_interval`（默认 5s，可调小缩短窗口）；要彻底消除窗口可开 `ordered_commit=true`（每条消息同步落盘 offset，单分区串行）；关键事件统一接 `event_dedup` 表可把 at-least-once 收敛为 effectively-once。at-least-once 本身是无消费组直读模式的固有权衡，无法在框架层消除到 exactly-once（除非 handler 在 DB 事务内推进 SQL offset）。

  6. ~~**【低】`start_from_latest` 交互反直觉**~~ ✅ 已修复（见 §3.56）：仅当本地无 offset 文件时生效；一旦 offset 文件存在，`SetOffset` 优先从已处理位置续读，改 `start_from_latest: true` **并不能**「跳过积压」。现 `Subscribe` 在文件存储模式下若检测到 `start_from_latest=true` 且 offset 文件已存在，会 `Warnf` 提示「改此值不能跳过积压，需删文件重启」，避免运维误以为改配置即可跳过积压。
  7. ~~**【低】单 topic 查询 partition 失败即整体订阅启动失败**~~ ✅ 已修复（见 §3.54）：`partitions()` 失败（topic 不存在且 broker 未开 `auto.create.topics.enable`）会让整个 `Subscribe` 返回错误，不及之前消费组「部分 topic 就绪也能跑」的韧性。现默认为韧性模式：单 topic 查询失败仅告警并跳过、继续订阅其余就绪 topic，仅当【全部】 topic 都失败时才启动失败；可用 `mq.kafka.consumer.partition_fetch_strict=true` 恢复严格 fail-fast。
  8. ~~**【低】多连接开销**~~ ✅ 已收敛（见 §3.58）：每个 `(topic, partition)` 一个 `Reader` 一个连接，分区总数大时连接数 = partition 总数（如 `12 × 6 = 72`），需关注 broker 连接数上限。现新增 `mq.kafka.consumer.connection_warn_threshold`：reader 数（=broker 连接数）超过阈值时启动 `Warnf` 提示合并分区 / 迁移消费组（默认 0 不告警，避免扰民）。结构性降低连接数需架构调整（多分区单 reader 或恢复消费组），不在 no-group 直读模式内。

## 八、遗留建议（非本次范围）

1. **L1 性能**：当前 L1(Ristretto) 也以 JSON 字节存储，命中时需 marshal+unmarshal 一次，未发挥进程内缓存"零序列化"的优势。若追求极致读性能，可评估 L1 直接缓存 Go 对象（需权衡内存与并发安全）。

3. **README 容量表**：`docs/00_文档导航.md` 百万级建议表中 `max_open_conns 200~400` 为生产语境，需与服务端 `max_connections` 同步调高，可按需补注。
4. **跨库一致性（6.1）**：建议作为后续迭代的高优先级改造项，复用现有 Kafka + DLQ 基建落地 Outbox。

## 九、防御性编码清单（§3.39–§3.46 收敛经验沉淀）

> 来源：本轮对「全链路崩溃面」的系统性收敛（消费侧 → 持久层 → ES → 限流后台 → 缓存 → 优雅关闭 → 竞态 → 密钥解析）。以下条目作为团队可复用的防御性编码硬规则。

### 9.1 必须加 `, ok` 守卫的三类断言
1. **后台 goroutine 内的类型断言**（无 `gin.Recovery` / 无 `recover` 兜底）→ 必须 `, ok`；脏 entry 跳过而非 panic。
   - 例：`middleware/ratelimit.go` 的 `cleanup()` 跑在 `go func(){ for range ticker.C }`，原 `v.(*tokenBucket)` 裸断言会击垮进程 → §3.43 加 `, ok`。
2. **全局 / 跨包共享状态的类型断言**（类型不可控，任何代码都可能写入）→ 必须 `, ok`。
   - 例：`cache/l2.go` 的全局 `lockTokens sync.Map` → §3.44 加 `, ok`。
3. **不可信外部输入（配置文件 / 文件 / 网络解析结果）的类型断言** → 必须 `, ok` 并转友好 error（禁止启动期 / 运行期 panic）。
   - 例：`pkg/jwt/jwt.go` 的 RSA 密钥解析，误配非 RSA 密钥原会启动 panic → §3.46 加 `, ok` + error。

### 9.2 可维持原样的断言（避免防御性噪音，契合 §四「不误改」）
- **封闭实例内部状态 + 运行在 handler 请求链路（`gin.Recovery` 兜底，panic 只变 500 不崩进程）** → 按构造只存该类型时维持原样。
   - 例：`cache/hotkey.go` 的 `b.m`（`string→*hotCounter`，仅 `Record` 写入且无独立后台 goroutine）；`middleware/ratelimit.go` 的 `getBucket`/`actual`（仅限流器自身写 `*tokenBucket`，跑在 gin 中间件链内）。

### 9.3 接口扩展的配套纪律
- 给 `repository` 等接口**新增方法**（如 `Close() error`）时，必须同步：① 所有生产实现；② 所有**测试夹具**（`fake*`/`noop*` 内存实现）+ `var _ repo.X = (*fakeY)(nil)` 编译期约束。遗漏夹具会导致 `go test` 直接 `build failed`（§3.43 修复的 8 处夹具）。
- 收口点：`Databases.Close()` 串起全部 adapter 的 `Close()`，且 `Run()→shutdown()→dbs.Close()` 调用链完整、关闭顺序正确（先停后台协程/消费者 → 排空缓冲 → 最后关 cache+db），§3.37/§3.44 已闭环。

### 9.4 不可信配置 / 部署形态
- 生产形态（多副本 / Leader 选举）却仍用 insecure MQ（memory/none/noop）时，**启动期硬拒绝**（§3.40 `validateInsecureMQ`），避免事件总线静默丢消息；紧急逃逸走显式环境变量。
- 不可信密钥 / 证书解析失败必须转 error，禁止 panic（§3.46）。

### 9.5 验证基线（固化进 CI）
- `make test` 与 `.github/workflows/ci.yml` 均已 `go test -race -count=1 ./...`：**竞态基线固化进 CI**，每次提交自动跑（§3.45/§3.46 已确认）。
- 全仓 `go vet ./...` + `go build ./...` 必须 0。
- 新增走缓存的 repository 读方法一律经 `DecodeCached[T]` 还原，禁止直接类型断言（§五）。

### 9.6 接口与 nil 指针陷阱（§3.47）
- **现象**：具体类型指针（如 `*T`）的 `nil` 值赋给接口变量后，**接口非空**（携带类型信息）、底层指针为 `nil`；此时 `iface != nil` 误判为 `true`，调用接口方法时方法接收者为 `nil`，访问值类型字段（如 `sync.RWMutex`）即 panic。
- **高发场景**：「未启用某能力时持有 nil 指针、但调用处把该指针直接塞进接口参数」——`bootstrap.initScheduler` 把 `a.leader`（未启用选主时为 `(*LeaderElector)(nil)`）直接传给 `leaderElector` 接口参数，导致 `idle-timeout-scan` 等四个定时任务 panic（§3.47）。
- **根因修复**：把「可能为 nil 的具体指针」转成接口时，**显式判断 `if p != nil { iface = p }`，否则保持真正的 nil 接口**，使 `iface != nil` 判定生效。
- **纵深防御**：接口方法对 `nil` 接收者做守卫（如 `IsLeader` 的 `if e == nil { return true }`，无选主语义 = 正常执行），即使再有 nil 底层指针路径也不 panic。
- **单测要点**：构造「nil 底层指针接口」用例（如 `var nilLE *T; f(nilLE)`）直接验证门控/守护函数不 panic 且正确降级。

### 9.7 下游等待必须有界（§3.48）
- **现象**：HTTP 请求把 `ctx` 透传给 GORM/DB 查询；若 ctx 无 deadline 且 DB 连接池（`max_open_conns`）被并发打满，`database/sql` 会让请求**无限等待空闲连接**，表现为极长尾（p99=15.47s，仅顶端 ~1%）。
- **根因修复（请求超时中间件）**：全局中间件 `middleware.Timeout` 给每个请求的 ctx 注入 `context.WithTimeout`（默认 10s，可配 `server.request_timeout`）。`database/sql` 在等待连接时监听 ctx，deadline 到达即取消等待 → 把无限挂起收敛为有界 504。置于 `Recovery` 之后、用**同 goroutine** 执行 `c.Next()`，确保 panic 仍被 `Recovery` 捕获。
- **容量侧（阈值本质）**：`p(99)<3000` 这类延迟阈值是「DB/锁是否成为瓶颈」的告警线，而非纯代码断言；要让 p99 真正达标，需按并发把 `database.*.max_open_conns` 上调、保证热路径走缓存（如 `GetDailyPoints` 走 Redis O(1) 而非 DB SUM）、并排查慢查询。超时中间件是「防无限挂起」的安全网，不替代容量规划。
- **单测要点**：用「慢 handler 等待 ctx.Done()」模拟被连接池阻塞的 DB 查询，断言超时返回 504；快 handler / 零配置默认兜底断言返回 200（`middleware/timeout_test.go`）。
- **请求关键路径不得串行占库连接（§3.48 第3项）**：把「业务提交后写另一库」的同步调用（如 `pointsOutboxApplier.applyAsync` 的 `userRepo.UpdatePoints`）改为**有界 goroutine 异步**（信号量限流 worker 池），请求「入队即返回」不再持有该连接；下游库不可用时由既有 Outbox/Relay 保证最终一致。要点：① worker 用 `context.Background()`+超时，**绝不沿用请求 ctx**（请求可能先返回取消 ctx）；② 池满时 `default` 分支**绝不阻塞请求**，降级为发布事件/交 relay 兜底；③ 并发上限须明显小于目标库连接池容量，为读路径留余量。
