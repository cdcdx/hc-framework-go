## 一、设计目标与总原则

面向 C 端高并发后台（百万级设备常驻、峰值数万心跳/秒、任务奖励与积分兑换瞬时并发），架构须同时满足：

- **高并发**：单实例高吞吐、低尾延迟；水平扩展近乎线性。
- **高可用**：任一组件（Redis/DB/MQ）抖动或失效不雪崩；过载自我保护；发布/缩容零中断。
- **易扩展**：新增消息队列、存储、业务域、中间件均以「适配器 / 接口」接入，不改动核心链路。

贯穿全程的五条工程原则：

1. **分层防护、各司其职**：每一层只解决一类问题（连接 / 速率 / 在途量 / 下游健康度 / 缓存），互不替代。
2. **快速失败（fail-fast）而非无限排队**：超限立即拒绝，把「不确定等待」转化为「确定的 429/503」，保护后端。
3. **降级优于崩溃**：依赖不可用时退而求其次（L2→L1、Redis→SQLite、同步→异步），保证核心链路存活。
4. **观测驱动**：每个防护层都暴露指标（Counter/Gauge/Histogram），容量是否合理、是否触发保护均可见。
5. **优雅退出**：先停止接收新流量，再排空在途请求，最后释放资源。

## 二、请求防护分层（高并发接入链）

一个请求从进入到业务处理，依次穿过以下防护层。每一层都是独立、可单独调参、可热更新的：

```
                 ┌──────────────────────── 客户端 / LB / Nginx ────────────────────────┐
                 │   TLS 卸载 · 前置限流 · 负载均衡                                        │
                 └───────────────────────────────┬─────────────────────────────────────┘
                                                   │
                        [Listener] 连接级快速失败（MaxConns / MaxConnsPerIP）  ← 超限直接断连
                                                   │
                [Recovery → Timeout → Trace → RequestInfo → Logger → CORS → Metrics]
                                                   │
                     [ConcurrencyLimit] 应用层有界并发 / 负载卸载（503）  ← 在途量上限
                                                   │
              [Ratelimit] 全局/用户/IP 令牌桶（429）  ← 速率上限（支持热更新）
                                                   │
   [CircuitBreaker] 熔断（下游错误率超阈即降级 5xx→快速失败）  ← 下游健康度
                                                   │
   [SecurityIPLimit → Captcha → Auth(JWT+黑名单+账号锁)]  ← 安全与身份
                                                   │
                                      业务 Handler / Service
```

### 2.1 连接级上限（`MaxConns` / `MaxConnsPerIP`）

- 位置：`net.Listener` 的 `Accept` 阶段（`internal/bootstrap/connlimit.go`）。Go 标准库 `http.Server` **无**此字段，故自行包装 Listener 在握手前拦截。
- 语义：全局并发连接数 / 单 IP 并发连接数超限，新连接被**立即关闭**。这是进程级「连接耗尽」防线，保护后端资源不被连接风暴打垮。
- 与 `ConcurrencyLimit` 的区别：连接数是「TCP 层」概念，并发限流是「HTTP 在途请求」概念。一个连接上可串行/管道化多个请求，二者维度不同、互补。

### 2.2 应用层有界并发 / 负载卸载（`ConcurrencyLimit`，本次新增）

- 位置：`middleware.ConcurrencyLimit`（`internal/middleware/concurrency.go`），挂在全局中间件链、业务处理器之前。
- **为什么需要**：限流按「速率」、令牌桶放行后请求仍会无限并发进入 DB/缓存/下游。短时突发（速率未超但瞬时并发极高）恰恰是打满 DB 连接池的典型场景——仅靠限流无法拦截。并发限流按「同时进行的请求数」设硬上限，达上限即**非阻塞**返回 503（load shedding）。
- **为什么非阻塞**：用 `semaphore.Weighted.TryAcquire`，拿不到立即失败，不排队。排队会放大尾延迟、与 `RequestTimeout` 抢夺资源。
- **为什么豁免系统端点**：`/health`、`/ready`、`/metrics`、`/debug/*`、`/swagger` 在过载时仍须可用——若 `/ready` 也被 503，K8s 会误杀正在排空的 Pod。
- **容量怎么定**：`concurrency_limit ≈ DB连接池上限 / 单请求平均下游并发度`。例如 `max_open_conns=300`、单请求平均占用下游并发 ≈0.1，则上限取 2000~4000。它是容量规划结果，**不是越大越好**。
- **重启生效**：信号量容量启动期固定、不可动态伸缩，与 `MaxConns` 一致不受热更新影响。

### 2.3 限流（`Ratelimit`）

- 全局 / 用户 / IP 三维度令牌桶，429。支持热更新（`/debug/reload`、SIGHUP）。详见 [405_安全与防护.md](405_安全与防护.md) §四。
- 心跳等「在线判活命脉」接口经 `exempt_paths` 豁免，避免 429 误判设备离线。

### 2.4 熔断（`CircuitBreaker`）

- 按路由独立、仅 ≥500 计入失败（4xx 不误触发）。下游 DB/缓存抖动时快速失败并触发全局降级。详见 [405_安全与防护.md](405_安全与防护.md) §四。

> 三层过载保护（速率 / 在途量 / 下游健康度）必须**组合使用**。缺任何一层都有盲区：
> - 只有限流：短时突发并发打满连接池；
> - 只有并发限流：恒定高速率慢请求仍会堆积；
> - 只有熔断：下游未「错误率超阈」但已「严重变慢」时不触发，长尾拖垮线程。

## 三、缓存体系（高并发读路径的核心）

三级缓存 `L1(Ristretto) → L2(Redis) → L3(主存储)` 是读并发的基石。三类经典问题及本框架对策：

| 问题 | 现象 | 对策（代码位置） |
|------|------|------------------|
| **穿透**（查不存在的 key） | 大量请求打到 DB | 布隆过滤器（L2）+ 空值缓存（`null_cache_ttl`） |
| **击穿**（热点 key 失效） | 同一热点 key 失效瞬间海量回源 | **进程内 `singleflight` 合并 + 跨进程分布式锁**（`cache/strategy.go`） |
| **雪崩**（大量 key 同时失效） | DB 瞬时压力陡增 | TTL 随机抖动（`ttl_jitter`）+ 延迟双删 + 热点 key TTL 放大 |

### 3.1 击穿防护的双重合并（重点）

热点 key 失效瞬间的并发回源是缓存击穿。本框架用两道合并：

1. **进程内 `singleflight`**：同一 key 的并发回源在本进程内合并为一次，消除「重复回源」放大效应，并作为 L2 不可用时的唯一本进程防护（填补原实现漏洞）。
2. **跨进程分布式锁**（`lock:source:<key>`，SETNX）：多副本部署下，仅持锁副本回源，其余自旋等待其回填。

关键工程细节：
- `singleflight` 的 leader 使用 `context.WithoutCancel(ctx)` 执行回源——避免某个等待者取消导致所有等待者共享一次回源失败（singleflight 标准陷阱）。
- L2 写必须**同步**：保证分布式锁释放前 L2 已写好，否则他副本抢到锁后 L2 仍 miss 会二次回源，破坏单飞语义。
- 抢锁失败的自旋用单个可 `Reset` 的 `time.Timer`，避免循环内反复 `time.After` 堆积短命 timer（高并发抢锁失败场景的 GC 压力）。

### 3.2 读写降级（流量降级）

`cache.degrade`：读降级（`read_skip_l2`）跳过 Redis 直读 DB、并仍用 singleflight 合并回源；写降级（`write_async`）同步写转异步（投递 Kafka 事件由消费者刷新，无 Kafka 则本地异步写 L2）。熔断打开时强制全量降级。详见 [405_安全与防护.md](405_安全与防护.md) §四。

## 四、水平扩展与高可用协调

### 4.1 扫描分片（Pod Sharding）

离线检测 scanner 按 `i % pod_total == pod_index` 分配活跃会话集合分片，消除「每副本全量扫描」的 O(K×N) 冗余。`pod_total` 可由 `HC_POD_TOTAL` 环境变量或 **Headless Service DNS** 动态发现（适配 HPA 自动扩缩）。详见 [101_架构说明.md](101_架构说明.md) §五、`idle` 配置。

### 4.2 死分片接管（Failover）

依赖 Leader 选举（Redis 租约）。各 Pod 周期性上报存活（`idle:pod-alive:{podIndex}`），Leader 发现某 Pod 失活即接管其分片，消除「Pod 宕机 → 其分片永不扫描」的可用性缺口。

### 4.3 选主（Leader Election）

多副本下仅 Leader 执行「恰好一次」类任务（回填、每日/每周任务重置、事件去重清理、Keyspace 通知配置）。L2 不可用时自动降级为「每 Pod 各自执行」（乐观锁兜底）。Redis 租约 + 续期，优雅关闭时释放锁加速接管。

### 4.4 多实例消息消费（无消费组直读）

Kafka 因 `kafka-go v0.4.51` 与 KRaft 4.0 group coordinator 不兼容，采用「无消费组 + 按分区直读 + `InstanceCount`/`InstanceID` 分区分配」替代消费组再均衡（[603_代码优化记录.md](603_代码优化记录.md) §6.5）。每个实例消费互不重叠的分区子集，实现水平扩展；offset 本地持久化（按 `instance_id` 区分文件）弥补跨重启不持久。

## 五、优雅退出与负载排水（高可用发布）

完整生命周期：`config → DB → JWT → 缓存 → 服务 → MQ → 调度/选主 → HTTP`，见 [504_启动流程与生命周期.md](504_启动流程与生命周期.md)。

优雅关闭（`bootstrap.shutdown`）核心两步与顺序：

1. **先摘流量**：关闭一开始即把就绪标志 `serving` 置 `false`（`handler.SetServing(false)`），`/ready` 立即返回 503 → K8s 就绪探针失败 → 本 Pod 从 Service 端点摘除、LB 停止转发新流量。
2. **再排空中途请求**：`srv.Shutdown` 仅等待已建立的在途请求完成（受 `shutdown_timeout` 兜底，超时强制关闭）。

随后按序释放：后台 goroutine（`bgCancel`）→ 限流器/验证码清理 → 事件驱动结算 → 心跳 flush → 调度器 → 选主锁 → MQ 消费者/生产者 → 日志服务 → 链路追踪 flush → 缓存与数据库连接池。每步带耗时日志，慢在哪一步一目了然。[702_优化清单与后续建议.md](702_优化清单与后续建议.md) / [603_代码优化记录.md](603_代码优化记录.md) 已修复其中多处 goroutine 泄漏与半成功连接未释放。

> 若缺少「先摘流量」这一步，关闭瞬间 LB 仍可能把请求转发到正在退出的 Pod，导致 5xx。就绪探针排水是高可用发布的标配。

## 六、可观测性（让防护「看得见」）

每个防护层均有指标（`/metrics`，独立 Prometheus Registry）：

| 防护层 | 关键指标 | 用途 |
|--------|----------|------|
| 限流 | `rate_limit_total{type,result}` | 拒绝速率 |
| 并发限流 | `http_concurrency_in_flight`（Gauge）/ `http_concurrency_rejected_total`（Counter） | 并发水位 / 负载卸载次数 |
| 熔断 | `circuit_breaker_state` / `circuit_breaker_transitions_total` | 熔断状态与切换 |
| 缓存 | `cache_*` 动态采集（L1 命中率/大小/驱逐、L2 开关、热点数） | 缓存有效性 |
| MQ | `mq_producer_*` / `mq_consumer_*` / `mq_*_dlq_backlog` / `mq_consumer_lag` | 投递/消费/积压 |
| 调度/仓储/追踪 | `scheduler_job_*` / `idle_repo_errors_total` / `trace_spans_dropped_total` | 后台任务与链路健康 |

推荐告警（节选，完整见 [403_可观测性与告警.md](403_可观测性与告警.md) §四）：`HighErrorRate`、`CircuitBreakerOpen`、`RateLimitRejectedSpike`、`ConcurrencyLimitRejected`（本次新增）、`MQConsumerLagHigh`、`MQConsumerDLQRateHigh`、`SchedulerJobPanic`。

## 七、容量规划与压测建议

1. **并发上限与连接池联动**：`concurrency_limit` 应 ≤ `DB max_open_conns / 单请求平均下游并发度`，并留余量给非请求路径（后台 scanner、消费者）。
2. **心跳豁免**：百万设备常驻下心跳（SETEX）峰值约 3.3 万/s，须在 `ratelimit.exempt_paths` 豁免或单独高配额；Redis `pool_size` 建议 200~500。
3. **压测配置**：`config.stress.yaml` 已放宽 `ratelimit.global`（`rate=20000`）并设 `concurrency_limit=4000`、`business.max_open_conns=300`（配合 `make mysql-stress-tune` 抬高服务端 `max_connections` 到 500），避免高并发 `Too many connections`。
4. **零超卖压测**：商城兑换路径豁免全局限流，聚焦库存并发竞争；结合 `PointsOutbox` + Redis Lua 原子封顶预占（消除每日积分上限 TOCTOU）验证一致性。
5. **观测先行**：压测时盯 `http_concurrency_in_flight` 是否贴近上限、`http_concurrency_rejected_total` 是否上升，据此回调 `concurrency_limit` 与副本数。

## 八、易扩展设计（新增能力的接入方式）

框架以「接口 + 适配器 + 组合根」支撑扩展，新增能力通常不触及核心链路：

- **新消息队列**：实现 `mq.Producer` / `mq.Consumer`（`internal/mq/adapter.go`），在 `mq/factory.go` 注册，`mq.type` 一行切换；跨切面逻辑已收敛到 `producerBase`（[702_优化清单与后续建议.md](702_优化清单与后续建议.md) §4）。
- **新存储**：实现 `db.Adapter` / `RelationalDB`（`internal/db/adapter.go`），在 `bootstrap.InitDatabases` 接入；异构后端（Mongo/CH/ES）不可用时统一回退 SQLite。
- **新中间件**：实现 `gin.HandlerFunc`，在 `router.Setup` 的全局链或分组链注册（如本次 `ConcurrencyLimit`）。
- **新业务域**：新增 `service/<domain>` 子包 + `repository` + `handler` + `router` 分组，复用缓存/限流/熔断/事件总线。
- **热更新参数**：经 `config.Manager`（atomic.Pointer 不可变快照），组件在请求路径实时读取，无需重启。

> 扩展点均以接口契约解耦；新增适配器/中间件请同步更新对应文档（[202_配置参考.md](202_配置参考.md) 配置、[405_安全与防护.md](405_安全与防护.md) 安全、[403_可观测性与告警.md](403_可观测性与告警.md) 指标）以保持 SSOT。
