# 24. 链路追踪架构

> **文档角色**：链路追踪设计与使用指南
> **对应源码**：`internal/trace/`
> **权威源约定**：Span 结构与 Exporter 配置以代码为准；告警规则以 [403_可观测性与告警.md](403_可观测性与告警.md) 为准；配置字段以 [202_配置参考.md](202_配置参考.md) 为准

---

## 一、设计目标

链路追踪需满足三个需求：

1. **零依赖**：核心追踪能力（生成 TraceID、Span 串联、日志导出）不依赖任何 OTel SDK 外部包，仅用 Go 标准库 + `go.opentelemetry.io/otel` 的 trace 值类型。
2. **OTel 兼容**：Span 结构、W3C Trace Context 传播标准（`traceparent`）与 OTel 生态完全互通，可随时切换到 Jaeger/Tempo 后端。
3. **可切换导出**：支持三种导出模式——日志（默认）、OTLP HTTP 推送、关闭。

---

## 二、核心概念

### 2.1 Trace 与 Span

- **Trace**：一次完整的请求链路，由全局唯一的 TraceID 标识。
- **Span**：链路中的一个工作单元，每个 Span 记录操作名称、起止时间、状态和可选的错误信息。

```
Trace: 4e29c3a1f2b8d7e9...
  ├── Span: HTTP POST /api/v1/idle/start  (server)
  │   ├── Span: IdleService.Start          (internal)
  │   │   ├── Span: Redis SETNX            (cache)
  │   │   └── Span: DB INSERT              (db)
  │   └── Span: MQ Send                   (mq)
  └── Span: Consumer process idle.settled  (consumer)
```

### 2.2 W3C Trace Context

框架使用标准的 `traceparent` HTTP 头传播追踪上下文：

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
              │  └───────── TraceID ─────────┘ └─── SpanID ───┘ │
              └─版本                                               └─追踪标志
```

- 上游服务传入 `traceparent` 时，当前服务继承 TraceID 并创建子 Span。
- 无传入时自动生成新 TraceID。
- 同时兼容旧版 `X-Trace-Id` 请求头（仅作为 TraceID 来源，不参与 W3C 传播）。

## 三、架构设计

### 3.1 模块结构

```
internal/trace/
├── trace.go          # 核心：Span 类型、Provider、Exporter 接口、默认日志导出
├── otlp.go           # OTLP/HTTP JSON 导出器（可选，零新增依赖）
└── trace_test.go     # 测试
```

### 3.2 接口体系

```go
// Exporter Span 导出器接口（默认实现：日志导出）
type Exporter interface {
    Export(ctx context.Context, spans []*Span) error
    Shutdown(ctx context.Context) error
}

// Provider 追踪器提供者
type Provider interface {
    Tracer(name string) Tracer
    Shutdown(ctx context.Context) error
}
```

- **`LogExporter`**（默认）：每 Span 一条 Zap 结构化日志，含 `trace_id`/`span_id`/`parent_id`/`duration_ms`/`status`/`error`。零外部依赖，日志平台即可串联。
- **`OTLPHTTPExporter`**（可选）：以 OTLP/HTTP JSON 格式批量 POST 到 `:4318/v1/traces`，对接 Tempo/Jaeger。内部有缓冲 channel + 后台 worker 批量 flush，优雅关闭时 flush 残余 span。
- **`none`**：关闭追踪，所有 `Start` 返回 noop span。

### 3.3 采样策略

由 `tracing.sampler` 配置控制：

| 采样器 | 配置值 | 行为 |
|--------|--------|------|
| 始终采样 | `always_on` | 所有请求都记录 Span |
| 关闭 | `always_off` | 不记录任何 Span |
| 比例采样 | `traceidratio` | 按 `tracing.sampler_arg`（0~1）比例采样 |
| 错误采样 | 任意 | 错误请求以 100% 概率采样（与上述策略叠加） |

## 四、使用方式

### 4.1 在 Handler 中使用

框架自动通过 `Trace()` 中间件为每个 HTTP 请求创建 server span 并注入 `traceparent`，业务层无需额外代码：

```go
// handler 中的 trace_id 已通过中间件注入 gin.Context
traceID := c.GetString("trace_id")
```

### 4.2 在 Service 中创建子 Span

```go
import "github.com/cdcdx/hc-framework-go/internal/trace"

func (s *IdleService) Start(ctx context.Context, ...) error {
    ctx, span := trace.DefaultTracer().Start(ctx, "IdleService.Start")
    defer span.End()

    // 记录业务逻辑...
    span.SetStatus(trace.StatusOK)
    return nil
}
```

### 4.3 在 MQ 消费者中提取

```go
// 从消息 Header 提取 traceparent
ctx := trace.ExtractHTTPHeader(context.Background(), func(key string) string {
    return msg.Headers[key]
})

// 创建消费 Span
ctx, span := trace.DefaultTracer().Start(ctx, "process idle.settled")
defer span.End()
```

### 4.4 记录错误

```go
if err != nil {
    span.SetStatus(trace.StatusError)
    span.RecordError(err)
    return err
}
span.SetStatus(trace.StatusOK)
```

## 五、导出器配置

### 5.1 日志导出（默认）

```yaml
tracing:
  exporter: stdout    # 使用 Zap 结构化日志导出
  sampler: traceidratio
  sampler_arg: 0.1   # 10% 采样率（生产推荐）
```

日志示例：
```json
{
  "level": "info",
  "ts": "2026-07-20T10:30:00+08:00",
  "msg": "span",
  "trace_id": "0af7651916cd43dd8448eb211c80319c",
  "span_id": "b7ad6b7169203331",
  "parent_id": "",
  "operation": "HTTP POST /api/v1/idle/start",
  "duration_ms": 45.2,
  "status": "OK"
}
```

### 5.2 OTLP 导出（对接 Jaeger/Tempo）

```yaml
tracing:
  exporter: otlp
  otlp_endpoint: "http://tempo:4318/v1/traces"
  sampler: always_on
```

- 使用内部缓冲 channel（容量 `otlpQueueSize`=2048）和后台 worker 批量 flush。
- 队列满时丢弃并递增 `trace_spans_dropped_total` 计数器（Prometheus 可告警）。
- 优雅关闭时 `Flush` 所有残留 span。

### 5.3 关闭追踪

```yaml
tracing:
  exporter: none      # 关闭追踪
```

## 六、中间件集成

`Trace()` 中间件位于全局中间件链第二层（紧接 `Recovery()`），确保所有下游中间件和 handler 都能拿到追踪上下文：

```
Recovery → Trace → RequestInfo → Logger → CORS → Metrics → ConcurrencyLimit → ...
```

- 优先从请求头 `traceparent` 提取父 span 上下文。
- 兼容旧版 `X-Trace-Id` 请求头（回退方案）。
- 始终设置响应头 `X-Trace-Id`，保持旧链路按 trace_id 串联日志。
